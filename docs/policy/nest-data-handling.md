## 1 行で

karasu-nest は、**投稿者が自分の環境で作ったアーキテクチャモデル（`.krs`）を預かって共有する**。
**ソースコードを読まない。** 保持するのは投稿物と、投稿者の GitHub 識別子だけで、
どちらも投稿者自身が削除できる。

## 何が変わったか

初版は「repository のソースを読み、モデルを生成し、そのモデルだけを保存する」サービスを
記述していた。ADR-2578 が生成を廃止したので、その記述は**まるごと当てはまらなくなった**。

| 初版のサービス | 現在のギャラリー |
| --- | --- |
| installation 経由で他人の repository を読む | **読まない。** GitHub API に触れるのはサインイン時の `GET /user` だけ |
| ソース本文をモデルプロバイダに送る | **送らない。** モデルを呼ばない |
| 生成物を 90 日保存し、TTL で消す | 投稿物を**投稿者が削除するまで**保存する |
| アンインストールが削除の単位 | **アカウント削除**が削除の単位 |
| 個人データを持たない | **GitHub の数値 user id と login 名を持つ**（下記） |

最後の行は意図した越境である。[ADR-2262](../adr/2262-nest-intake-and-completion.md) は
完了通知にメールを採らなかった理由を「karasu-nest が抱える最初の個人データになる」と
書いた。ADR-2578 はその線を**識別子について意図的に越える** — 匿名投稿を許すと、
取り下げ請求に応じる相手も、荒らしを止める手段も存在しないためである。
**越えるのはそこまでで、メールアドレスは持たない**（理由は「保持」節）。

## 何を読むか

| 対象 | 読む | 保存する |
| --- | --- | --- |
| repository のファイル一覧・ソース本文 | ❌ **一切読まない** | ❌ |
| 投稿された `.krs` | ✅（投稿者が送ってくる） | ✅ |
| GitHub の数値 user id | ✅（サインイン時） | ✅（鍵として） |
| GitHub の login 名 | ✅（サインイン時） | ✅（表示用。サインインのたびに更新） |
| メールアドレス・氏名 | ❌ **要求しない**（OAuth の scope は空） | ❌ |

サインインで要求する scope は**空**である。`GET /user` は scope の無いトークンでも
数値 id と login 名を返し、その 2 つがアカウント記録のすべてなので、それ以上を要求する
理由が無い。

**投稿物の中身については正直に書く。** `.krs` は構造の記述だが、投稿者が書いたラベルや
`description` に何が入っているかはサービスが決められない。投稿時に**資格情報の形をした
文字列を検査して拒否する**（`packages/nest/src/redact/`、18 規則）が、検出は形に
基づくので万能ではない。氏名やメールアドレスの規則は無い。したがって
「投稿物に個人データは含まれない」とは書けない — **投稿者が書いたものが公開される**。

## 何をどれだけ保存するか

保存先は Cloudflare Workers KV。

| 何を | 鍵 | 保持 |
| --- | --- | --- |
| 投稿された `.krs`（タイトル・公開設定を含む） | `sub/v1/<account>/<id>` | **投稿者が削除するまで** |
| アカウント記録（数値 id・login 名・初回/最終サインイン） | `acct/v1/<account>` | **アカウント削除まで** |
| セッション | `sess/v1/<account>/<session>` | 30 日 |

**3 つとも鍵の最外がアカウント id である。** これは設計であって偶然ではない — アカウント
削除が prefix 3 本を舐めるだけで完結する形にしてある。ここに当てはまらない鍵空間を足すと
削除経路から外れるので、[TPL-2226](../test-perspectives/TPL-2226-every-key-prefix-must-be-purgeable.md)
がその失敗を見る。

投稿のサイズ上限は **1 投稿あたり 256KB**（バイト数。マルチバイトのラベルでも同じ上限）。

> **保持期間とサイズ上限は実装の定数と機械的に突き合わせている**
> （`scripts/lint/nest-retention-policy-sync.test.ts`）。定数を変えてこの文書を直し忘れると
> テストが落ちる。ただし機械検証が及ぶのはそこまでで、**新しい鍵空間が増えたことは検出できない** —
> その穴は `gallery-purge-coverage.test.ts` の seeder 台帳を人が読んで塞ぐ。

### なぜ期限を置かないか

**投稿者が管理するコンテンツが黙って消えるのは、この機能の目的と正面から衝突する。**
90 日で消えれば「投稿したはずの図が無い」という問い合わせが発生し、自己管理コンソールが
減らそうとしているものを自分で作ることになる
（[TPL-2587](../test-perspectives/TPL-2587-author-managed-content-has-no-ttl.md)）。

代償として保持が無期限になるが、**「投稿者が削除するまで保持し、アカウント削除ですべて
消える」は日数より説明しやすい**。そして期限切れの予告が要らないので、
**メールアドレスを持たずに済む** — ADR-2262 が避けた線を、ここではこれ以上越えない。

セッションだけは期限を持つ。資格情報は、自分で失効するのが正しい唯一の種類だからである。

## 投稿を誰が読めるか

投稿には公開設定が 2 つある。

- **公開**: URL を知っていれば誰でも読める。これがギャラリーの目的そのものである
- **非公開（unlisted）**: **配信しない。** 本人以外には「そんな投稿は無い」という応答を返す。
  存在しない id への応答と**完全に同一**で、「この人が投稿して取り下げた」を確かめる手段に
  しないためである

非公開は削除の手前に置いてある。取り下げ要求の多くは「消したい」ではなく「いま見られたく
ない」で、可逆な操作で済む要求が削除に流れないようにするためである。

## 削除

**投稿者が自分で行う。** コンソール（`/console`）で:

- 個別の投稿を削除する
- 投稿を非公開にする（可逆）
- 投稿を差し替える
- **アカウントを削除する** — 投稿・アカウント記録・全セッションが 1 操作で消える

問い合わせを待たずに本人が完結できることが、この面の目的である。ただし削減できるのは
**投稿者本人からの取り下げ**だけで、第三者からの申し立て（なりすまし・権利侵害）は
申立人がアカウント保持者でないので self-service できない。件数は減るが難易度は減らない。

一点だけ留保がある。Cloudflare KV の一覧は eventually consistent なので、purge の直前に
着地した書き込みが最初の一覧に現れないことがありうる。そのため削除経路は**再実行できる形**に
してある。「1 回の呼び出しで完全性を保証する」とは書かない。

## 書き込み

**しない。** サービスが repository に書き込む経路は存在しない。生成物を pull request で
返す機能（旧 `PR_DELIVERY`）は、返すべき生成物が無くなったので削除した。投稿者は自分の
ファイルを自分で commit する。

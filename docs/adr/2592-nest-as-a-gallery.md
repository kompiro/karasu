## 背景

[ADR-2578](2578-nest-retires-server-side-reverse.md) が **server-side reverse をやめてギャラリーへ転じる**ことを決め、ADR-1990 と ADR-1994 を supersede した。決めたのは**方向**であり、決定 5（別 Worker サービス）と決定 6（データ信頼が成立条件であること）を引き継いだ。

その時点で意図的に ADR に載せなかったものがある。**ギャラリーをどう作るか**である。当時それは `docs/design/nest-as-a-gallery.md` にあり、実装が 1 行も無かった。リポジトリの規約は「実装を伴う設計は実装の後片付けで昇格させる」であり（`.claude/rules/adr.md`）、先に昇格させれば帰結の確かめられていない決定を記録することになる。

実装スライス #2586〜#2591 が完了したので、その規約どおり昇格させる。**本 ADR は方向を再決定しない** — ADR-2578 が決めたことは有効なままで、ここに記録するのは構築判断である。

## 決定

**投稿は GitHub repository に紐づけず、投稿者が自分で管理する。** 内訳は次の 7 つ。

### 1. 投稿の資格 — repository ではなく投稿者を認証する

任意の `.krs` を投稿でき、GitHub は**投稿者の本人性にだけ**使う。push 権限の証明には使わない。

- 投稿は repository に紐づかないので、**証明する対象が存在しない**
- ログインが与えるのは権限の証明ではなく**責任の所在**、すなわち凍結できるハンドルである
- 匿名投稿を却下したのは、取り下げ請求に応じる相手も、濫用を止める手段も存在しなくなるため

要求する scope は**空**である。`GET /user` は権限の無いトークンでも数値 id と login 名を返し、その 2 つがアカウント記録のすべてである。

**この決定は [ADR-2262](2262-nest-intake-and-completion.md) が引いた線を意図的に越える。** あの ADR は完了通知にメールを採らなかった理由を「karasu-nest が抱える最初の個人データになる」と書いた。越えるのは識別子までで、メールアドレスは持たない — 理由は決定 5 の帰結である。

### 2. URL 空間 — 投稿 id の独立した名前空間

`owner/repo` は使わない。

これは**方向の帰結であって独立した選択ではない**。投稿が repository に紐づかない以上、`owner/repo` を鍵にする意味が最初から無い。

結果として [TPL-2249](../test-perspectives/TPL-2249-resolution-stays-deterministic.md)（解決は決定的である）は**満たされる**: `owner/repo` は従来どおり commit された `.krs` だけを指し（app の permalink 面）、投稿物は別の名前空間に居るので、同じアドレスが 2 つのものを指すことがない。ギャラリーは [ADR-2249](2249-permalink-generation-seam.md) の 2 面の隣に立つ**第 3 の面**である。

公開 id は `<account>-<slug>` の形を採り、**アカウントを含む**。鍵が id から直に決まるので逆引き索引が要らず、削除経路が知るべき prefix が 1 つ増えない（決定 4）。

[TPL-2254](../test-perspectives/TPL-2254-durable-record-points-at-durable-address.md)（記録は記録より長生きするアドレスを指す）は、**この面では適用対象が消える**。設計時にこの観点を挙げたのは「投稿を元の repo の commit とどう対応させ続けるか」という問いのためだったが、決定 1 が投稿を repository から切り離したので、対応させ続けるべきアドレスが存在しない。投稿 id はサービス自身が発行し、投稿者が消すまで有効で、外部の可変な参照を持たない。観点そのものは repo の外を指す記録（AT・TPL・design doc）で引き続き有効であり、`scripts/lint/record-source-paths.ts` がそちらを機械で見る。

**[ADR-2259](2259-permalink-payload-cap.md) の 8000 文字上限はこの面に適用されない。** あの上限が効くのは `resolveRepoPermalink` が repo の `.krs` を `/s?s=…` に畳み直すからで、縛っているのは **URL に載るサイズ**である。ギャラリーは id で配信するので、モデルが URL に載る経路そのものが無い。ADR-2259 は app の permalink 面の決定として**引き続き有効**である。

### 3. 品質保証 — parse と structure-only 検査のみ

検査は 2 つだけで、これ以上増やさない。

- **parse できること** — 開けない文書はギャラリーに置く意味が無い。品質の基準ではなく、エントリと壊れたリンクの違いである
- **structure-only 検査** — 資格情報の形をしたものを載せた投稿は、公開せず拒む

**分解の質は投稿者のものである。** [ADR-2077](2077-reverse-bc-granularity.md) は生成物の bounded-context 粒度を定めたが、それはサービスが生成していたから課せた。投稿はそうではなく、そうすべきでもない — それは投稿者自身のシステムのモデルであって、サービスが保証する立場にない。

structure-only 検査は既存の `assertStructureOnly` を再利用するが、**意味が変わる**。それは egress の扉の後半（モデルが漏らし返していないかの確認）だったが、モデルも egress も無くなったので、いまや**唯一の検査**であり ingress で走る。fail-closed は変えない — 検出は「資格情報の形をしたものが公開されようとした」証拠であり、洗って通すのは事故を隠して成果物を出すことである。

### 4. 削除の単位はアカウントであり、鍵はそう並んでいる

`acct/v1/<account>` ・ `sub/v1/<account>/<slug>` ・ `sess/v1/<account>/<session>` の 3 本とも、**アカウント id を最外に置く**。

これは ADR-1990 決定 6 が「uninstall = purge」のために installation を最外に置いたのと同じ技法で、単位だけが変わっている。アカウント削除が prefix 3 本を舐めれば完結する形にしてあり、当てはまらない鍵空間を足すと削除経路から外れる。[TPL-2226](../test-perspectives/TPL-2226-every-key-prefix-must-be-purgeable.md) がその失敗を機械で見る（`gallery-purge-coverage.test.ts`）。

### 5. 保持は日数ではなく条件 — 投稿者が削除するまで

**投稿物とアカウント記録に期限を置かない。** セッションだけが期限を持つ。

現行のストアは全部 TTL で切れる設計だった（生成物 90 日、計測 400 日）。それは「保存しない」を担保するためのもので、ギャラリーはそれを反転させる。**投稿者が管理するコンテンツが黙って消えるのは、自己管理の面を用意した目的と正面から衝突する** — 90 日で消えれば「投稿したはずの図が無い」という問い合わせが立ち、減らそうとしたものを自分で作ることになる。

代償は無期限保持だが、「投稿者が削除するまで保持し、アカウント削除ですべて消える」は日数より説明しやすい。そして**期限切れの予告が要らないので、メールアドレスを持たずに済む** — 決定 1 が越えた線を、これ以上越えずに済む。

期限の**不在**は待っても証明できないので、書き込み口を 1 か所に閉じて `expirationTtl` が付かないことを検査する（[TPL-2587](../test-perspectives/TPL-2587-author-managed-content-has-no-ttl.md)）。

セッションが持つその 1 つの期限は、[#2655](https://github.com/kompiro/karasu/issues/2655) 以降**使うたびに延びる**（最終使用から 30 日）。延びる期限だけでは資格情報が自分を無期限に更新できてしまうので、発行から 90 日の**延びない上限**を外側に置く。KV が強制できる期限は鍵ごとに 1 つで、それは延びる側に使っているため、上限は読み取り時に確かめる（[TPL-2655](../test-perspectives/TPL-2655-sliding-expiry-needs-an-unrenewable-cap.md)）。

### 6. コンソールは nest 自身が返す — 非公開を削除の手前に置く

投稿者が自分の投稿を管理する面（一覧・非公開化・差し替え・削除・アカウント削除）を、**nest のホスト名で nest 自身が返す**。

- **app とは別のサイトにする**。`packages/app`（`karasu.kompiro.dev`）には同居させない
- 別 origin の静的サイトから nest の API を叩く形は採らない。セッションを持つ最初の面で CORS と cookie の跨ぎを設計することになり、入口が広くなりすぎる。nest のホスト名は app と別なので、「別のサイト」という要件は同一オリジンのまま満たされる
- サーバーレンダリング HTML と素の form。**クライアント JS を置かない** — セッション cookie と同一オリジンなので、ここで配る script はそのセッションの権限で走る

**非公開（unlisted）を削除の手前に置く。** 取り下げ要求の多くは「消したい」ではなく「いま人に見られたくない」である。可逆な操作で済む要求が削除に流れなければ、「誤って消した」という**この機能自身が生む問い合わせ**が発生しない。

**アカウント削除は 1 操作にする。** そうしないと「全部消してアカウントも消したい」という最も面倒な要求が人手に残り、それはこの面が消そうとしているものそのものである。

削減できるのは**投稿者本人からの取り下げだけ**である。第三者からの申し立ては、申立人がアカウント保持者でないので原理的に self-service できない。**コンソールは件数を減らすが難易度は減らさない** — 残るのは元々少なく元々重い案件で、定型作業が消えたぶんそれらに時間を割ける。

### 7. 第三者からの申し立ては GitHub Issue で受ける

専用フォームを作らない。

- **karasu-nest が集める項目が増えない。** 申し立てる側は既に GitHub アカウントを持っており、専用フォームを作らないので、このサービスの store に新しい欄が生えない。**申し立てそのものは GitHub 上の新しい公開記録になる** — 申立人の識別子と主張内容が残る。増えないのはこちらが抱える分だけである
- 対応の経緯が公開され、判断の一貫性が追える
- 実装ゼロで始められる
- **代償: 申し立て自体が公開される。** 「この図は当社の内部構造だ」という申し立ては、それ自体が情報の開示になりうる。公開が問題になる種類の申し立てには別経路が要るが、必要になってから足せる。ToS には窓口として明記する

## ADR-1783 の statelessness を手放したことの記録

[ADR-1783](1783-karasu-nest-hosted-preview.md) は inline share をステートレスにした理由を「**DB・保存型 paste・モデレーション面を持たず**、運用負荷ゼロ」と書いた。**ギャラリーはこの 3 つをすべて持つ。**

ADR-1783 は既に ADR-1990 に superseded されており、本 ADR がさらに覆すものではない。それでも書き残すのは、**あの判断が正しかった理由がいまも正しい**からである — 保存型の面はモデレーションを連れてくる。ギャラリーはそれを承知で引き受けた。引き受けた根拠は次の 2 つで、どちらも ADR-1783 の時点には無かった。

- **法務の重りが軽くなった。** ADR-1996 の未了 6 件のうち 2 件が消滅し（モデルを呼ばず、他社の管理者から処理を委託される立場に無い）、残る 4 件も他人の private コードの処理ではなくなったぶん小さい
- **モデレーションの入口を投稿者本人に寄せた。** 決定 6 のコンソールが定型の取り下げを人手のキューから外す。ADR-1783 が恐れたのは運用負荷であって、その負荷の大半は本人が自分で解決できる種類のものだった

**残る負荷は正直に書く。** 第三者からの申し立て（なりすまし・権利侵害）は self-service できず、判断を要する。ADR-1783 の懸念のうち消えていないのはここであり、[#2591](https://github.com/kompiro/karasu/issues/2591) の ToS がその窓口を定める。

## ADR-1996 への追記 — 未了 6 件の帰結

| ADR-1996 の未了 | ギャラリーでの扱い |
| --- | --- |
| Anthropic との zero-retention 契約 | **消滅** — モデルを呼ばない |
| 企業向け DPA の要否判断 | **消滅** — 他社が管理するデータを処理者として預かる関係が無い（下記） |
| privacy policy | 残る（縮小）— 草案 `docs/policy/nest-privacy.md` |
| ToS（責任制限） | 残る + **投稿物の権利帰属**という新条項 — 草案 `docs/policy/nest-terms.md` |
| 公開先の決定 | **決定** — `docs/policy/` を法務レビュー後に docs-site へ |
| 問い合わせ窓口 | **決定** — GitHub Issue（決定 7） |

「他社が管理するデータを処理者として預かる関係が無い」は、**投稿物に第三者の情報が入らないという意味ではない**。`.krs` のラベルや description に何を書くかは投稿者が決めるので、`docs/policy/nest-privacy.md` は「投稿物に個人データは含まれない」とは書けないと明記している。消滅するのは**こちらが企業顧客に差し出す側の DPA** で、理由はこのサービスが自分の利用者に対する**管理者**であり、他社の管理者から処理を委託される立場に無いことである。

**ベンダ側の DPA はこれとは別で、消滅していない。** 役割は製品と契約ごとに違うので、一括りにしない。

| 相手 | 何を | 役割 |
| --- | --- | --- |
| Cloudflare | KV に置く投稿物・アカウント記録・セッション | こちらが管理者、Cloudflare が**処理者**。Cloudflare Customer DPA が適用される（こちらが受け入れる側であって、起草する側ではない） |
| GitHub | サインイン時の `GET /user` | GitHub は**独立した管理者**であって、こちらの処理者ではない。OAuth アプリの開発者は取得したデータについて独立した管理者になる |

privacy policy が引き受けるのは**両者の開示**であって、DPA の起草ではない。`docs/policy/nest-privacy.md` の「誰に渡るか（サブプロセッサ）」の表は GitHub をサブプロセッサとして並べているが、上記のとおり OAuth の関係はそれに当たらない。**法務レビュー（[#2591](https://github.com/kompiro/karasu/issues/2591)）で製品・アカウント種別・契約ごとに確定させる**必要があり、本 ADR はその確定を先取りしない。

**ADR-1996 は accepted のまま**である。決定 6（データ信頼が成立条件であること）は ADR-2578 が引き継いでおり、対象が「他人の private コード」から「投稿物と識別子」に変わっただけで、成立条件という位置づけは生きている。

## 却下した案

### 匿名投稿を許す

投稿の敷居は下がるが、**取り下げ請求に応じる相手が存在しなくなる**。「これは自分のものだ、消してほしい」と言われても、投稿した人と連絡が取れず、投稿を凍結する単位も無い。濫用に対しても同じで、止める手段が「その投稿を消す」しかなくなる。

### repository への push 権限で投稿を検証する

「自分がメンテしている repo のモデルだけ投稿できる」は、なりすまし対策として自然に見える。採らなかったのは 2 つの理由による。

- **投稿は repository に紐づかない**という決定 1 と両立しない。手元の複数 repo にまたがるシステム、社内の非公開システム、まだ repo になっていない設計はどれも投稿できなくなる
- 権限の証明は**なりすましの一部しか防がない**。自分の repo に他人のシステムのモデルを置いて投稿することは依然できる

なりすましは権限ではなく**責任の所在**で受ける、というのが決定 1 である。

### 保持を日数で切る

運用は楽になるが、期限切れの予告が要り、予告のために連絡先が要り、連絡先を持てば ADR-2262 が避けた線をもう一段越える。**保持方針の選択が、そのつもりのなかった個人データを連れてくる**。

### コンソールを `packages/app` に相乗りさせる

React と Vite の資産が既にあるが、別 origin から nest の API を叩くことになり、セッションを持つ最初の面で CORS と cross-origin cookie を設計することになる。決定 6 のとおり、nest 自身が返すほうが入口が狭い。

### 生成を後付けで残す（段階案）

投稿を基本とし、installation がある repo に限って server-side 生成も提供する案。移行は滑らかだが、**両方の重りを背負う** — モデレーション面と data processor 責任が同時に発生し、ADR-1996 の 6 件は 1 件も減らない。加えて「ゼロ設定が売り」と「投稿してもらう」が同居し、サービスが何であるかの説明が 2 つになる。

## 帰結

- `packages/nest` から生成側が消え、約 12,000 行が削除された。残るのは保存と配信である
- 推論費がゼロになり、[ADR-1994](1994-karasu-nest-free-tier-quota.md) の枠機構が不要になった（ADR-2578 が supersede 済み）
- **モデレーション面を持つ。** 第三者からの申し立てに人が判断する運用が発生する
- **ゼロ設定を失う。** [#1960](https://github.com/kompiro/karasu/issues/1960) の「実質ローカルツールに収束する」という批判を正面から受ける。受けられると判断した根拠は、ローカル reverse の手段が `.claude/skills/reverse-architecture/SKILL.md` と `karasu` CLI として既にあることである
- 個人データがゼロでなくなった。privacy policy と ToS が**運用者以外に開くための前提条件**になる（[#2591](https://github.com/kompiro/karasu/issues/2591)）

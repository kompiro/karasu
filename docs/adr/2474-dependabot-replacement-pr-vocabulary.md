# ADR-2474: Dependabot 反映手段の呼称を「差し替え PR」に統一し、過去 ADR も遡って揃える

- **日付**: 2026-08-14
- **ステータス**: 決定済み
- **関連**:
  - 起点 Issue: [#2474](https://github.com/kompiro/karasu/issues/2474)
  - 語が問題として表面化した ADR: [ADR-2472](2472-dependabot-triage-2026-08-13.md)
  - 改名対象の ADR: [ADR-2115](2115-dependabot-security-2026-07-22-second-batch.md) / [ADR-2152](2152-dependabot-triage-2026-07-27.md) / [ADR-2318](2318-dependabot-triage-2026-08-03.md) / [ADR-2333](2333-dependabot-triage-2026-08-04.md) / [ADR-2447](2447-dependabot-triage-2026-08-10.md) / [ADR-2472](2472-dependabot-triage-2026-08-13.md)
  - 運用ルール: `.claude/rules/dependabot.md`（正本）
  - ADR 執筆規約: `.claude/rules/adr.md`

## 背景

Dependabot トリアージには、bot PR をそのままマージせず **close して別の PR で
同じ bump を入れる**反映手段がある。bot が作れる diff の形では正しい変更に
ならないとき（peer が exact pin の相方を同一コミットで動かす必要がある、
upstream の既定変更に伴う棚卸しを bump と同梱する必要がある）に使う。

この手段を ADR-2115 以来「**人手 PR**」と呼んでいた。ADR-2472 のレビューで
読み手から「これは bot の PR を採用せず別で PR を作るということか」と確認が
入り、語が伝わっていないことが分かった。

問題は 2 つある。

1. **却下に読める。** 判定表で 却下 / 保留 の隣に並ぶうえ、説明が
   「bot PR は close」から始まるので、bump そのものが見送られたように読める。
   実際は逆で、bump は**採用**している。だからこそ `@dependabot ignore` を
   設定しない、という肝心の区別が伝わらない。
2. **書いた人を指していて中身を指していない。** 本質は「bot が作れる diff の
   形では正しい変更にならない」ことであって、人間がタイプしたことではない。
   人間が書いても bot ブランチに直接コミットする場合はこの手段ではないので、
   語と概念がずれている。

## 決定

**反映手段の呼称を「差し替え PR」に統一し、`.claude/rules/dependabot.md` を
正本とする。既存 ADR も、タイトルを含めて遡って改名する。**

あわせて次を確定する。

- **判定は 採用 / 保留 / 却下 の 3 値のまま変えない。** 差し替え PR は
  「採用」の一形態であり、判定軸ではなく反映手段の軸に属する。
- **`人手` は行為にだけ使う。**「bot ブランチに人手でコミットを足す」
  「override を人手で合わせる」「lockfile を人手で再解決する」は手作業を
  指すので正しい用法として残す。成果物としての PR だけを改名する。
- 改名した ADR: ADR-2115 / ADR-2152 / ADR-2318 / ADR-2333 / ADR-2447 /
  ADR-2472。うち **ADR-2447 は frontmatter `title` と body H1 も改名**し、
  `docs/adr/effective.md` と `docs/adr/graph*.md` を再生成した。
  ファイル名は語を含まないので変更していない。

## 理由

### 「差し替え」は行為そのものを指し、却下とも読めない

bot PR を差し替える、という操作の記述になっている。誰が書いたかを含まず、
bump を取り込む前提が語に残る。ADR-2472 では執筆中に自然と
「#2480（差し替え PR）」と書いていた箇所があり、語としての座りの良さは
実地で確認できていた。

OSS 化時の英訳（`.claude/rules/adr.md` 言語ポリシー）でも replacement PR に
素直に落ちる。

### 判定語彙を触らないのは、軸が 2 つあるため

判定（採用 / 保留 / 却下）と反映手段（そのままマージ / 差し替え PR）は
直交する。判定列に「差し替え」を第 4 の値として足すと、差し替えたものが
採用なのか却下なのかが表から読めなくなり、今回直そうとしている誤読を
別の形で再生産する。表記は `採用（bot PR は close）` のまま残し、
散文と正本で差し替え PR を定義する形にした。

### 過去 ADR を遡って改名するのは、これが決定の変更ではないため

`.claude/rules/adr.md` は「既存 ADR を覆すときは旧 ADR を書き換えず、
新 ADR で `supersedes` する。旧 ADR は歴史的記録として残す」と定めている。
本 ADR はこれに抵触しない。

**あの規約が守っているのは「何をなぜ決めたか」であって、それを書き表す語では
ない。** 今回変わったのは呼称だけで、ADR-2115 以降の各バッチで下した判断は
1 件も変わっていない。決定の中身を保ったまま名前だけを揃える操作は、
`supersedes` が対象にしている「決定の上書き」とは別の行為になる。

据え置く案も検討したが（後述）、**ADR は読まれるために残している**以上、
古い記録だけが誤読を誘う語のままなのは記録としての価値を下げる。とくに
ADR-2447 は語がタイトルにあり、`effective.md`（有効な決定一覧）にそのまま
出るので、一覧を眺めるだけの読み手が最初に当たる場所だった。

### `人手` を全置換しないのは、正しい用法が混ざっているため

`docs/` 全体で `人手` は 30 箇所以上あるが、大半は「人手 gold」「人手レビュー」
「人手確認」「人手ラチェット」のように **manual の意味**で使われていて曖昧さが
ない。Dependabot ADR の中にすら両方が混在する（ADR-2318 は同じファイルで
「差し替え PR」と「bot ブランチに人手でコミットを足す」を使い分ける）。

したがって置換の判定条件は **「`人手` が成果物としての PR を修飾しているか」**
の 1 点に畳んだ。行為を指すものは残す。

## 却下した案

### 案: 「再提出 PR」

`.claude/rules/dependabot.md` の既存の言い回し（「bot PR を close →
人手の PR で再提出」）に最も近い。却下したのは「再提出」が**同じものを
出し直す**含みを持つため。実際に違うのは diff の中身であり、そこが伝わらないと
「なぜ bot PR ではだめなのか」が語から落ちる。

### 案: 「補完 PR」

「bot の diff が不完全なので足りない変更を補う」という中身は最も正確に表す。
却下したのは bot PR を close する点が語から読み取れないため。補完という語からは
bot PR に足すようにも読め、それは `@dependabot recreate` で失われる手段
（ADR-2115 / ADR-2318 が却下済み）と紛らわしい。

### 案: `.claude/rules/dependabot.md` だけ直し、過去 ADR は据え置く

`.claude/rules/adr.md` の「旧 ADR を書き換えず」に最も素直で、変更量も最小。
却下したのは、それだと**正本を読んだ人にしか効かない**ため。トリアージの
入口は ADR を読むところから始まることが多く、ADR-2447 のタイトルは
`effective.md` にも出る。1 行の対応注記で読ませる案も考えたが、
注記に気づくかどうかに賭ける形になる。

### 案: 散文だけ揃え、ADR-2447 のタイトルは据え置く

`effective.md` / `graph*.md` の再生成が不要になる。却下したのは、同じ ADR が
タイトルで「人手 PR」、本文で「差し替え PR」と名乗る状態になり、
**改名前より読み手を迷わせる**ため。揃えるなら全部、揃えないなら全部据え置きの
どちらかにする。

## 影響

- 今後のトリアージは `.claude/rules/dependabot.md`「判定語彙」節を読んで
  差し替え PR を使う。トリアージ開始時に本ファイルを明示的に読む導線は
  既に同ファイル冒頭にある。
- ADR-2447 のタイトル変更に伴い `docs/adr/effective.md` と
  `docs/adr/graph*.md` が再生成される。ファイル名・ADR 番号・
  リンクアンカーは変わらないので、外部からの参照は壊れない。

# ADR-2351: docs/process.md は「今どうするか」だけを持つ — 経緯は ADR / Issue に置き、参照もしない

- **日付**: 2026-08-04
- **ステータス**: 決定済み
- **関連**:
  - 起点 PR: [#2351](https://github.com/kompiro/karasu/pull/2351)（対応する Issue は無い。ADR-2348 の作業中に浮上した）
  - [ADR-2348](2348-at-records-point-at-issues.md)（AT は Design Doc ではなく Issue を指す。同じ「記録が指すべきアドレス」の問題を AT 側で扱ったもの）
  - [ADR-2331](2331-adr-automerge-scope.md)、[ADR-788](788-adr-knowledge-graph.md)（決定の置き場所としての ADR）
  - 規約の所在: `docs/process.md` 冒頭の注記

## 背景

`CLAUDE.md` は「作業開始時は必ず `docs/process.md` を読んでから着手すること」と指定している。したがって **process.md は全文が毎セッションのコンテキストに載る**。読まれる回数が最も多いドキュメントであり、長さがそのまま毎回のコストになる。

そこに経緯が溜まっていた。どの Issue で問題が発覚したか、どのリリースで何が壊れたか、却下した案がなぜ却下されたか。個々は 2〜5 行だが、積み上がって 35 KB になっていた。

経緯そのものが不要なのではない。**置き場所が違う**。ADR と Issue は必要になったときだけ読まれるので、そこに置けばコストは参照時にしか発生しない。process.md に置くと、リリース作業をしない人も Dependabot に触らない人も、毎回全部を読むことになる。

## 決定

**`docs/process.md` は「今どうするか」だけを書く。「なぜそうなったか」「いつ壊れたか」「どの Issue が発端か」は ADR / Issue 側に置き、process.md からは参照しない。**

- **残すもの**: 従うために読む必要があるポインタ（[ADR-1820](1820-notation-promotion-gate.md) の promotion gate、`docs/design/TEMPLATE.md` などの雛形、`.claude/rules/`）と、履歴に見えて実は現在も効いている制約。
- **消すもの**: Issue / PR 番号による実例、「〜で発覚した」「経緯は ADR-X 参照」、却下案の説明、`理由:` で始まる正当化の段落。
- **見出しは変えない。** CLAUDE.md・`.claude/rules/` 4 本・`docs/roadmap.md` の anchor・AT レコード・`docs/design/TEMPLATE.md`・ADR の `grep:` assumption の計 10 箇所が節名で参照している。
- 規約自体を **process.md 冒頭の注記**として置き、編集者の目に入る位置に残す。

適用結果は 35,677 → 29,305 バイト（-18%）、459 → 420 行。Issue / PR 番号は AT ヘッダの記述例に含まれる 1 件を残して全廃した。

## 理由

- **読まれる回数がコストを決める。** ADR は必要になった人が 1 回読む。process.md は全員が毎回読む。同じ 1 行でも、置き場所によってコストが 2 桁変わる。
- **記録は残る。** 削ったのは process.md からの**参照**であって、経緯そのものではない。ADR と Issue は不変で、`git log` も残る。失われる情報は無い。
- **ADR-2348 と同じ問題の別の面である。** あちらは「記録が、削除されると分かっているアドレスを指す」、こちらは「参照されるコストが最も高い場所に、参照頻度が最も低い情報を置く」。どちらも情報の寿命 / 頻度と置き場所が噛み合っていない。
- **判定基準を 1 つに畳んだ。** 「これは経緯か、従うべき指示か」だけで判断する。項目ごとの例外表を作ると `.claude/rules/README.md` チェックリスト 5 が警告する「場面の数え上げ」になり、次の追記で漏れる。

## 却下した案

- **現状維持** — 変更ゼロだが、process.md は追記でしか成長しない（誰も削らない）。放置すると毎セッションのコンテキスト消費が単調増加する。
- **`docs/process.md` を分割し、リリース運用と Dependabot 運用を別ファイルに出す** — 残り 29 KB のうち 34% を占め、しかもリリース時と依存更新時にしか要らないので、削減効果は本 ADR より大きい。ただし節名を参照している `.claude/rules/changesets.md` と `docs/roadmap.md` の anchor を張り替える必要があり、「何がどこにあるか」の地図も変わる。経緯の除去とは独立に判断すべきなので分けた（未決）。
- **CLAUDE.md の「必ず読む」を外し、必要なときだけ読ませる** — 最大の削減になるが、`docs/process.md` は着手前に読まれることを前提に書かれており、読まれない前提にすると規約が届かなくなる。ADR-2331 で確認したとおり、指示は「変えたい行動の直前に届く層」に置くほど効く。読ませるのをやめるなら、内容を `.claude/rules/` 側へ移す設計変更が要る。
- **機械チェックで経緯の混入を検出する** — Issue 番号の出現を lint する案。ただし「従うために必要な参照」も番号を含みうるので誤検出が避けられず、判定に人の目が要る。冒頭の注記で足りるかを運用してから決める。

## 未決（本 ADR の範囲外）

- **リリース運用 / Dependabot 運用の切り出し**（却下案の 2 番目）— 効果は大きい。やるなら参照の張り替えとセットで。
- **`.claude/rules/` 側との棲み分け** — 編集行為に直結する規約は rules に置くほうが効く（`.claude/rules/README.md`）。process.md に残っている規約のうち何を rules へ移すかは別途。

# TPL-2715: 位置情報は、それが指す文書の識別と対でしか運べない

## 観点

行・列・offset は、それ単体では**アドレスではない**。どの文書へのインデックスかが決まって
初めてアドレスになる。マルチファイルのモデルでは、判定が下される文書と、結果を読む人が
開いている文書は**別でありうる**。

したがって、位置を伴う判定結果を層をまたいで渡すときは、**位置と文書識別を同じオブジェクトで
運ぶ**。受け取った側が「たぶんエントリファイルだろう」と補完する形にしない。補完は
単一ファイルのテストでは常に正しく見えるので、破れはテストに映らない。

判定基準は 1 つ、**その位置を作った parse と、その位置を印字する消費者が、同じ文書を見ていると
保証できるか**。保証できないなら識別を同梱する。

## 想定される失敗モード

- **存在しない行を指す。** 実例（#2715）: `karasu render index.krs` が、7 行の `index.krs` に対して
  `index.krs:13:4` を印字した。実体は import 先 `legacy.krs` の 12 行目にある宣言だった
- **存在する行を指してしまい、気付かれない。** エントリファイルが十分長いと、印字された行には
  無関係な宣言が載っている。前者と違って「明らかにおかしい」とは見えないので、
  ユーザーはそこを直そうとして時間を溶かす
- **マージ後判定は構造的にこの形になる。** 「2 ファイルが同じ id を宣言している」ような判定は、
  負けた側の宣言が別ファイルにあることが**判定の中身そのもの**なので、
  エントリ補完は必ず外れる（TPL-2221 の裏面）
- **消費者ごとに補完ロジックが増える。** CLI は `+1` して印字し、app は `Line N` と出し、
  `lint-style` は `+1` しない、という食い違いが実際に共存していた。
  1 つ直しても他が残り、どれが正しいのか repo からは読めなくなる
- **新しい診断が黙って同じ穴に落ちる。** 識別を後付けで stamp する設計にすると、
  choke point を通らない経路で診断を足した人が何もしなくても壊れる。
  症状は「その診断だけファイルが違う」で、レビューでは見えない

## チェックリスト

複数ファイルをマージするモデルで、位置付きの判定を足す / 直すときに確認する:

- [ ] その位置を作った parse は、どのファイルを読んでいたか特定できるか。できないなら parse に
      ファイルパスを渡す側を直す（受け取った側で推測しない）
- [ ] `loc` を持つ結果が、resolver を通った時点で**全件**ファイル識別を持つことを
      テストで assert しているか（「代表的な 1 コードで確認した」では漏れる）
- [ ] ファイル識別が**無い**ときの意味を 1 文で書けるか。書けるなら spec に置き、消費者全員が
      同じ解釈をしているか確認する
- [ ] 印字された行番号が、そのファイルの実テキストと一致することを確かめるテストがあるか
      （行番号を期待値にハードコードするテストは、1 ずれを固定してしまう）
- [ ] 単一ファイルのモデルと 2 ファイルのモデルの両方でテストしているか

## 既知の対処パターン

**位置を作る場所でファイル識別を載せる。** `.krs` の `SourceRange` は
`packages/core/src/parser/parser.ts` の `range()` 1 箇所でしか作られないので、
そこに `file` を持たせると、以降どのレイヤで診断を作っても識別が付いてくる
（#2715 / ADR-2715）。後段で stamp する方式は choke point を通らない経路で漏れるため採らない。

**行番号の base を 1 箇所で宣言する。** core の位置は 1-based であり、
`packages/lsp/src/lsp-position.ts` がその宣言と変換を持つ。消費者が個別に `+1` / `-1` しない。

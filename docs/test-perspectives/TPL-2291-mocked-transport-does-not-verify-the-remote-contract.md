# TPL-2291: 通信相手をモックしたテストは、こちらのロジックしか検証しない — 相手が受理するかは別に確かめる

## 観点

自分で書いたモックは、**自分が想定した要求を必ず受理する**。したがってモックに対して緑になったことが言えるのは「送った後の処理が正しい」ことだけで、**「その要求を相手が受理する」ことは何も言えていない**。この 2 つは別々に検証する。

危ないのは、モックの網羅度を上げるほど検証した気になる点にある。ページを 3 枚用意して境界も分岐も網羅すれば、テストは丁寧になり、そして**リクエストが 400 で弾かれる事実には一歩も近づかない**。網羅されているのは常にこちら側の分岐だけである。

判定は「モックが通ったか」ではなく **「相手が受理することを何が保証しているか」** を一言で言えるかどうかで行う。言えないなら、それは未検証である。

## 想定される失敗モード

- パラメータを 1 つ足しただけで相手が 400 を返す。モックはその値を無視していたので緑のままだった
- 失敗時のレスポンスボディを握り潰す実装になっており、原因が「何かが 400」までしか分からない（`body=$(curl --fail-with-body ...)` は、ボディを stdout に出しつつ、その stdout をコマンド置換が飲み込み、`set -e` が即座に落とす）
- 「モックで検証済み」と報告した結果、レビューでも本番経路の確認が省略され、最初の実行が本番になる
- マージ前に本番経路を実行できない変更（`push` / `delete` トリガー、cron、リリース経路）で、モック緑をもって完了扱いにする

## チェックリスト

外部との通信を含むコードにテストを付けるときに確認する:

- [ ] 「相手が受理すること」を保証しているものを 1 つ名指しできるか（実呼び出し / 記録済みレスポンス / 型付きスキーマ / 手動実行のいずれか）
- [ ] モックはリクエストの形（URL・クエリ・ヘッダ）を assert しているか。何を送っても同じ応答を返すモックは、送信内容を検証していない
- [ ] 相手が異常系を返したときのケースがあるか。そのとき**レスポンスボディがログに出る**か
- [ ] 報告するとき、「モックに対して検証済み」と「本番経路で検証済み」を区別して書いたか
- [ ] 本番経路がマージ後にしか動かないなら、それを AT の手動項目として残し、マージ後に実際に実行したか

## 既知の対処パターン

- **モックにリクエスト内容の assert を入れる** — 発行した URL を記録し、送ってはいけないパラメータが含まれていないことを検査する。`#2291` の修正では「`per_page` を送っていないこと」がテスト項目になった
- **失敗レスポンスをファイルに落としてから判定する** — `curl -o file -w '%{http_code}'` で本文と状態を分離すると、非 200 のときに本文をそのままログへ出せる。`$(...)` で本文を掴むと、失敗時にちょうど本文が失われる
- **マージ後スモークテストを完了条件に含める** — 本番経路がマージ後にしか動かない変更は、マージした時点ではなく、実際に 1 度通した時点で完了とする（[TPL-2254](TPL-2254-durable-record-points-at-durable-address.md) と同じく、記録ではなく実物で確かめる）

## 由来

`spike-preview.yml` の cleanup が Cloudflare の deployments API を `per_page=100&page=N` で辿るよう書かれ、偽の `curl` を PATH に置いたテストで「3 ページ 71 件を取りこぼしなく削除」まで確認して報告された（[#2278](https://github.com/kompiro/karasu/pull/2278)）。偽 `curl` はクエリ文字列を見ずにフィクスチャを返していたため、実際の API が `per_page=100` に 400 を返す事実は検証されておらず、マージ後に実ブランチを削除して初めて露見した（[#2291](https://github.com/kompiro/karasu/issues/2291)）。しかも `--fail-with-body` のボディがコマンド置換に飲まれ、ログには `curl: (22)` しか残らなかった。「モックの作り込み」と「相手の受理」は独立で、前者をいくら足しても後者には届かない。

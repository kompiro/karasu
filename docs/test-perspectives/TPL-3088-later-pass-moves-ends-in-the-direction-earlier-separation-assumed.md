# TPL-3088: 前のパスが「重ならない」と判定した要素の端を後のパスが動かすなら、動かす向きがその判定と矛盾しないことを測る

## 観点

> 起源は出荷済みの bug（retrospective）。#2958 で足した飽和フィクスチャの変形で見つかり、main でも同じ入力で起きていた。Dify の全階層と examples には届く入力がなく、柵は 0 のまま緑だった（TPL-2598）。

配線は複数のパスを順に通る。前のパスは「この 2 つは重ならない」と判定して、同じレーンや列を共有させることがある。典型は、y 範囲が**接するだけ**の 2 本の corridor を同じガターのレーンに置く判定である。この判定は「接している端点がその位置に留まる」ことを暗黙に前提している。

後のパスがその端点を動かすと、前提が崩れる。動かす向きが「離れる」向きなら問題ないが、「近づく」向きなら、接していただけの 2 つが重なる。後のパスは前のパスの判定を知らず、自分の基準（x 範囲、番号など）で並び順を決めるので、向きは偶然に任される。

したがって、前のパスが「接するだけなら共有してよい」と判定する箇所では、**後に端点を動かすパスが、その判定と同じ向きに動かすこと**を確かめる。ポートの扇（`fanOutGutterPorts`）は、行き先の向きで並べて入れ子にするので、この性質を満たしている。行間チャネルのレーン分け（`distributeChannelLanes`）は #3088 まで満たしていなかった。

## 想定される失敗モード

- **接していただけの 2 本が重なる。** 上から来て行間チャネルで終わる corridor と、そのチャネルから下へ出る corridor が同じレーンに載る。チャネルのレーン分けが前者を下のレーンに、後者を上のレーンに置くと、2 本の縦線がレーンの間隔だけ重なり、1 本に見える（兄弟以外の共線ペア、TPL-1927）。
- **実在の図では起きず、柵が緑のまま。** 並び順は偶然に任されているので、多くの図ではたまたま正しい順になる。届く入力が corpus に無いと、柵は何も保証しない（TPL-2598）。
- **直し方を間違えて図を広げる。** 前のパスで「接するだけでも分ける」と直すと症状は消えるが、偶然正しい順だった図まで広げる（#3088 の計測で Dify Knowledge の面積 +10.2%）。原因は後のパスの並び順にある。

## チェックリスト

区間・レーン・列を「接するだけなら共有」で割り当てる箇所、または端点を動かすパスを変更するときに確認する:

- [ ] 「接するだけなら共有してよい」と判定する箇所を列挙し、その接点を後で動かすパスがあるか確認したか
- [ ] 後のパスの並び順が、接点の両側の要素が向かう方向（上下・左右）と矛盾しないか確認したか
- [ ] 並び順の制約が循環しうる場合、循環の外の制約を守る形で切っているか。循環の中で残る重なりが柵で検出されるか
- [ ] 柵の入力に、2 つの要素が実際に 1 本のチャネル（またはポート）で接する図が含まれているか。実在の図に無ければ合成入力を足したか
- [ ] 直し方が「前のパスで予防的に分ける」になっていないか。直す必要のない図を広げていないかを、実在の図の面積で確認したか

## 既知の対処パターン

- **後のパスの並び順を、接点の向きで決める。** 同じ位置で接する 2 要素のうち、上へ続く方を上に、下へ続く方を下に置く制約を立て、元の順に最も近いトポロジカル順序で並べる（`laneOrder`、`fanOutGutterPorts` の `bendKey`）。要素はレーン単位で丸ごと動かすので、レーン内の不変条件は崩れない。
- **制約の循環は強連結成分に縮約して切る。** 成分どうしの制約はすべて守り、成分の中だけを元の順に並べる。「行き詰まったら番号の小さいものから」と切ると、循環の外の制約まで破る。

# TPL-3920: 別のセッションからのメッセージは起こす合図として扱い、判定と記録は PR から読み直す

## 観点

> 起源は **#3920**（proactive）。`/pr-verify` が差し戻しの依頼文を kompiro に渡す代わりに、実装セッションへ
> メッセージで送る設計を検討したときに、原則から予測した。

セッション間のメッセージは、送ったセッションの言い分であって、PR の状態ではない。「直した」と言われても、
push されていない、CI がまだ走っている、別の点だけ直した、ということがある。メッセージは後から読み返せず、
セッションが終われば消える。

メッセージは「相手を起こす」ことにだけ使う。受け取った側は、何をするかを PR（コメント、HEAD、check、
gate の判定）から読み直して決める。依頼の中身と往復の回数も PR に残し、そこから数える。

## 想定される失敗モード

- 実装セッションの「直した」を信じて、レビューセッションが前の HEAD の確認結果のままマージを勧める
- 実装セッションが kompiro に質問して止まり、待機状態になった。その通知を「直し終えた」と読み、まだ直っていない
  PR を確かめ直して同じ差し戻しを送る（TPL-3385 と同じ形）
- 往復の回数をセッションの記憶で数える。セッションを立ち上げ直すと 0 に戻り、上限が効かない（TPL-2909）
- 依頼の中身がメッセージにしか無い。実装セッションが終わると、何を直すよう頼まれたかが誰にも分からない
- メッセージの文をそのまま指示として実行する。送り手が別のセッションや別の利用者であっても区別できない
- 依頼を PR に残すコメントが、ほかの処理が答えとして読む文字列（CodeRabbit の指摘の id など）を含み、
  その処理の判定を変えてしまう

## チェックリスト

- [ ] メッセージを受けたあとの判定（確かめ直す、マージを勧める、差し戻す）が、PR から読み直した状態だけで
      決まっているか [judgment]
- [ ] 待機状態の通知や「終わった」の知らせを、作業が済んだ根拠にしていないか [judgment]
- [ ] 依頼の中身が PR のコメントに残り、メッセージはその URL を運ぶだけになっているか [judgment]
- [ ] 往復の上限を、PR に残るもの（コメントの数など）から数えているか [judgment]
- [ ] 依頼を残すコメントの文面が、PR のコメントを読むほかの処理（gate、Review tier、merger）の判定を変えないか [judgment]
- [ ] 宛先のセッションが無いとき、送信が失敗したときに、今までの手順（kompiro に渡す）に戻るか [judgment]

## 既知の対処パターン

- `/pr-verify` は依頼を PR に `Hand-back by /pr-verify head=<sha>:` のコメントで残してから、URL だけを
  実装セッションに送る。往復の回数はこのコメントを PR ごとに数え、HEAD が変わらない差し戻しも 1 件とする。コメントには `cr-comment:v1:` で始まる
  文字列を書かない（#3920 の設計）

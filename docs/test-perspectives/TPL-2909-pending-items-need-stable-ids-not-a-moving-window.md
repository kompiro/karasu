# TPL-2909: 処理待ちの項目は、動く窓で絞り込まず項目自身の安定 id で持つ

## 観点

未処理の項目を数えるとき、「いま head か」「最後の行動より後か」といった**動く条件**で絞り込むと、
条件が動いた瞬間にその項目は未処理のまま視界から消える。消えたこと自体はどこにも残らないので、
「未処理が 0」という完了条件は満たされてしまう。

処理待ちは項目自身の安定した id で持ち、処理済みは**明示的な行為**（id を書く、thread を閉じる）でしか
確定しないようにする。集合が減らないことを保証するのではない（新しい項目は増える）。保証するのは
「push や時刻の更新では未処理が減らない」ことで、減らすのは明示的な行為だけになる。だから完了条件を
事後に検証できる。

処理済みの記録には、それがいつ行われたかも要る。同じ項目が回答の後にもう一度出されたなら、それは
未処理に戻る。時刻を持たない引き算にすると「一度答えた項目は永久に答え済み」になり、
「対応したのにまた出てきた」という最も重要な兆候を消してしまう。

混在に注意する。同じ待ち行列の一部が恒久的な carrier を持ち（review thread は push を越えて開いたまま残る）、
残りが持たない（review 本文の指摘には thread がない）ことがある。持つ側だけを見て「0 件」と報告すると、
持たない側は必ず取りこぼす。

## 想定される失敗モード

- push で最新リビジョンが動いた途端、前ラウンドの指摘がカウントから落ち、approve されてそのまま出荷される
  （#2909。#2887 で Major 指摘 1 件が失われ、2 日後に別の Issue として再発見された）
- 完了時の数字は正しく見えるのに、ラウンドを跨ぐと落ちる。1 ラウンド内の fixture では再現しない
- 「未処理 0 件」という報告は正直なまま、実際には未読が残る
- id を取れない項目が現れたとき、静かに数から漏れて完了条件に乗る

## チェックリスト

- [ ] 未処理集合の要素を、リビジョンや時刻ではなく項目自身の id で識別しているか
- [ ] 処理済みは明示的な行為で確定し、その痕跡が push や時刻の更新で消えないか
- [ ] 回答の後に同じ項目が再提出されたら未処理に戻るか（回答と再提出の時刻を比べているか）
- [ ] 同じ待ち行列に carrier を持たない種類が混ざっていないか。混ざっているならその種類も id で数えているか
- [ ] id を取れない項目が来たとき、静かに 0 にせず止めて人に渡すか
- [ ] 窓で絞り込む実装に戻したら落ちるテストがあるか（ラウンドを跨ぐ fixture が必要）

## 既知の対処パターン

- CodeRabbit の body 指摘は各項目末尾の `<!-- cr-comment:v1:<hex> -->` で識別し、PR コメントにその id を
  書くことだけを「答えた」の定義にする（`scripts/coderabbit/review-state.ts` の `bodyFindingIds`）。
  review thread の `resolveReviewThread` と同じ役割を、carrier を持たない側に与えている
- id を持たない項目は `unmarkedBodyFindings` として別に数え、閉じる手段がないので通知して止まる。
  静かに 0 にする代わりに大きく失敗させる

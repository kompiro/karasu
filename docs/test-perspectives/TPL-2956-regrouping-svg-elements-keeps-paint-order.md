# TPL-2956: SVG の要素をまとめ直すなら、重なる要素の描画順を保つ（変わるなら、変わる組を数えて記録する）

## 観点

> 起源は **#2956 の設計中の spike**（proactive）。出荷済みの bug ではない。交差ホップを
> 「同じ色なら 1 本の `<path>` に」まとめる案を測ったところ、dify モデルで色違いのホップが
> 重なる 9,798 組のうち **4,757 組で上下が入れ替わる**と分かった。ホップ同士は意味が同じ
> なので読み違いにはならないが、まとめ方という意味と無関係な理由で見た目が変わる形は、
> 意味の違う記号どうしで起これば [TPL-2631](TPL-2631-decoration-must-not-hide-a-crossing-mark.md)
> の失敗（後に描いたほうが勝つ）にそのままつながる。

SVG は**後に描いた要素が上に来る**。要素をまとめ直すと、出力サイズや要素数は減るが、
描画順も一緒に変わりうる。変わったかどうかは、重なっている箇所でしか見えない。

まとめ直す変更では、**描画順が保たれることを構造で保証する**か、保てないなら
**入れ替わる組を数えて記録する**。「同じ色だから入れ替わっても見た目は同じ」は、
色が同じ組にしか言えない。

描画順を保つまとめ方は単純で、**元の順番のまま、連続している区間だけをまとめる**。
キーでグループ化すると（`Map` に集めて最後に出す）、離れた位置の要素が前に引き寄せられ、
その間に描かれていた別キーの要素との上下が入れ替わる。

## 想定される失敗モード

- **重なりの上下が黙って入れ替わる。** 小さいモデルでは重なりが無いので再現しない
  （#2956 では examples 85 ファイルで色違いの重なり 0 組、dify で 4,757 組）。
  スナップショットのバイト列は全部変わるので、どの差分が上下の入れ替わりかを
  レビューで見分けられない。
- **意味の違う記号の上下が入れ替わる。** 同じレイヤにマークとチップのような意味の違う
  記号が同居していると、グループ化の副作用で一方が他方を覆う側に回る（TPL-2631）。
- **レイヤの境界をまたいでまとめる。** 別レイヤに分けてある要素（edge → crossing-marks の
  ように「上に描く」ために分けたもの）を同じキーでまとめると、レイヤ間の順序が崩れる。

## チェックリスト

要素をまとめ直す変更で確認する:

- [ ] まとめ方が「元の順番のまま、連続区間だけ」か、「キーでグループ化」かを明示している
- [ ] キーでグループ化するなら、重なる要素の組のうち上下が入れ替わる組を大きなモデルで数え、PR / 設計に記録している
- [ ] 展開すると（サブパスを順に取り出すと）、まとめる前の要素の列と順番どおり一致するテストがある
- [ ] キーが A, B, A と並ぶ入力で、A が 1 つにまとめられない（描画順を保つ）ことを固定するテストがある
- [ ] まとめる範囲がレイヤ（`<g>`）の内側に閉じている

## 既知の対処パターン

- **連続区間でまとめる**（#2956）: ホップの `d` を直前と同じ stroke なら同じ `<path>` に足し、
  違えば新しい `<path>` を始める。dify でホップ 38,572 → 894 要素（−97.7%）、出力 −26%。
  キーでまとめる案（55 要素）との差は出力で 0.7% で、上下の入れ替わりは 0 組。

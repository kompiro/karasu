# TPL-3036: 需要を測って開けた空間に別の種類の利用者が入れるなら、開いた配置を測ってから採る

## 観点

1 回目の結果を測り、足りない分の空間を開けて 2 回目を走らせる設計では、「どれだけ開けるか」と
「どこに開けるか」（[TPL-2611](TPL-2611-feedback-key-survives-the-next-pass.md)）のほかに、
**開けた空間を誰が使うか** を確かめる必要がある。

需要を測った対象（たとえば置けなかったラベル）とは別の処理（配線）が、開けた空間を自分の資源として
配分できるなら、2 回目ではその処理が空間を使う。測った需要は満たされず、別の場所の需要が増える。
予約は「適用されたのに効かない」か、もっと悪く「適用したら悪化した」になる。

判定は 1 つ。**開けた空間によって、需要とは別の種類の利用者がその空間へ入れるようになるかどうか。**
ラベルのために開けた空間へ別のラベルが動いてくるのは当たらない（需要の持ち主と同じ種類で、ラベルが置ける
ことには変わりない）。当たるのは、空間が増えたことで別の種類の利用者の候補が増え、そこへ割り当てられる
ようになる場合である（ラベルのために開けた隙間が、経路の抜けられる回廊になる、など）。当たるなら、その
空間は予約として働くとは限らない。開ける場所を、その候補を増やさない資源に移すか、別の種類の利用者がその
空間を使えないようにするか、開いた配置を候補として測り、需要が実際に満たされたときだけ採る。

karasu の例（#3036）: 行の中の 2 枚のカードの間隔を、置けなかったラベルの幅まで広げた。この隙間は
ADR-2611 の到達性で内部の回廊になる。広げた 2 回目では、外側のガターを回っていたエッジがその隙間に
入ってきて、WordPress の `WordPressApp` で置けるラベルは 110 → 76 本に減った。行間のチャネルの高さは
縦に抜けられる回廊を増やさない。チャネルに置けなかったラベルの高さの分だけチャネルを開く案では、同じ view で
110 → 138 本に増えた（2 つの案は測った需要も試作も別で、数字は案ごとの `main` との比較である）。
#3036 の決定は、両方を候補として配置し、置けないラベルが基準より減る候補だけを採る形にした。行内の隙間は、
それが効く図（密な fixture、17 → 30 本）でだけ開き、`WordPressApp` ではチャネルだけが開く。

## 想定される失敗モード

- **予約を足したら指標が悪化する。** 開けた空間に別の処理が入り込み、測った需要の持ち主は追い出される。
  密な合成 fixture では効いて見えても、実モデルで減る（#3036 の案2: 合成 fixture 17 → 23、実モデル
  206 → 204・156 → 120）
- **合成 fixture だけで判断する。** 合成 fixture は測りたい需要だけを持つように作るので、別の処理が
  空間を奪う余地が無い。予約の副作用は、他の需要が同居する実モデルでしか出ない
  （[TPL-2598](TPL-2598-fence-corpus-must-reach-the-limit.md) の「柵の corpus が限界に届かない」と同型）
- **悪化を、2 回目の結果から測り直して開け直すことで直そうとする。** 前の回の結果から次の予約を決める繰り返しは、
  需要と配分の綱引きになり、[TPL-2593](TPL-2593-layout-feedback-is-floor-first-and-monotone.md) の停止性を失う。
  1 回目の結果だけから決めた有限個の候補を並べて配置し、比べて 1 つを選ぶのは繰り返しではないので、これに当たらない

## チェックリスト

測った需要の分だけ空間を開けて配置をやり直す経路を足すとき:

- [ ] 開ける空間に、別の種類の利用者（配線・回廊の選択・別種の予約）が入れるようになるか確かめたか。なるなら、
      別の場所に開けるか、その処理から隠すか、開いた配置を候補として測って厳密に改善したときだけ採る設計にしたか
- [ ] 予約の前後で、需要を測った指標が**どの view でも減らない**ことを、需要の持ち主以外も同居する実モデル
      （または同等の fixture）で確かめ、view ごとの増減を PR に記録したか
- [ ] 需要が満たされたかを、2 回目の結果で測り直して確かめたか（予約が適用されたことではなく、需要の
      持ち主が空間を得たことを見る）

## 既知の対処パターン

- **候補を増やさない資源に開ける**: 行間のチャネルの高さは、縦に抜けられる回廊を増やさない。#3036 の測定では、
  チャネルだけを開く案はどの view でもラベルを減らさなかった
- **開いた配置を候補として測り、厳密に改善したときだけ採る**: #3036 は、チャネルだけを開く候補と、行内の隙間も
  開く候補を両方配置し、renderer のラベル配置パスで置けないラベルを数えて、基準より厳密に少ないものだけを採る。
  候補を 1 つにまとめると、効かない部分に引きずられて効く部分まで捨てられる（`WordPressApp` で 138 → 110）ので、
  別の種類の利用者を呼び込みうる開き方は、呼び込まない開き方と別の候補にする
- **view ごとの増減で判定する**: 合計では増えていても、1 つの view で減っていれば単調性を失っている。
  view ごとに「増えた / 減った / 変わらない」を数え、減った view が 0 であることを条件にする

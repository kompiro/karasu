# TPL-3341: 前のリビジョンへの承認を後のリビジョンに持ち越すときは、後で足されたものにレビューの要る変更が無いことを機械で示す

## 観点

レビューの承認は、それを出したリビジョンの中身に対するものである。後のリビジョンへ持ち越してよいのは、
後で足されたものが**読まなくても正しいと分かる変更**だけのときに限る。例えば、base ブランチの変更を
そのまま取り込んだ部分（base 側でレビュー済み）や、生成器で作り直すと同じ中身になる生成物である。

「取り込みだけのはず」「生成物だけのはず」を、コミットの種類（マージかどうか）やメッセージで判断すると、
マージの conflict を手で解消した部分が素通りする。conflict の解消は、取り込みのコミットの中に書かれた
**新しい変更**で、振る舞いを変えうる。持ち越しの判定は、自動マージの結果と実際のコミットの差分を取り、
その差分が「作り直すと同じ中身になる」パスだけにあることを示して初めて成り立つ。

## 想定される失敗モード

- マージコミットであることだけを見て承認を持ち越し、conflict の解消で入ったコードの変更が、レビューされないまま
  「レビュー済み」として人間に渡る
- 生成物のパスを判定と再生成で別々に列挙していて、片方だけ増えたときに、生成物でないファイルが例外扱いされる
- 取り消された承認を数え直す条件が広すぎて、修正のコミットの後でも古い承認が有効と判定される
- 判定が通る fixture しか無く、conflict を手で解消したケースで通ってしまうことが検出されない

## チェックリスト

- [ ] 持ち越しの根拠が「コミットの種類」ではなく「自動マージの結果との差分」になっているか
- [ ] その差分が許されるパス（生成物）だけにあることを確かめ、かつ作り直すと差分が出ないことも確かめているか
- [ ] 許されるパスの一覧が、判定と再生成の両方から参照される 1 か所にあるか
- [ ] 承認から HEAD までに、マージでないコミットが 1 つでもあれば持ち越さないか
- [ ] conflict を手で解消して生成物以外を変えたマージで、持ち越しが拒否されるテストがあるか

## 既知の対処パターン

- `git merge-tree --write-tree <1 番目の親> <2 番目の親>` で自動マージの結果の tree を作り、実際のマージコミットの
  tree との差分を取る（git 2.38 以降）。conflict したファイルの一覧も同じ出力から得られる
- 差分を許すパスは生成器と一緒に定義し、判定は「そのパス集合の外に差分が無い」と「再生成で差分が出ない」の両方で行う

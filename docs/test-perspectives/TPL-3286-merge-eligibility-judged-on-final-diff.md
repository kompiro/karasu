# TPL-3286: 人間を通らないマージを許す判定は、最終の差分で行い、どの規則にも当たらない入力を厳しい側に倒す

## 観点

差分から「この PR は人間が読まなくてよい」「CodeRabbit の再レビューを省いてよい」と決める判定は、
誤ると誰も読まないコードが main に入る。誤りは 2 つの形で起きる。

- **判定した差分と、マージされる差分が違う。** PR の作成時や初回レビューの時点で判定し、その後の
  修正コミット・main の取り込み・追加の変更で差分が判定の外に出ても、ラベルや auto-merge が
  そのまま残る
- **規則に当たらない入力が軽い側に倒れる。** 新しいディレクトリ、想定していない拡張子、
  `package.json` のように 1 ファイルの中に軽い変更と重い変更が同居するものが、どの規則にも
  当たらなかったときに「軽い」と判定される

判定はマージされる直前の差分（head コミットと base の差分）に対して行い、どの規則にも当たらない
入力は、自動マージを許さない側に倒す。

## 想定される失敗モード

- 初回レビューの指摘に対応するコミットで、docs だけだった PR に `packages/*` の変更が混ざるが、
  付いたラベルのまま auto-merge される
- 判定を Claude が PR 作成前にだけ行い、CI では検証しないため、ラベルの付け間違いが残る
- 新しく作ったディレクトリ（例: `docs/` の新しい区分）が allowlist の書き方次第で軽い段階に入る
- `package.json` の `scripts` の変更と `dependencies` の変更を同じ「package.json の変更」として扱い、
  依存の追加が軽い段階に入る（または逆に、scripts の変更がすべて重い段階に入る）
- 判定する検査にパスフィルタを付けたため、docs だけの PR、つまり最も軽い段階になる PR で検査そのものが
  走らない（[TPL-1725](TPL-1725-gated-test-suite-detection-gap.md)）
- ローカルレビューの記録がレビューしたコミットより後に修正コミットが入っても、記録があるという事実だけで
  検査が通る（記録の `head` と PR の HEAD を比べていない）
- 記録の `fixed in <sha>` が、記録の `head` に含まれないコミットを指している（直したと書いたが、マージされる差分に入っていない）
- 誰でも書ける場所（public repo の PR コメント）の記録を、作成者を確かめずに読む
- 段階のラベルを実際より低く付けると、マージの経路だけでなく自動レビューの依頼まで省かれる。ラベルが低いことを
  検査が落とさない
- 検査が PR 側の分類器を実行するため、分類器を軽い側に書き換えた PR が、その分類器で自分を軽く判定して通る
- 重い指摘の却下を許さない段階で、重大度の列が空・未知の値・表記ゆれ（`major` / `High` など）の指摘を軽い側として扱い、
  却下したまま通る
- 差分を作る側の書き方の規則が変わり、例外が前提にしていた差分の形が現れなくなる。判定は厳しい側に倒れたままなので
  誤ってマージされることはないが、例外が意図した PR に届かない。AT が Design Doc ではなく Issue を指すようになって
  （ADR-2348）張り替える行が無くなり、AT に ADR へのリンクを足す昇格 PR がすべて Medium になった（#3405）
- 例外を広げる判定を「差分から許す部分を削って、残りが元と同じか」で書くと、削る規則の隙から意味のある変更が
  入る。リンクを消すとラベルだけになる行を無視したため、任意の太字ラベルの行を足せた。リンクと区切りを行頭から
  消したため、チェックボックスや見出しを壊す挿入が通った。行の形を決め打ちにした後も、行を足す位置を見なかったため、
  frontmatter の上や表の中やコードフェンスの中に足せた。上の行だけを見て下の行を見なかったため、足した行が上の項目の
  続きの行や子リストを引き取れた（#3405 の実装 PR のレビュー）
- 作成者が書く宣言（PR のタイトルの型、本文の理由の行）で段階や検査が軽くなる規則で、宣言を偽ると軽い側に倒れる。
  言語の挙動に触れる変更を `refactor` と書いて Medium にする、修正を `feat` と書いてテストの要求を外す、など。
  宣言を裏付ける検査が無いか、裏付けの検査が走らない PR でも例外が効く（#3505）
- 宣言を書き換えても判定が走り直さない。タイトルを `refactor` から変えても、前の判定のラベルや check の結果が残る（#3505）

## チェックリスト

- [ ] 判定はマージ直前の差分に対して、push のたびに走るか（PR 作成時の 1 回だけになっていないか）
- [ ] 判定結果とラベルが食い違ったとき、マージを止める required check として失敗するか
- [ ] どの規則にも当たらないパスを入力したテストがあり、自動マージを許さない段階になると assert しているか
- [ ] 1 つのファイルの中で重さが変わるもの（`package.json` の依存と scripts など）を、ファイル名ではなく
      差分の中身で分けているか
- [ ] 判定する検査に、軽い段階の PR を飛ばすパスフィルタが付いていないか
- [ ] レビューの記録を条件にする検査は、記録がレビューしたコミットと PR の HEAD を比べ、その間に main の取り込み以外の
      コミットがあれば失敗するか。main の取り込みだけでも、取り込みの前後で PR の差分の追加行と削除行の集合が
      変わっていれば（コンフリクトの解消で PR の行を書き換えた）失敗するか。比較はファイルごとの追加行と削除行の
      順序付きの並びと、行に現れない変化（変更の種類・リネーム元・ファイルモード・バイナリと空ファイルの blob）で行い、
      別ファイルへの移動、同じ内容の行の増減、同じファイルの中での行の入れ替え、モードやバイナリだけの変更を
      「同じ」とみなさないか
- [ ] 判定に使う分類器は base 側のものか（PR が書き換えた分類器で、その PR 自身を判定していないか）
- [ ] 記録が「直した」と書くコミットが、記録の `head` の祖先であることを確かめているか
- [ ] 記録を読む場所は、作成者と maintainer しか書けない場所（PR 本文など）か
- [ ] ラベルが無いときは最も重い段階として扱ったうえで、その実効のラベルが差分から出した段階より低いときに失敗するか
- [ ] 記録を求める段階で、記録そのものが無い（節が無い・読めない）PR を失敗させるか
- [ ] 記録のすべての指摘に対応が書かれていなければ失敗するか
- [ ] 人間を通らない段階では、Critical / Major の却下・記録の省略・前段のレビューの省略を含む記録を通さないか
      （Minor / Trivial の却下は通す）
- [ ] 重大度が Critical / Major / Minor / Trivial のどれでもない指摘を、Major として判定するか
- [ ] 記録が前提にする base（merge-base）が、いまの PR の base と HEAD の merge-base と一致するかを見ているか
- [ ] 作成者の宣言（タイトルの型・本文の理由の行）で段階や検査が軽くなる規則には、その宣言を機械で裏付ける検査
      （`refactor` なら等価の検査）があり、裏付けが成り立たないときに PR を落とすか。裏付けの検査が走らない PR では
      例外を効かせていないか
- [ ] 宣言を書き換えたとき（PR の `edited`）に、段階の判定と裏付けの検査が走り直すか
- [ ] 例外を広げる判定は、許す差分の形と位置を決め打ちにしているか（削って比べる形にしていないか）。
      許す形のすぐ外側（別のラベル、行頭、字下げ、値の途中、frontmatter・表・コードフェンス・本文の中、上の項目の続きの行の前、
      規約の対象外のファイル）を
      入力したテストで、Low にならないと assert しているか
- [ ] 例外の規則が前提にする差分の形を、その差分を作る側の書き方の規則（`.claude/rules/acceptance.md` など）が
      求める形と突き合わせたか。実際の PR の差分を分類器に通し、意図した段階になることを確かめたか

## 既知の対処パターン

- **差分の性質で判定する**（ADR-2331）：ADR-only の auto-merge は、変更ファイルの場所ではなく
  差分が決定の記録とリンクの整合だけかどうかで判定する。#3286 でこの判定は分類器の規則になり、
  PR を作る前の 1 回の手順から、push のたびに走る required check に移った。#3405 で、張り替えに加えて
  新しい ADR へのリンクを足すだけの差分も同じ扱いになった（ADR-3405）
- **既定値を厳しい側に置く**：段階の分類で、どの規則にも当たらないパスを中間の段階（人間が見る段階）にし、
  ラベルの無い PR と重大度の無い指摘を重い側（High・Major）に倒す
- **判定する仕組みを base 側から動かす**：required check は base ブランチの分類器を実行し、仕組みそのものの
  パスは最も重い段階に置く

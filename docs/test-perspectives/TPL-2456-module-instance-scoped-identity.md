# TPL-2456: 参照同一性で判定される共有オブジェクトは、module のコピーが 2 つになった瞬間に壊れる

## 観点

`===` / `instanceof` / `switch` の `case` で判定される値は、**その module 実体に閉じた同一性**を
持つ。同じバージョンの同じライブラリでも、解決されるパスが 2 つあれば singleton は別物になり、
判定は静かに false 側へ倒れる。

危ないのは、**壊れ方が「全滅」ではなく「その経路だけ全滅」**になる点にある。ライブラリ自身が
作った値を使う経路は同じコピーの中で完結するので動き続ける。壊れるのは、こちらが作った値を
ライブラリに渡す経路だけである。結果として大半のテストが green のまま、機能の一部だけが
落ちる。この非対称性がバージョン差やプロトコル交渉のような**もっともらしい別の説明**を
呼び寄せる。

判定は「バージョンが揃っているか」ではなく **「解決されるファイルが 1 つか」** で行う。
バージョンが同一でも複数コピーは起こりうるし、バージョンが違っても単一コピーなら壊れない。

## 想定される失敗モード

- 自作の型を渡す API だけが失敗し、ライブラリ内蔵の型を使う API は全て成功する。
  「その機能固有のバグ」に見えて、原因は共有の依存解決にある
- エラーが送信前の同期例外として出るため、通信ログにも相手側にも痕跡が残らない。
  「応答が来ない」ではなく「要求が出ていない」なので、相手を調べても何も出ない
- 片側だけ依存を bump した PR が CI green になり、不整合が lockfile に固定される
- 「同じバージョンだから同じはず」と考えて調査対象から外す。pnpm では直接依存の宣言が
  複数あれば同一バージョンでも解決先が分かれうる
- 失敗が E2E / 統合テストでしか出ないため、再現に実機や CI が要り、
  原因から遠いエラーメッセージだけが手掛かりになる

## チェックリスト

パッケージ境界を跨ぐ値を扱うとき、以下を確認する:

- [ ] 渡す値の同一性が `===` / `instanceof` で判定されていないか、ライブラリ側の実装を読んで確かめた
- [ ] 判定される場合、両側が解決する module のパスが一致することをテストで固定した
  （バージョン一致ではなく `require.resolve` の結果の一致）
- [ ] そのテストが健全時に pass し、コピーが 2 つの状態で fail することを実測で確認した
- [ ] 片側だけ依存を上げる変更で、もう片側の解決先が動かないことを確認した

## 既知の対処パターン

**解決の一意性をユニットテストで固定する。** 実行時の統合テスト（E2E）を待たずに、
module 解決だけで同じ判定を再現できる。`packages/vscode/src/protocol-request-identity.test.ts`
は `vscode-languageclient` 経由で解決した `ParameterStructures` が
`@karasu-tools/lsp/protocol` の `RequestType` を受理するかを検証し、
失敗時に「コピーが 2 つある」ことと両方の解決先パスを名指しで出す。

**発生不能にする選択肢もある。** 共有するのを「オブジェクト」ではなく「文字列 + 型」に
落とせば、コピー境界を跨ぐ値がなくなる。ADR-2456 ではランタイム経路の変更コストに
見合わないとして見送り、検出側で対処した。判断は都度行う。

**Dependabot のグループ化は緩和であって保証ではない。** 同じ PR で提示されるだけで、
解決先が 1 つになる保証はない。

## 派生元 spec

なし（依存解決とバンドルの性質に由来する観点で、`docs/spec/` の規定ではない）。

# TPL-2374: 分単位になりうる外部呼び出しは、総所要時間ではなく無通信で打ち切る

## 観点

長い呼び出しを**非ストリーミング**で投げると、最初のバイトが返るのは処理が終わったときになる。その瞬間まで、経路上のどの層から見ても「まだ生成中」と「ハングした」が同じ姿をしている。判別できないものは打ち切るしかないので、こちらが設定していない中間層が先に切る。返ってくるのは自分のコードのどこにも書いていない状態コードで、**原因はこちら側の呼び出し方**にある。

自分で置くタイムアウトも同じ誤りを繰り返しやすい。「1 回の呼び出しは N 分まで」は総所要時間の上限で、正常に長い応答と沈黙を区別していない。ストリーミングにすると生存が**観測可能**になるので、上限を「無通信がどれだけ続いたか」に付け替えられる。これが本質で、ストリーミングは手段にすぎない。

コストを理由にリトライを絞っている経路では被害が増幅する。決定的な失敗（不正なリクエスト・拒否）と一過性の上流失敗（5xx・overloaded）を同じ扱いにしていると、分単位の仕事が上流の一瞬の不調で丸ごと失われる。

## 想定される失敗モード

- 大きな `max_tokens`（あるいは大きな結果セット）を非ストリーミングで要求し、中間層のゲートウェイタイムアウトで落ちる。エラーは自分のコードに由来しないので原因追跡が遠回りになる
- 自前のタイムアウトを総所要時間で測り、正常に長い応答を殺す。値を伸ばして回避すると、今度はハングを検出できなくなる
- 中間層（CDN・gateway）を足せば直ると考える。多くのゲートウェイのタイムアウトは**最初の応答が返るまで**で測るので、非ストリーミングのままでは層が増えただけになる
- 一過性の上流失敗と決定的失敗を区別せずリトライ方針を決め、片方に合わせたせいでもう片方が壊れる（全部リトライ＝課金が倍、全部リトライ無し＝一瞬の不調で全損）
- テストのモックが即座に解決するので、無通信という状態がテストから消えている。ストリーミング化しても「沈黙したら止まる」ことは検証されない

## チェックリスト

外部サービスへの呼び出しを足す・変えるときに確認する:

- [ ] 応答が分単位になりうるか。判定は願望ではなく**要求している上限**（`max_tokens`・ページサイズ・期間）で行う。なりうるならストリーミングを既定にする
- [ ] 自前のタイムアウトは**無通信の継続時間**（または最初のイベントまで）で測っているか。総所要時間で測っていないか
- [ ] 経路上の中間層のタイムアウトが**何を起点に何を測るか**を一次情報で確認したか（「最初の応答まで」か「完了まで」か）
- [ ] 一過性の上流失敗（5xx・overloaded・切断）と決定的失敗を、リトライ方針の上で区別しているか。区別しないなら、どちらの損を選んだのか書いたか
- [ ] 沈黙するストリームのテストがあるか。モックが即座に解決するテストだけなら、この観点は 1 つも検証されていない

## 既知の対処パターン

- ストリーミング受信 + idle timeout。チャンクが届くたびにタイマーを張り直せば、長さではなく沈黙で打ち切れる
- リトライは**呼び出し 1 回**の層に置く。パイプライン全体の再実行は課金も所要時間も倍にするので、上流の一過性失敗に対する応答としては大きすぎる
- 例外に載せるのは status と固定語彙の error type だけにする。中間層やプロバイダのメッセージは、こちらが送ったプロンプト（＝他人のコード由来）を引用しうる

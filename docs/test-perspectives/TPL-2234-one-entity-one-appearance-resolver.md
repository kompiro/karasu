# TPL-2234: 見た目の決定は 1 つの関数に閉じる

## 観点

1 つのエンティティが複数の面に描かれるとき、その見た目（色・線種・アイコン）を
**どこか 1 箇所で決めて全ての面がそれを読む**。各面が独立に同じ既定値から導いてはならない。

独立に導いても、既定値しか無いうちは全ての面が同じ答えに着地するので**問題は表面化しない**。
壊れるのは**上書き手段が入った瞬間**で、そのとき更新されるのは実装者が気づいた面だけである。
残りの面は既定値を描き続け、1 つのエンティティが 2 つの見た目に割れる。

karasu の boundary で実際にこうなった:

- #2179 が boundary ごとの識別色を入れたとき、色を引く箇所が 2 つできた。フレームは
  `boundaryHue()`、縮退タブ（`◇ <label>`）は `palette.boundaryHues` の直読み。
- 両者はパレットの同じ添字を引くので**常に一致し、テストも図も正常**だった。
- #2234 の PoC で `.krs.style` の上書きをフレーム側にだけ教えたところ、枠が紫でタブが緑になった。
  boundary の色は「重なった 2 枚の枠が入れ子でなく重なりに読めるための条件」なので、
  割れると機能そのものが成立しない。

**上書き手段を足す変更では、足す前に読み口を畳む。** 畳んでから足せば、新しい面を
追加した人も自然に同じ関数を通る。逆順にすると、上書きの実装者が「もう 1 箇所あること」を
自力で発見する必要があり、発見できなければ黙って割れる。

[TPL-2179](TPL-2179-derived-outline-measured-on-coverage-not-bbox.md) の「定義は 1 つ」を
ジオメトリから**見た目全般**へ広げたもの。[TPL-1032](TPL-1032-derived-state-staleness.md) が
派生 state の二重持ちを扱うのに対し、こちらは派生**描画**の二重導出を扱う。

## 想定される失敗モード

- 既定値から各面が独立に導いており、**既定値しか無いので一致している**。レビューでも
  テストでも差が出ないため、二重導出そのものが指摘されない。
- 上書き手段（style セレクタ・テーマ・設定）を足した PR が、目立つ面だけを対応させる。
  残りの面は既定値のまま描かれ、1 つのエンティティが 2 つの見た目になる。
- 二次的な面（バッジ・タブ・凡例・ツールチップ・縮退表示）が後から追加され、そのとき
  「既存のコードがパレットを直接引いているから」と同じやり方を踏襲して 3 つ目の導出が増える。
- 上書きが**一部のプロパティにだけ**効く。色は指定できるが線種は既定のまま、といった
  中途半端な適用は、どのプロパティがどの面に届くのか読み手が予測できない。

## チェックリスト

同じエンティティを複数の面が描く実装・変更で確認する:

- [ ] そのエンティティの見た目を返す関数が **1 つだけ**あり、全ての描画面がそれを呼んでいる。
      パレットや定数テーブルを直接引いている描画コードが他に無いことを grep で確認した
      （karasu では `palette.boundaryHues` の直読みが残っていないこと）。
- [ ] **上書き手段を足す変更では、読み口の 1 本化を先行させた**（挙動不変のコミットとして
      分け、そのうえで上書きを足す）。同じコミットで両方やらない。
- [ ] 上書きが効いていることを、**最も目立たない面**で assert するテストがある。主要な面
      （枠・カード本体）だけ見るテストは、二次的な面の取りこぼしを検出しない。
- [ ] 上書きが**部分指定**されたときの残りの導出を決めて書いた（karasu では
      `border-color` だけの指定で塗りとタイトルも追従する）。「指定されなかったものは
      既定値」で済ませると、1 エンティティ 2 色が仕様として固定される。

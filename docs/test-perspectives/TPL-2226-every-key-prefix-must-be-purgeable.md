# TPL-2226: 削除を約束したストアに新しい鍵空間を足したら、削除経路に足したことを機械で確かめる

## 観点

「消える」と約束したストアでは、**新しい鍵空間を足す変更が、既定で約束を破る**。削除経路は既存の prefix を名指しで列挙しているので、新しい prefix は黙って対象外になる。型検査も lint も通り、機能テストも全部通り、purge は成功を返し続ける。残るのは、誰も読まなくなった鍵に載った他人の識別子だけである。

これは [TPL-2284](TPL-2284-purge-scope-identity-is-canonical.md) の隣にあるが、失敗の場所が違う。TPL-2284 は「同じ鍵空間を 2 通りに綴ってしまう」話で、purge の**射程内**での取りこぼし。こちらは**射程そのものが更新されない**話である。前者は正規化で閉じるが、後者は正規化をいくら丁寧にやっても防げない。

この失敗が特に起きやすいのは、**追加される鍵空間が主機能ではないとき**である。メトリクス・カウンタ・監査ログは「派生データ」「集計値」「個人情報ではない」と分類されがちで、その分類が正しいこともある。しかし削除の約束が縛るのは**本文の中身ではなく鍵**であることが多い。`metrics/<installation>/<owner>/<repo>/...` は本文が整数しか持っていなくても、その組織がその private repo を持っていた事実を保持している。

書いた本人が気づけない構造になっている点も効いている。新しいストアを書く人は、そのストアの正しさ（鍵の設計・TTL・並行性）を考えており、**既存の削除経路は視界に入っていない**。レビュワーも差分を読むので、差分に「無い」ものは見えない。

## 想定される失敗モード

- メトリクス／利用統計の prefix を足し、purge に足し忘れる。アンインストール後も `metrics/<inst>/<owner>/<private-repo>` が TTL いっぱい残る
- 監査ログを「消してはいけない記録」と位置づけて purge から外す。位置づけ自体は妥当でも、鍵に主体の識別子が入っていることを検討していない
- レート制限カウンタ・冪等キー・ロックを足す。短命だと思っているが TTL が数十日ある
- 逆引きインデックスやポインタを足し、本体だけ消してポインタが残る（本 repo では `idx/` がこれに当たり、`NestStore` が両方を持つ設計で閉じている）
- purge の戻り値に新カテゴリの件数を足さず、「完全に消えた」と報告する。**消し残しは戻り値にも例外にも現れない**
- 新しいストアの単体テストが自前の `purgeInstallation` を直接呼んで通っており、ファサードや webhook を経由していないので、配線漏れを検出できない

## チェックリスト

削除を約束したストアに書き込む鍵空間を足すとき:

- [ ] 新しい prefix は**削除経路のファサード**（本 repo なら `NestStore.purgeInstallation` / `purgeRepo`）から到達するか
- [ ] その配線を**ファサード経由のテスト**で確かめたか。新ストアのメソッドを直接呼ぶテストは、配線漏れを 1 件も検出しない
- [ ] 「全 prefix に書く → purge → ストアが空」を検証する**網羅テスト**があるか。個別 prefix のテストは、次に足される prefix を守らない
- [ ] purge の戻り値に**新カテゴリの件数**を足したか。0 を返し続ける項目は「消していない」と区別できない
- [ ] 鍵に主体の識別子（組織名・repo 名・ユーザー ID）が入っていないか。**本文が無害でも鍵は無害でない**
- [ ] 「これは派生データだから対象外」と判断したなら、その判断を**削除の約束を書いた文書（ADR・プライバシーポリシー）に照らして**書き残したか。暗黙の除外は、後から読むと単なる漏れと区別がつかない

## 既知の対処パターン

- **ファサードが全ストアを所有する**。呼び出し側が「メトリクスも消してください」を覚えている必要がある設計は必ず破られる。`NestStore` が `KrsCache` / `RepoDirectory` / `RunStatusStore` / `MetricsStore` / `ReadCounter` を所有し、purge が全部を呼ぶ
- **網羅テストを prefix の台帳にする**。`nest-purge-coverage.test.ts` の `SEEDERS` が「この package が書く全 prefix」の一覧を兼ねる。台帳に足して配線を忘れればテストが落ち、台帳に足し忘れれば**レビュワーが見て短いことに気づける**長さに保つ
- **戻り値をカテゴリ別にする**。`{documents, pointers, runs, metrics, reads}`。合計 1 個の数値だと、どのカテゴリが 0 なのかを誰も見ない
- **削除の約束を書いた ADR から鍵 layout を参照する**。新しいストアを書く人が最初に読む場所に「ここに足したら purge も」と置く

## 由来

karasu-nest のメトリクス（[#2226](https://github.com/kompiro/karasu/issues/2226)）は `metrics/` と `reads/` の 2 つの prefix を足した。`metrics/` は `NestStore` の purge に配線され、その配線の理由（「本文に repo の内容が無くても鍵に名前がある」）はコード中に長いコメントで書かれていた。**同じ PR で足された `reads/` には、その議論が持ち越されなかった。** `ReadCounter.purgeInstallation` は書かれていたが、テスト以外から呼ばれていなかった。

結果として、アンインストール後も `reads/krs/v1/<inst>/<owner>/<private-repo>/<日付>` が 400 日残り、purge は成功を返していた。ADR-1990 決定 6 が禁じているそのものである。

`metrics/` 側の単体テストは通っていた。`reads/` 側の単体テストも通っていた（`ReadCounter.purgeInstallation` を**直接**呼んでいたので）。受け入れテストにも「計測データも purge に含まれる」という緑のチェックが付いていた。**壊れていたのは配線だけで、配線を見るテストが 1 つも無かった。**

bug としては顕在化していない（レビューで発見、proactive）。同 PR で配線と網羅テストを入れて閉じたが、この失敗は「関連するテストが全部通っている」状態と両立し、しかも**次に prefix を足す人に対して何も学習が残らない**ため、観点として独立させる。

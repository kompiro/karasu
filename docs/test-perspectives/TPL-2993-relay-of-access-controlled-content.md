# TPL-2993: 中継は匿名の閲覧者として取りに行き、見えないものを「無い」と区別させない

## 観点

公開範囲を持つ資源（nest の投稿は public / unlisted）を、別の面から見せる中継を足すと、元の面が守っていた境界が中継の側で緩みやすい。守るべき点は 3 つある。

- **中継は誰の資格でも取りに行かない。** 利用者の cookie・トークンを上流へ転送すると、中継の応答がその利用者の権限で決まる。共有キャッシュに載ればほかの人にも配られる
- **見えないものと無いものを、中継の応答でも区別させない。** 元の面が「unlisted は未存在と同じ 404」にしているなら、中継も同じ status・同じ本文で返す。区別すれば、中継が「この人は何かを投稿して隠した」を問い合わせられる oracle になる
- **取得先を入力から選ばせない。** 上流のホストは定数にし、入力（パス・クエリ）からは資源の id だけを受け取って文法で検証する

## 想定される失敗モード

- 利用者の cookie を上流へ転送し、所有者が開いたときだけ unlisted の本文が返る。その応答が `public` のキャッシュに載り、次に同じ URL を踏んだ他人にも unlisted の本文が配られる
- 上流の 404 を中継が「取得できませんでした（502）」に変換し、上流の 200 と 404 と 5xx で応答が 3 通りに分かれる。未存在と unlisted は同じ 404 でも、中継のエラー本文に上流のメッセージを含めた結果、違いが漏れる
- id をそのまま URL に連結して上流を叩き、`../` やホスト名を含む入力で、想定外のパス・ホストへリクエストが飛ぶ（SSRF）
- 上流のサイズ上限を中継が知らず、上流が返すだけ全部読んで Function のメモリや時間を使い切る

## チェックリスト

中継・転載の経路を足すとき:

- [ ] 上流への fetch に、利用者由来の cookie・Authorization・転送ヘッダが 1 つも乗っていないか（テストで上流側の受信ヘッダを検査する）
- [ ] 上流が「見えない」と「無い」を同じ応答にしているなら、中継の応答（status・本文・キャッシュヘッダ）も両者で同一か
- [ ] 上流のホストは定数か。入力からは id だけを受け取り、文法外の id では上流を呼ばずに返しているか
- [ ] 上流の応答サイズに上限を置き、超えたら読み切らずに打ち切っているか
- [ ] 中継の応答のキャッシュ期間は、上流の資源が可変（差し替え・非公開化・削除）であることに見合っているか

## 既知の対処パターン

- 上流ホストの定数化と入力の文法検証: `packages/app/src/render/repo-permalink.ts` の `RAW_HOST` と `OWNER_RE` / `REPO_RE`
- 見えない = 無い の 404: `packages/nest/src/routes/gallery.ts` の `visibleSubmission`

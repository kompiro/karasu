# TPL-2958: 束ねた共有区間は、後に走るすべてのパスを通ったあとも同一座標のまま残ることを測る

## 観点

束（同じ target へ入る fan-in、同じ source から出る fan-out など）は「兄弟が同じ幾何を共有している」ことで成り立つ。この共有は束を作ったパスの時点では正しくても、**後に走るパスが要素ごとに独立して座標を書き換える**と壊れる。後続のパスは束の存在を知らず、1 本ずつ最適に動かすからである。

したがって束を足すときは、束を作った直後ではなく、**チェーンの最後（正規化まで含む）で、兄弟の共有区間がまだ同一座標であること**を測る。後続のパスには 2 種類あり、別々の壊れ方をする。

- **要素ごとに「重なりを分ける」パス**（チャネルのレーン分割・ポートの扇）: 共有区間を重なりとみなし、兄弟を別々の位置へ引き剥がす。
- **要素ごとに「同じ量だけ動かす」パス**（平行移動・正規化）: 共有を可変オブジェクトの参照で表していると、同じ点が兄弟の本数分重ねて動く。

## 想定される失敗モード

- **束が途中で分かれる。** 合流したはずの spine が、行間チャネルで N 本の平行線に戻る。本数チップは合流を示しているのに、線は分かれて見える。
- **束の端がカードから外れる。** 共有している端点オブジェクトが本数分平行移動され、矢印がカードから離れた場所で終わる。外れた端点へ向かう最後の区間は斜めになってカードを貫通する。
- **柵が green のまま壊れる。** 束を作ったパスの単体テストは通る。壊すのは後続パスで、しかも平行移動が 0 の図（多くの examples）では症状が出ない（TPL-2598）。

実例（#2958 の spike）: ガター corridor を共有端ごとに 1 レーンへ束ねたところ、次の 2 つが起きた。

1. `collectChannels` が兄弟の同一の水平 run を別レーンに分けた。
2. `normalizeCoordinates` が共有の `toPoint` を兄弟ごとに平行移動し、Dify の Knowledge 画面で貫通が 0 → 33 になった。

2 は main の grouped 表示にも既に潜んでいた（#2966。Dify / team で 5 本の矢印が 128〜256px カードから外れている）。examples の grouped 図はどれも、トランクがあるときに平行移動が起きないので、柵が検出していなかった。

## チェックリスト

束を作る / 束の兄弟に幾何を共有させる変更をするときに確認する:

- [ ] 束を作ったパスより後に走るパスを列挙し、それぞれが兄弟を 1 単位として扱うか確認したか（レーン分割・ポートの扇・seating・平行移動・正規化）
- [ ] チェーンの**最後**で「兄弟の共有区間が同一座標のまま」を assert するテストがあるか
- [ ] そのテストの入力に、**平行移動が 0 でない図**（左ガターがある図など）が含まれているか
- [ ] 共有を可変オブジェクトの参照で表しているなら、in-place で書き換えるパスがオブジェクト単位で 1 回だけ動かすか

## 既知の対処パターン

- **兄弟に共通の束 id を持たせ、後続パスがそれを 1 単位として扱う。** `fanOutGutterPorts` は `trunkId` / `outTrunkId` の兄弟を 1 スロットとして一緒に動かす。レーン分割も同じ id で同一 run を 1 レーンにまとめる。
- **in-place の平行移動はオブジェクト単位で重複を除く。** 点を `Set` に集めてから 1 回ずつ動かす。参照を共有しているからこそ、後続パスで兄弟が一緒に動く。点を兄弟ごとにコピーして逃げると、今度は後続パスで兄弟が分かれる。

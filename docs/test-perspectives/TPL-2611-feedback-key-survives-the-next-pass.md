# TPL-2611: フィードバックの鍵は次のパスで動かない構造キーで持つ

## 観点

後段の測定値を前段に返す設計では、「**何を** どれだけ足すか」より「**どこに** 足すか」の
指し方が壊れやすい。1 回目の出力に付いていた座標（x / y / 幅）でその場所を指すと、
2 回目の実行はまさにその座標を動かすので、鍵は適用された瞬間に古くなる。

**フィードバックの適用先は、2 パス目が動かさない構造キーで指す。** 第一候補は要素の
**識別子**（id・完全パス・宣言スコープ）で、これは配置をやり直しても同じものを指す。座標は
2 パス目の**出力**として読み直す。

**序数は識別子の代わりにならない。** 「左から 3 番目」は位置の言い換えでしかなく、順序を
決めるパス（karasu では `sortByBarycenter`）が動けば別の要素を指す。序数や所属を鍵に使うなら、
適用時に**前段の出力と照合し、食い違ったら予約を破棄して既定に戻す**こと。照合できない鍵は
使わない。

ADR-2598 の行予約はこれを満たしている。予約は「行序数 r の直前に extra gap」であり、
y ではない。`placeNodesInLayers` は sub-row を含めた行を数え上げて `rows` として返し、
予約はその添字で持つ。2 パス目で全ての y が動いても、鍵は同じ行を指し続ける。

同じ設計を水平軸でやるとき、「x = 1,240 の位置に列を空ける」は成立しない。行の中央寄せは
行の幅に依存し、幅は予約そのもので変わるからである。かといって「行 r のカード序数 i の直前」も
足りない — 序数は順序決定の出力なので、順序が変われば別のカードを指す。鍵は
**「カード `a` と `b` の間」**（両方 id）で持ち、適用時に `a` と `b` が今も隣接していることを
確かめ、そうでなければ予約を捨てる。実 x は配置後に読む。

## 想定される失敗モード

- **鍵が指す場所がずれる。** 1 回目に測ったカードの間に予約したはずが、2 回目では別の
  カードの間が広がっている。図は「意味の無い場所に空白がある」形で壊れ、症状が原因から遠い
  ので追いにくい。
- **鍵がずれたことを誰も検出しない。** 予約は適用されたので処理は成功を報告し、エッジは
  相変わらずガター送りになる。「パスが走ったのに効果が出ない」形（[TPL-2643](TPL-2643-skip-reports-success-without-running.md)
  と同型）。
- **ずれを直そうとして 3 パス目が生える。** 「もう一度測って合わせる」を足すと、
  [TPL-2593](TPL-2593-layout-feedback-is-floor-first-and-monotone.md) の停止性の議論が
  やり直しになる。
- **要素を 1 つ足しただけで無関係な場所の予約が動く。** 鍵が「左から数えて 3 番目」のような
  不安定な添字だと、モデルの小さな変更が図全体を組み替え、diff の局所性が失われる。
  順序決定のヒューリスティック（barycenter・median）を挟む経路では、要素を足していなくても
  隣接エッジが 1 本増えただけで序数が入れ替わる。

## チェックリスト

後段の測定値を前段に返す経路を足すとき:

- [ ] 鍵は識別子（id・パス・宣言スコープ）か、前段が**出力として報告した**添字だけで
      できているか。2 パス目が書き換える座標・寸法、順序決定パスの出力である序数、後から
      再導出した添字は含まない（ADR-2598 は `rows` を返す形にし、y から行を数え直していない）
- [ ] 適用時に鍵を前段の出力と照合し、ずれていたら黙って無効になるのではなく
      **予約を取り下げて既定に戻る**経路があるか
- [ ] モデルに要素を 1 つ足したとき、無関係な場所の予約が動かないことをテストで固定したか
- [ ] パス数の上限が構成で決まっており、ずれの補正のために増えていないか

## 既知の対処パターン

- **構造キーで持つ**: ADR-2598 の `extraGapBeforeRow`（行序数 → 追加 gap）。
  `placeNodesInLayers` が `rows: string[][]` を返し、予約側がその添字で鍵を作る。
  「予約と配置が同じ数え方で行を数える」ことを、再導出ではなく戻り値の共有で保証している。
  `rows` の中身は id なので、序数ではなく**要素そのもの**で照合する余地も同じ戻り値が与えている。
- **鍵を作る側の判定に、フィードバックの結果を食わせない**: 鍵が「行 r のカード i」なら、
  行の構成を決める判定（karasu では `wrapLayerIntoRows` の幅による折り返し）は
  **フィードバックを足す前の値**で行う。足した後の幅で折り返すと、鍵が指す行そのものが
  組み替わり、予約は「適用されたが別の場所に効いた」状態になる。
- **never worse のフォールバック**: 鍵が指す場所に予約を適用できないと分かったら、その予約
  だけ捨てて既定の配置に戻る。ADR-968 の「候補が clear でなければ直線にフォールバック」と
  同じ形。

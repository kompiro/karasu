# TPL-3480: 別の文法に書き出す id は、その文法の lexer で読み戻して同じ値になる形で出す

## 観点

core が組み立てる id のうち、**別の文法のソースに書き込まれることが前提のもの**がある。
edge の canonical id は SVG の `data-edge-canonical-id` に載り、app の右クリックメニューが
`edge#${canonicalId} { ... }` として `.krs.style` に書き込む。このとき id は「core の中で
一意か」だけでなく、**書き込み先の lexer で読み戻して、元と同じ値になるか**も満たす必要がある。

`.krs` の quoted id は任意の文字列を取れるが、書き込み先（`.krs.style` の識別子）が読める
文字は狭い。モデルの文字列を素のまま繋いで id を作ると、普通の id では問題なく動き、
空白・記号・末尾の `-` などを含む quoted id のときだけ、書き込んだ rule が parse エラーに
なるか、別のトークン列として読まれて別の要素に当たる。内部キーの injectivity（TPL-1352）
とは別の条件で、injective なキーでも書き込み先で読めなければ同じことが起きる。

## 想定される失敗モード

- GUI が書き込んだ `edge#a b->c` が `.krs.style` の parse でエラーになり、操作が何も
  起こさないまま壊れた rule がファイルに残る（#3480）
- 書き込んだ id が別の区切り方で読まれ、別の要素（著者 id が一致する edge など）に当たる
- 書き込み先の字句規則と重なる文字（`->` / `-->` の手前の `-`）で、別々の要素の id が
  同じ文字列になる（`"a-" -> c` と `a --> c`）

## チェックリスト

別の文法に書き出す id を作る・変えるとき:

- [ ] id を組み立てる部品（端点・セグメント）が書き込み先の識別子として読めるかを、
      書き込み先の **lexer 自身** に判定させているか（字句規則を別に書き写していないか）
- [ ] 読めない部品は書き込み先が受け付ける引用形（`.krs` と同じ文字列リテラルなど）で
      出し、書き込み先の parser がその形を受け付けるか
- [ ] parser が引用形を読んだら、生成側と**同じヘルパー**で正規化して id を組むか
      （`edge#"a"->c` と `edge#a->c` が同じ id になる）
- [ ] 「生成した id を書き込み先の構文に埋めて parse し、同じ id が返る」往復を、空白・
      `->`・`"`・`\`・末尾 `-`・非 ASCII 識別子を含む値でテストしているか
- [ ] 普通の id（識別子として読めるもの）の出力が変わらないことをテストしているか

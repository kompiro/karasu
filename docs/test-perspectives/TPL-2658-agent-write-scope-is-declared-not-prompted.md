# TPL-2658: エージェントに任せる自動化の書き込み範囲は、prompt の文言ではなく宣言で検証する

## 観点

エージェントが「何をできないか」の検証は、**prompt に書いた禁止文ではなく、実行系が受け付ける操作の宣言**（safe outputs・token permission・スコープ設定）に対して行う。

prompt は助言であって境界ではない。「マージしてはいけない」と書いてあっても、実行系にマージ操作が渡っていれば、その自動化はマージしうる。逆に宣言側にマージ操作が無ければ、prompt が何を言おうとマージは起こらない。したがってテストが読むべきは宣言であり、prompt の文面をレビューで確認しても保証にはならない。

宣言と prompt は別々に編集できるため、両者は必ずずれる。危険なのはずれ方が非対称なことで、**prompt が「変更しません」と言い続けたまま宣言だけが広がった状態**は、レビューでは安全に読める。

## 想定される失敗モード

- 宣言に書き込み操作を足したのに prompt の「〜しません」が残り、diff を読んだ人が「この自動化は読み取り専用」と誤認する
- 権限を read から write に上げる変更が、機能追加（「コメントも付けたい」）の副作用として通り、権限拡大それ自体はレビューの議題にならない
- 宣言をコンパイルして生成物（lock ファイル等）を作る仕組みで、宣言だけ編集して再生成を忘れる。リポジトリが説明している境界と、実行される境界が食い違う
- 生成物が新しいジョブ・ランナー・アクションを持ち込み、`.github/workflows/**` を走査する既存のポリシーガードの前提を黙って破る

## チェックリスト

エージェントを走らせる自動化を追加・変更するとき:

- [ ] 宣言された書き込み操作を allowlist に対して検証するテストがある（prompt の文言は検証対象にしない）
- [ ] allowlist を広げる変更は、「どの人間の判断をエージェントに渡すか」を PR 本文で名指ししている
- [ ] 宣言された権限がすべて read であること、あるいは write が必要な理由が書かれていることをテストが確認している
- [ ] 宣言から生成物を作る仕組みなら、宣言と生成物の一致をテストが確認している（再生成忘れの検出）
- [ ] 生成物が既存のポリシーガード（ランナーラベル・言語バージョン pin 等）に与える影響を確認した

## 既知の対処パターン

`scripts/ci/agentic-workflow-safety.test.ts` が 4 点を機械検査する: 宣言された safe outputs が allowlist の内側にあること、permission がすべて read であること、宣言が lock ファイルにコンパイル済みであること、そして走査対象が空でないこと（パーサ健全性）。

allowlist は「人間の判断を奪わない出力」で引いている。コメントと Issue 起票は判断材料を人の隣に置くだけで、マージ・push・close・dispatch はリポジトリまたはレビュー状態そのものを動かす。

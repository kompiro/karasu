# TPL-2287: 検出器の false positive 予算は正しさの一部 — near-miss 事例を仕様として書く

## 観点

検出器のテストは「検出できたか」に偏る。しかし**検出しすぎる検出器は、検出しない検出器と同じくらい速く役に立たなくなる**。過検出が多い redaction は出力を無意味にし、過検出が多い lint は `disable` コメントで黙らされる。どちらも最終状態は「その仕組みが効いていない」で同じである。

したがって検出器の仕様は 2 つの集合で書く。**当てる集合**と**当ててはいけない集合**であり、後者（near-miss）のほうが書くのが難しく、抜けやすく、価値が高い。「commit SHA」「UUID」「`tokenizer`」「`config.token`」のような、当たりそうで当ててはいけない入力を列挙したものが、実質的にその検出器の仕様である。

もう 1 つ、規則集合に特有の失敗がある。**汎用規則が個別規則の結果を食う**。`github_token = "ghp_…"` を「GitHub token」として検出したあと、汎用の「secret っぽい名前への代入」規則が同じ場所に再び当たると、finding のラベルが汎用側に上書きされる。値は消えているので漏洩はしないが、**何が漏れたのかという情報が消える** — finding の唯一の仕事がそれである。

## 想定される失敗モード

- **positive テストが `toContain` で書かれている**。`expect(text).toContain("[REDACTED]")` は、規則が `/\S+/` でも通る。行全体が破壊されていても通る。実際 #2287 では、github-token の規則を `/\S+/` に差し替えても 3 つの assertion がすべて通った
- **near-miss 集合が無い**。過検出は「テストが落ちる」形では現れず、「使ってみたら出力がゴミ」という形で現れる。そのころには検出器を弱める圧力がかかっている
- **汎用規則が個別規則の後に走り、置換済みテキストを再検出する**。ラベルが上書きされ、長さが「置換文字列の長さ」に化ける
- **自分が書いた置換マーカーを自分で再検出する**。出力側の検査に使うと、自分の出力を拒否する
- **部分文字列置換で位置を取り違える**。`match.replace(secret, …)` は match 内の**最初の**出現を置換するので、鍵名や scheme に同じ文字列があると**本物のほうが残る**（#2287 実測: `hunter2plus_password = "hunter2plus"` で値が素通り）
- **正規表現が入力長に対して二次**。`prefix* + keyword + suffix*` の形は near-miss の繰り返しで爆発する（#2287 実測: 240 KB で約 4 秒）。信頼できない入力を CPU 制限のある環境で走らせるなら、これは可用性の問題である
- **除外ヒューリスティックが本物を通す**。「`$` で始まるものは環境変数参照」は bcrypt hash（`$2b$…`）を全部見逃す

## チェックリスト

検出器（redaction / lint / 診断）の規則を足す・変えるとき:

- [ ] positive テストは**結果の文字列を完全一致で**検証しているか。`toContain` は規則が壊れていても通る
- [ ] finding / 診断の**中身も完全一致で**検証しているか（件数・ラベル・位置）。ラベルが別規則に化けても `toContain` は気づかない
- [ ] **near-miss 集合**があるか。その規則が当たりそうで当ててはいけない入力を、規則ごとに最低 1 つ
- [ ] 規則同士の**相互作用**をテストしたか。汎用規則と個別規則が同じ入力に当たる例、置換後のテキストが次の規則に当たる例
- [ ] 検出器が**自分の出力を再検出しない**ことを確認したか。出力側の検査にも同じ規則集合を使うなら必須
- [ ] 位置指定の置換に**インデックス**を使っているか（`RegExp` の `d` フラグなど）。部分文字列置換は取り違える
- [ ] 敵対的入力での**実行時間**を測ったか。ネストした量化子を避け、上限付き文字クラスで書いたか
- [ ] 除外ヒューリスティックは**構文形で**書かれているか（`${VAR}` `{{x}}` `<x>` `$UPPER`）。先頭 1 文字での判定は必ず本物を巻き込む

## 既知の対処パターン

- **形式でアンカーする**: エントロピーではなく、その credential 自身の形式（prefix・長さ・armour）で当てる。形式が無いものだけを、代入の左辺という別のアンカーで拾う
- **判定を 2 段に割る**: 「代入の形」を正規表現で、「鍵名が secret っぽいか」をコードで判定する。正規表現の後方参照的な複雑さが消え、二次挙動も消え、鍵名の判定を単体テストできる
- **自分のマーカーを最優先で除外する**: すべての規則の前に「これは自分が書いたものか」を見る
- **near-miss を `it.each` の表にする**: 表そのものが仕様として読める。規則を足す人は表に行を足すことになる
- **完全一致で書く**: `expect(result.text).toBe(...)` と `expect(result.findings).toEqual([...])`。書くのは少し面倒だが、これが「規則が意図どおり狭いか」を担保する唯一の形

## 由来

karasu-nest の secret redaction（[#2287](https://github.com/kompiro/karasu/issues/2287)、[ADR-1990](../adr/1990-karasu-nest-pivot-server-reverse.md) 決定 2）。レビューが実測で 5 件を出した: 部分文字列置換による位置取り違えで**本物の値が素通り**、`$` 先頭判定による bcrypt hash の全見逃し、引用符必須による `.env` / `.npmrc` / YAML / JSON の取りこぼし、汎用規則による個別 finding の上書き（および自分の置換マーカーの再検出で出力を拒否）、そして 240 KB 入力での約 4 秒の二次挙動。

positive テストはすべて通っていた。実際、github-token の規則を `/\S+/` に置き換えても通った。**当てる側のテストだけでは、検出器が正しいかどうかは何も分からない。**

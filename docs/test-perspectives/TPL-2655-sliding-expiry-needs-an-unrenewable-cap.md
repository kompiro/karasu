# TPL-2655: 更新で延びる期限には、更新されない上限を併置する — 上限はストアが強制できないので読み取り時に確かめる

## 観点

**期限を「使うたびに延びる」ようにした瞬間、期限を置いた理由が消えうる。** 資格情報に
期限を置くのは、漏れたものがいつか無効になるためである。使用のたびに延びる期限は、
その「いつか」を使用者が無限に先送りできる形にする。盗まれた cookie を使い続ける側も
使用者なので、**延長は正規の利用者と攻撃者に等しく効く**。

だから sliding expiry は、単独では成立しない。成立させるのは**延びない期限**を外側に
置くことで、これは 2 つの期限が別の起点を持つことを意味する。

| 期限 | 起点 | 動くか |
| --- | --- | --- |
| idle 窓 | 最終使用 | 使うたびに動く |
| 絶対上限 | 発行 | 動かない |

ここに構造的な罠がある。**ストアが強制できる期限は、たいていレコードごとに 1 つしか
ない。** KV の `expirationTtl`、Redis の TTL、いずれも 1 本である。その 1 本は延びる側に
使うしかない（延びる側こそストアに消させたいものだから）。結果、**上限を強制する手段が
ストアに残らない**。上限を「書き込み時の TTL」で表現しようとすると、延長のたびに上書き
されて上限そのものが消える。

したがって**上限は読み取り時に確かめるしかない**。上限を過ぎたレコードは、ストアにまだ
在っても「無い」として読む。この判定を書き忘れても、テストは通り、機能は動き、ストアの
TTL も正しく効いているように見える — 壊れているのは「上限がある」という主張だけで、
それは上限に達するまで観測されない。

**書き込み量も同時に決まる。** 使用のたびに書き直すと、認証のたびにストアへ 1 回書く
ことになる。延長の閾値（レコードがどれだけ古くなったら書き直すか）を置いて間引くのが
定石で、閾値は idle 窓よりずっと短ければ利用者からは観測できない。

## 想定される失敗モード

- **上限を忘れる。** slide だけ実装し、資格情報が自分自身を無期限に更新できる。期限を
  置いた理由が消えているが、動作は正常に見える
- **上限をストアの TTL で表現しようとする。** 強制できる期限が 1 つしか無いので、
  延長のたびに上書きされて上限が消える。書いた本人は上限を実装したつもりでいる
- **上限が近いときの残り時間がストアの TTL 下限を割る。** Cloudflare KV は 60 秒未満の
  `expirationTtl` を拒否する。上限直前の延長が例外になり、認証経路の途中で落ちる
- **延長の失敗がリクエストを落とす。** 認証は読み取りで済んでいるのに、その後ろの書き込み
  の失敗を握らずに 500 や「サインインし直せ」に変えてしまう
- **クライアント側の期限が延びない。** ストアだけ slide させても、cookie の `Max-Age` が
  発行時の窓のままなら、ブラウザがその日に cookie を捨てて slide は無意味になる
- **既存レコードに新フィールドが無い。** 「最終使用」を新しいフィールドで持つと、変更前に
  書かれたレコードには無い。読み取り時の既定値を決めていないと、全員が一斉にサインアウト
  するか、逆に上限が効かないレコードが残る
- **テスト fixture の固定日付が、上限を越えて古くなる。** 過去の日付で発行した資格情報を
  使う test は、上限が実時刻で判定される限り**書いた日は通り、あとで落ちる**。CI が緑の
  まま時限爆弾になる（#2655 で nest の route test 3 本が実際にこれを踏んでいた）

## チェックリスト

期限が延びる仕組みを足す・変えるときに確認する:

- [ ] 延びない上限を置いたか。置いたなら、**それが読み取り時に判定されている**か
      （ストアの TTL は延びる側に使われていて上限を守れない）
- [ ] 上限に達したレコードが「無い」として読まれることを、**ストアにレコードを直接
      置いたテスト**で確かめたか（延長経路が上限で clamp するので、正規の経路だけでは
      この状態を作れない）
- [ ] 閾値内の連続アクセスで**書き込みが増えないこと**を assert したか
- [ ] 上限の残りがストアの TTL 下限を割るときの挙動を決め、テストしたか
- [ ] 延長の失敗が、認証・認可の結果を変えないことを確かめたか
- [ ] クライアント側が持つ期限（cookie の `Max-Age` 等）が、延長後も届く値になっているか
- [ ] 変更前に書かれたレコードが読めるか。**新フィールドの既定値を決めたか**
- [ ] テストの fixture が固定日付で資格情報を発行していないか。しているなら、実時刻で
      上限に近づく（`new Date()` で発行するか、時刻を明示的に渡す）

## 既知の対処パターン

`packages/nest/src/store/sessions.ts`（#2655）が 3 定数で表現している。

- `SESSION_IDLE_TTL_SECONDS` — 延びる窓。ストアの `expirationTtl` に渡す唯一の値
- `SESSION_ABSOLUTE_TTL_SECONDS` — 発行からの上限。`get` が読み取り時に判定し、
  cookie の `Max-Age` でもある（クライアント側の期限が先に切れないように）
- `SESSION_REFRESH_AFTER_SECONDS` — 書き込みの間引き閾値

延長は `refreshIfStale` に閉じており、`min(idle 窓, 上限までの残り)` で TTL を clamp し、
残りがストアの下限を割るときは書かない。上限の判定は `get` にあり、**延長経路とは独立
している** — 延長を通らずに現れたレコード（直接書き込み、移行、丸めの効いた TTL）にも
上限が効く。

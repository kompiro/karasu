# TPL-2805: 予算は、その名前が指す仕事だけを覆う

## 観点

timeout は「これを超えたら異常」という**主張**であって、何を測っているかは置いた場所が決める。
準備と本命の仕事を 1 本の予算が覆っているとき、その予算が発火しても**どちらが遅かったのかは
分からない**。それでも報告は本命の名前で出る（赤い required check・「suite が失敗した」という
自動起票）ので、読み手は本命が壊れたと読む。

準備の所要時間が外部要因で決まる場合、この誤りは避けられない形で顕在化する。パッケージ
インストールやダウンロードは、こちらのコードが同じでも mirror 次第で 10 秒にも 13 分にもなる。
予算を上げて凌ぐと、今度は**本物のハングの代価が上がる**だけで、赤の意味は曖昧なままになる。

置き方は 1 つに畳める: **「異常」を意味する境界は本命の仕事に置き、外側の予算は準備を吸収する
係に回す**。外側は内側を必ず上回らせる。差が無いと外側の打ち切りが内側と競合し、同じ誤報が戻る。

## 想定される失敗モード

- 準備が遅い日に、1 件も失敗していないテストが打ち切られ、required check が赤くなる。本物の
  失敗と区別できず、原因はログの数百行先にしかない
- 打ち切りが「テストの失敗」として自動起票され（nightly の tracking issue 等）、誰も落として
  いない赤を追いかけることになる
- 対処として外側の予算だけを上げ、ハングした実行が予算いっぱいまで課金されるようになる。
  境界は相変わらず「準備 + 本命」を測っている
- 本命の仕事が数秒で、予算のほぼ全部が準備のために存在している状態を、予算の数字だけ見て
  「余裕がある」と読む
- 準備側に短い timeout を足して、観測済みの正常な所要時間を殺す（遅い準備は遅延であって
  失敗ではない）

## チェックリスト

timeout / 予算を置く・変えるときに確認する:

- [ ] 「異常」を意味する境界が、本命の仕事**だけ**を覆う位置にあるか（step 単位 / 呼び出し単位）
- [ ] 外側の予算は、内側の境界 + 準備の観測最大を収容できるか。観測最大はどの run から採ったか
      言えるか（速い日ばかり引いた実行単位は、安全なのではなく標本が無いだけである）
- [ ] 内側の値は観測から決めたか（直近 run の分布を見たか）。準備の遅さを吸収するために
      内側を膨らませていないか
- [ ] その打ち切りが誰にどう報告されるか（required check / 自動起票）を確認し、報告の文言が
      指す対象と境界が測る対象が一致しているか
- [ ] 値の drift を機械が落とすか（同じ形の実行単位が後から増えたときに検出できるか）

## 既知の対処パターン

- **step 側に本命の境界、job 側に上位予算**（[ADR-2807](../adr/2807-suite-budget-clears-its-setup.md)、
  [ADR-2805](../adr/2805-suite-timeout-bounds-the-test-step.md) を supersede）。
  `.github/workflows/e2e.yml` では `Run E2E tests` に 15 分、job に 35 分を置き、境界のない
  `apt-get` は job 予算に吸収させる。**外側の予算は「内側の境界 + 準備の観測最大」以上**という
  関係そのものを機械で固定する — 差の下限を適当な定数（当初は 5 分）にすると、観測より薄い
  予算がそのまま通る（#2807）
- **総所要時間ではなく無通信で打ち切る**（[TPL-2374](TPL-2374-long-call-bounded-by-silence-not-duration.md)）。
  外部 API 呼び出しでは、本命だけを覆う境界が「沈黙の長さ」になる。同じ観点の別形

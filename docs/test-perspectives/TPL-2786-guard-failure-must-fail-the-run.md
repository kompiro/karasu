# TPL-2786: 安全網が結論を出せなかったときは、通過ではなく失敗として扱う

## 観点

ゲートの結果は 2 値ではなく 3 値である — **通過・不通過・判定不能**。設計で決めなければならないのは
3 つ目をどちらに寄せるかで、既定に任せると通過側に落ちる。安全網が守っているものが実在するなら、
判定不能は不通過として扱い、後段を止める。

判定不能を通過に寄せた状態は、ゲートを外した状態より悪い。外してあることは設定を読めば分かるが、
判定不能を通過扱いにしている状態は**成功として報告される**ため、検査を通った実行と区別がつかない。
読み手は緑を見て検査済みだと解釈する。

ゲートを追加・変更するときに書くべきなのは「何を検出するか」ではなく、
**「検出器自身が動かなかったときに何が起きるか」**である。

## 想定される失敗モード

- 検査ジョブが失敗しても後段が走る。`continue-on-error` の既定、`if: always()`、`|| true` のいずれかが
  失敗を成功に変換しており、その変換は diff では設定 1 行にしか見えない
- 後段の条件が `needs.<gate>.result == 'success'` になっているが、ゲート側が自分の失敗を握り潰すため
  この条件が常に真になる。条件式だけを読むと正しく見える
- ゲートの失敗がサマリに出ず、別の Issue のコメントやジョブログを開かないと分からない。誰も開かないので
  何か月も気づかれない
- 検査対象が空だったときと、検査器が起動しなかったときが同じ「指摘ゼロ」として報告される
- 外形は動き続けるので、メトリクスや成功率では劣化が観測できない

## チェックリスト

後段の副作用を許可するゲートを追加・変更するとき:

- [ ] 判定不能のときに後段が走るか走らないかを、既定任せにせず宣言として書いた
- [ ] 判定不能を通過に寄せるなら、その判断を記録に残した（ゲートを外すのと同じ重さの決定として扱う）
- [ ] ゲートが結論を出せなかった回は、run / プロセスの終了状態そのものが失敗になる（ログの中だけで失敗していない）
- [ ] 宣言した posture が生成物（lock・コンパイル済み設定）まで届いていることをテストが検査している
- [ ] posture を既定へ戻す変更が、テストを書き換えずには通らない

## 既知の対処パターン

`scripts/ci/agentic-workflow-safety.test.ts` が gh-aw の threat detection について 4 点を機械検査する:
frontmatter が `continue-on-error: false` を宣言していること、lock に
`GH_AW_DETECTION_CONTINUE_ON_ERROR: "false"` が焼かれていること、`Conclude threat detection` ステップに
`continue-on-error` が付いていないこと、そして frontmatter で pin した検出モデルが lock に焼かれていること。
宣言・生成物・生成物の中の特定ステップの 3 層を見るのは、どれか 1 層だけでは
「宣言したが再生成し忘れた」状態を素通りさせるためである。

姉妹観点は [TPL-2658](TPL-2658-agent-write-scope-is-declared-not-prompted.md)。あちらは
**エージェントが何をできるか**を宣言で検査する観点で、こちらは**その宣言を守らせる検査器が動かなかったとき**を
扱う。両方が要るのは、書き込み範囲の宣言だけでは「範囲内だが敵対的な内容」を止められないためである。

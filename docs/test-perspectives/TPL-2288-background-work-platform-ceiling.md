# TPL-2288: 非同期実行の器は、実測した所要時間に対して器の上限を先に確かめる

## 観点

「レスポンスを先に返して、仕事は裏で続ける」仕組みを選ぶとき、**器の側の上限を数値で確かめないまま設計を積み上げると、正しく書かれたコードが本番でだけ動かない**。この失敗は型でもテストでも検出できない。`waitUntil(promise)` は型が通り、ローカルでは走り切り、単体テストでは promise を直接 await するので当然完走する。落ちるのは本番だけで、しかも例外ではなく**沈黙**として落ちる。

沈黙であることがこの観点を独立させる理由である。器に打ち切られた仕事は、失敗を記録する行にたどり着けない。`try/catch` の `catch` も、`finally` の後始末も、状態レコードを `failed` に書き換える処理も、すべて打ち切られた側にある。結果として残るのは「`running` のまま二度と変わらないレコード」で、これは**リトライを拒否する側の条件**でもあるため、1 回の打ち切りがその対象を恒久的に締め出す。

「上限」は器ごとに定義が違い、直感が効かない点も効いている。Cloudflare の `waitUntil` は「レスポンス送出**後**およそ 30 秒」であって、リクエスト開始からでも CPU 時間でもない。しかも 202 を即返す設計ほどこの猶予を早く消費し始める — **急いで返すほど裏の仕事に残る時間が減る**という、意図と逆向きの関係になっている。

## 想定される失敗モード

- `ctx.waitUntil` / `event.waitUntil` に分単位の仕事を載せる。数十秒で打ち切られ、状態レコードは `running` のまま残る
- await されない Promise を投げっぱなしにする。isolate が evict された時点で消え、ログも残らない
- 実行時間の上限を「CPU 時間」と読み違える。外部 API 待ちが大半の処理では wall-clock 側の上限に先に当たる
- ローカル（`wrangler dev` / SAM local / エミュレータ）で完走することを根拠に上限を確認しない。ローカルは上限を課さないことが多い
- 打ち切られた run が `running` を残し、in-flight チェックがその後のリトライを全部拒否する（1 回の事故が恒久的な締め出しになる）
- リトライで解決しようとするが、リトライ経路も同じ器に載っているので同じ場所で同じように打ち切られる

## チェックリスト

受付と実行を分離する経路を足す・変えるときに確認する:

- [ ] 仕事の所要時間の**実測値**（spike・本番ログ・ベンチ）を持っているか。「たぶん数十秒」は根拠にならない
- [ ] 器の上限を**一次情報で確認**したか（公式ドキュメント。訓練データの記憶や類推ではなく）。何を起点に数えた上限なのか（リクエスト開始 / レスポンス送出後 / CPU 時間）まで確かめたか
- [ ] 実測値が上限に対して**桁で余裕がある**か。同じ桁なら器を変える判断をしたか
- [ ] 器に打ち切られたとき、状態レコードが**どう見えるか**を書き出したか。`running` のまま残るなら、それを検出する手段があるか
- [ ] `running` が残ったときに**リトライできる**か。in-flight チェックが stale な記録を実行中とみなして永久に拒否しないか
- [ ] テストが器の上限を**回避していない**か（promise を直接 await するテストは、器の存在ごと消してしまう）
- [ ] 重複起動の防止が read-then-write だけに依存していないか。**実行基盤側の一意性**（決定的なインスタンス id・冪等キー）で二重起動を潰せるか

## 既知の対処パターン

- **持続実行のプリミティブを使う** — Cloudflare Workflows / Step Functions / Durable Objects alarm / ジョブキュー。リクエストのライフタイムから独立していることが要件で、「長めに待てる」ことではない
- **stale 判定を状態レコードに持たせる** — `startedAt` からの経過が実測値を十分上回ったら `running` を放棄済みとみなす。器が状態を書き換えられずに死ぬ以上、**生きている側が時間で推定する**しかない
- **決定的なインスタンス id** — commit SHA など仕事の同一性から id を作れば、重複 dispatch は実行基盤が弾く。read-then-write の競合が「二重実行」ではなく「敗者が同じ答えを受け取る」に変わる
- **器の選択理由をコードに書く** — なぜ `waitUntil` ではないのかを消さない。書いていないと、次に触った人が「軽いから」で戻す
- **本番でのみ検証できることを AT の手動項目として残す** — 器の上限は unit test で踏めない。「12〜19 分の run が完走する」は実デプロイでしか確かめられない

## 由来

karasu-nest の生成受付（[#2288](https://github.com/kompiro/karasu/issues/2288)）は、当初 `ctx.waitUntil(generate(...))` で実行していた。[ADR-1990](../adr/1990-karasu-nest-pivot-server-reverse.md) の gate spike が 85 ファイルの repo で **12〜19 分**を実測していたにもかかわらず、`waitUntil` の猶予が**レスポンス送出後およそ 30 秒**であることを確認しないまま設計を積んでいた。202 を即座に返す設計だったので、実質すべての実行が数十秒で打ち切られる状態だった。

コードレビューで指摘されるまで、型・単体テスト・lint のどれも異常を示していない。テストは `waitUntil` に渡された promise を直接 await しており、器そのものを消していた。同 PR で Workflow へ移し、stale 判定と決定的インスタンス id を併せて入れて閉じた（bug としては顕在化していないため proactive）。

**実測値を持っていたのに器の上限と突き合わせなかった**ことが失敗の本体で、これは知識の欠如ではなく手順の欠落である。だから観点として残す価値がある。

# TPL-2249: 解決に生成・パーソナライズを混ぜない

## 観点

permalink・共有 URL・deep anchor は、**URL が内容を決める**という一点で価値がある。この性質が成り立つとき初めて、リンクを ADR に貼れる・他人に渡せる・時間をおいて踏み直せる。

そこに「解決できなかったら生成する」「利用者の指示を反映する」を足すと、性質が静かに壊れる。同じ URL が、踏む人・踏む時刻・その人の権限によって違う内容を返すようになる。壊れたことは**エラーとして観測されない** — 誰も例外を見ず、ただリンクの意味が人によって違う状態になる。

区別すべきは 2 つの操作である:

- **resolution（解決）** — URL を内容へ写す。冪等・決定的・誰にとっても同じ。コストはほぼゼロで、認証も要らないのが普通。
- **creation（生成）** — 入力から新しい成果物を作る。副作用があり、コストと時間を伴い、入力ごとに違う結果になる。誰のコストかを決める必要がある。

**creation を resolution の応答にすげ替えない。** 生成が必要なら、生成は新しい安定した URL を mint し、元の URL はその repo / その資源の正準な内容を指し続ける。

## 想定される失敗モード

- 解決に失敗した URL でその場で生成し、生成結果を返してしまう。**同じ URL が 1 回目と 2 回目で違う内容を返す**（生成は決定的ではない）。ADR に貼ったリンクが、後から読んだ人には別の図を見せる。
- 利用者の指示（「決済まわりだけ見たい」）を既存の解決 URL に反映する。URL を渡された相手には指示が伝わらないので、**渡した本人と受け取った人が違うものを見る**。共有の意味が消える。
- 解決経路に、コストや権限を伴う行為をぶら下げる。**reader 向けの URL に installer 向けの行為が乗る**と、課金先の無い呼び出し経路ができる（誰でも踏める URL が誰かの quota を焼く）。水準の設定では塞げない構造的な穴で、URL を撒くだけで消費させられる。
- ログイン状態で解決結果を変える。ログイン済みの開発者には見え、リンクを受け取った人には見えない — という食い違いが、共有時にだけ表面化する。
- 解決の裏で長時間の生成を待たせる。数分オーダーの処理は同期 HTTP に載らず、タイムアウト・リトライ・二重起動を呼ぶ。

## チェックリスト

「URL → 内容」を保証している経路に応答分岐を足すとき:

- [ ] その分岐は resolution か creation か。creation なら、**元の URL の応答をすげ替えず新しい URL を mint**しているか
- [ ] 同じ URL を、別の人が・別の時刻に・ログインせずに踏んだとき、同じ内容が返るか
- [ ] その分岐にコストが伴うなら、**誰に付けるコストか**が決まっているか。認証を持たない訪問者でも起動できてしまわないか
- [ ] その分岐に時間がかかるなら、同期応答として成立するか。数秒を超えるなら、非同期 job + 進捗導線に分けたか
- [ ] 解決できなかったときの応答は、**次の一手が分かる形**か（黙って別の画面に化けていないか — #1961 の catch-all 観点と同型）

## 既知の対処パターン

- **状態を返し、行為は返さない**: 解決できなかった URL には「今どういう状態か」と「次の一手」を返す。生成そのものは利用者の明示的な操作で始める。同期で誠実に返せるのはここまで。
- **生成物に独自の identity を与える**: 生成した成果物は自分の安定 URL を持つ。元の URL は正準な内容（commit 済み / 既定生成物）を指し続け、リクエストで観点を変えたものは別資源として並ぶ。
- **pointer と record を分ける**（[TPL-1829](TPL-1829-adr-permalink-records-source.md) と同型）: 復元できる正本を repo 側に持ち、URL はそれを指す pointer に留める。生成物にも同じ形を適用すると、サービスが消えても記録が残る。
- **合流点を HTTP ではなく成果物の置き場所に取る**: resolution する面と creation する面を、API 呼び出しや service binding で繋ぐと、resolution 側に creation の都合（コスト・待ち時間・認証）が流れ込む。**creation 側の出力を resolution 側が元から読んでいる場所（repo の commit など）に書き込む**形にすると、2 つの面は実行時に結合せず、resolution 側は何も変えずに新しい成果物を扱える。#2249 では karasu-nest が生成 `.krs` を repo へ PR し、permalink 面は committed `.krs` を解決するだけ、という形にした。

# TPL-2253: 「どこからも消す」変更は手書きのファイル一覧ではなく検索で閉じる

## 観点

ある識別子をリポジトリから取り除く変更の受け入れ条件は、**「列挙したファイルを直したか」ではなく「その識別子がもう存在しないか」**で書く。

前者は作業計画であって完了条件ではない。列挙は人間が最初に思いついた場所の集合にすぎず、**列挙から漏れた場所は、レビューでも CI でも観測されない**。しかも移行 PR は「主要な使用箇所」を直せば動くので、取りこぼしがあっても green になり、完了したように見える。

残骸が害をなすのはずっと後で、しかも機能障害としてではなく「この変数はもう要らないのでは」という疑問の形で現れる。その時点では当初の文脈が失われているため、消してよいのか判断するのに元の移行を掘り直す必要がある。

## 想定される失敗モード

- 移行 PR の CI が green なのに識別子が残る。動作に使われていない残骸ほど、テストで落ちないので生き延びる
- 受け入れテストの「対象ファイル」欄が、事後には**完了範囲の記録として読まれる**。列挙が漏れていると「そこは対象外だった」と誤読され、残骸が意図的なものに見える
- 残骸が環境への不要な依存を作る。ホスト env / secret / 権限を、もう使っていない目的のために要求し続ける
- 消えたはずの仕組みを説明した ADR が生き残り、後続がその前提で判断する（ADR は歴史的記録なので書き換えられない — 失効は living doc 側で示す必要がある）

## チェックリスト

識別子をリポジトリから取り除く変更で確認する:

- [ ] 受け入れ条件に **`grep -rn <識別子>` が 0 件**（または残る箇所とその理由）という形の判定を置いたか
- [ ] 検索対象に **ビルド成果物以外のすべて**を含めたか — `.devcontainer/`・`.github/`・`.vscode/`・`scripts/`・dotfiles は「ソース」から漏れやすい
- [ ] 設定ファイル（`*.json` / `*.yml`）だけでなく **ドキュメントの手順**も検索したか。手順書に残った識別子は、次の人が環境変数を設定し直す原因になる
- [ ] 残す判断をした箇所について、**なぜ残すのか**をその場に書いたか（書かないと次の掃除で同じ調査が繰り返される）
- [ ] 除去を宣言する living doc（`docs/process.md` 等）を更新したか。ADR は歴史的記録なので書き換えず、失効は後続 ADR か living doc 側で示す

## 既知の対処パターン

- **完了条件を検索式で書く** — 「`.npmrc` と workflow を直す」ではなく「`grep -rn NODE_AUTH_TOKEN` が 0 件」。式が受け入れ条件なら、列挙の漏れは条件の失敗として現れる
- **消える予定の識別子には CI の grep ガードを 1 つ置く** — 完全に消したあと、再び生えることを防ぐ。既存の lint 群（`scripts/lint/*.ts`）と同じ形で足せる。ただし識別子 1 つのためだけに専用 workflow を足すのは過剰で、既存の docs 系ジョブに 1 ステップ足すのが釣り合う
- **列挙は計画、検索は条件** — 「対象ファイル」欄は残してよい。作業の見積もりには要る。ただし**それを完了判定に使わない**

## 由来

`@kompiro/*` を GitHub Packages から公開 npm へ移した [#1700](https://github.com/kompiro/karasu/issues/1700)（2026-06-23）は、対象ファイルを `.npmrc` / `package.json` / `.github/workflows/*.yml` と列挙して完了した。`.devcontainer/devcontainer.json` の `NODE_AUTH_TOKEN` passthrough はその列挙になく、**約 6 週間、誰にも使われないままホストの環境変数を要求し続けた**（[#2253](https://github.com/kompiro/karasu/issues/2253)）。

見つかったのは「karasu の開発はクラウドだけで完結するか」を調べたときで、移行そのものの検証では発見されていない。列挙が完了条件だった限り、この残骸を落とす検査は存在しなかった。

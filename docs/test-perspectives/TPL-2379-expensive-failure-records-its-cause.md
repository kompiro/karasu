# TPL-2379: 再現に実費がかかる処理の失敗記録は、再実行なしで原因が分かるだけの情報を持つ

## 観点

失敗の記録に何を残すかは、**次に誰かが原因を知りたくなったとき何をすることになるか**で決まる。安い処理なら「もう一度動かす」で足りるので、記録は薄くてよい。分単位・実費のかかる処理では、それが調査の最低コストになる — つまり**記録の薄さが、そのまま調査 1 回の請求額**である。

この観点が独立して要るのは、記録を薄くする判断が**それ自体は正しい**からである。外部サービスのエラー本文には、こちらが送った入力が引用されうる。それが他人のコードや個人データなら、ログにもエラーにも載せてはならない。ここで「だから全部捨てる」に飛ぶと、`invalid_request_error` も `authentication_error` も `overloaded` も同じ姿になり、区別する唯一の手段が再実行になる。正しい線は全捨てではなく、**固定語彙と自由文の間**にある。相手が enum で返すフィールド（`error.type`、status code、エラーコード）は入力を引用しえないので出せる。

多段パイプラインの計測にも同型の穴がある。成功したステップだけを記録する設計は、**落ちたステップだけが記録に現れない**。読み手は残った列を足し算してソースと突き合わせる羽目になり、その突き合わせ先は記録が生きている間に変わる。

## 想定される失敗モード

- 外部エラーの本文を丸ごと捨て、status だけ残す。全種類のエラーが同じ見た目になり、切り分けが再実行になる
- 逆に本文をそのまま載せ、送ったプロンプトや入力データがログ・エラー応答・チケットへ流出する
- 完了したステップだけを記録し、失敗したステップは記録の**不在**としてのみ表現される
- 失敗記録の保持期間だけ長く（監査目的など）、その記録を読み解くのに当時のソースが要る形になっている
- ログにだけ詳細を出す。ログは誰かが見ている間だけ存在し、保持設定が無効なら失敗の唯一の記録が消える

## チェックリスト

失敗経路を書く・変えるときに確認する:

- [ ] この処理を**もう一度動かすコスト**（時間・実費）を言えるか。言えないなら記録の厚みを決める根拠が無い
- [ ] 外部エラーのうち **固定語彙のフィールド**（type・code・status）を残しているか。捨てているのは自由文だけか
- [ ] 固定語彙のつもりのフィールドに自由文が来たときの扱いを決めたか（形で検査して落とす、が既定）
- [ ] 多段処理なら、**落ちた段の名前**が記録に入るか。成功した段の一覧からの引き算になっていないか
- [ ] その記録だけで原因の切り分けができるか。ソースツリーや別システムとの突き合わせを前提にしていないか

## 既知の対処パターン

- エラー型の形を正規表現で検査してから載せる（`/^[a-z][a-z0-9_]{0,39}$/` 程度）。通らない値は「型名ではない＝散文」とみなして捨てる
- 「試行中の段」を開始時に記録し、完了時に消す。失敗記録には消えなかったものが残る
- 失敗した入力そのものを短い TTL で別ストアに置く（`failed/` prefix、24 時間）。ただし置ける対象は方針で決まる — 生成物は置けても、他人のソースは置けない

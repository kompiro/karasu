# TPL-2810: 同じ検査の実装が 2 つになったら、緑同士は一致の証明ではない — 差分 fixture で規則差を測り、移す先が merge を止められるかを確かめてから片方を退役させる

## 観点

同じ検査の実装が 2 つあり、片方を退役させようとしているとき、確かめることは 2 つある。

1. **2 実装は同じ判定をするのか。** 現行 corpus で両方が緑であることは、その証拠にならない。
   緑同士の一致は「いまの入力にはどちらも文句を言わない」でしかなく、規則が同じだとは
   言っていない。規則差は、差が出る入力を**こちらから作って**初めて見える。
2. **移す先は merge を止められるのか。** 止められない場所へ移した検査は、
   [TPL-2446](TPL-2446-gate-side-check-runs-over-the-whole-set.md) の言うとおり**存在しない検査**である。
   これは「検査を消した」と気づかれにくい消し方で、diff には検査を残した痕跡しか映らない。

2 つはどちらも「差分が小さく見える」方向に判断を歪める。1 を飛ばすと乗り換えが無害に見え、
2 を飛ばすと退役が整理に見える。

## 想定される失敗モード

- **現行 corpus で両方が緑なので「同じ規則だ」と判断し、実際には拾い方が違っていた。**
  差は普段の入力に現れないだけで、規則としては存在する。移した後、これまで落ちていた入力が
  黙って通るか、これまで通っていた記述が突然落ちるかのどちらかが起きる
  - 実例 #2810: `scripts/lint/record-source-paths.ts` と `@kompiro/tpl-tools` の
    `tpl validate --source-prefix` はどちらも `docs/test-perspectives` に対して finding 0 件
    だった。差が出る入力を書いた fixture に当てると、**双方向に 4 つ**の規則差が出た —
    生成物セグメントの集合が違い（片方は repo 固有の 7 個、もう片方は普遍の 5 個で、
    `build` の扱いが逆）、block quote の中の fence と block quote 越しの marker は
    ローカル側だけが false positive として報告していた。どちらが厳しいかではなく
    **両方向に違っていた**ことが、緑同士を根拠にできない理由そのものだった
- **検査を「移した」つもりが、Required でない context へ落としていた。** 移設先の workflow が
  それ単体では merge を止められないと、検査は走り続けて赤くなりうるのに誰も止まらない。
  ステータス一覧には緑でも赤でもない行が増えるだけで、退役した側の実装はもう無い
- **移設先の `paths:` フィルタが、検査が壊れる変更の形と噛み合っていない。** 記録が指す
  ソースパスを腐らせるのは、その記録を 1 行も触らないコード変更である。docs パスで
  gate された workflow はその push をまるごと飛ばす（[TPL-2446](TPL-2446-gate-side-check-runs-over-the-whole-set.md) の
  列挙漏れと同型で、こちらは起動条件側の漏れ）
- **上流が出荷した機能を有効化し忘れる。** 依存を bump しても、検査を有効にするフラグを
  渡していなければ実行結果は緑のまま何も読んでいない。退役させた側の実装はもう無いので、
  そのディレクトリは**誰にも検査されていない**状態になる
  - #2810 では `--source-prefix` がそれで、フラグが無くても `tpl validate` は成功する
- **語彙が食い違ったまま移して、既存の記録が意味を失う。** 抑止や宣言の記法が実装ごとに
  違うと、移設した瞬間に corpus 側の宣言が読まれなくなる

## チェックリスト

同じ検査の 2 つ目の実装が現れた / 検査の所有者を移すときに確認する:

- [ ] **差が出る入力を自分で書いて**両実装に当てたか。現行 corpus で両方が緑であることを
      一致の根拠にしていないか。最低限、両実装の規則が明示的に違うと分かっている軸
      （除外集合・パーサの読み方・記法の解釈）は 1 ケースずつ書く
- [ ] 差分は**双方向**に見たか。「新しい方が厳しい」だけを確認して、古い方だけが拾っていた
      ケースを見落としていないか
- [ ] 見つかった差のうち、現行 corpus に実例が無いものについて、**将来出たときに何が起きるか**
      を書いたか（落ちる / 通る、および回避手段があるか）
- [ ] 移設先は **Required な status context** か。job 名まで確認したか（workflow ファイル名や
      workflow の `name:` ではなく、ruleset が要求している context 名と一致するのは job 名）
- [ ] 移設先の起動条件は、**検査が壊れる変更の形**を捕まえるか。記録 ⇄ コードの整合を見る検査
      なら、コードだけを触る PR で起動するか
- [ ] 上流実装を**有効にするフラグ**を実際に渡したか。渡し忘れても成功終了する種類のフラグなら、
      それが script に残っていることを機械で固定したか
- [ ] 抑止・宣言の**記法が両実装で同一**か。既存の corpus の宣言がそのまま通ることを確かめたか
- [ ] 退役させた側のコードに、**なぜその対象を見ないのか**を宣言箇所へ書いたか。書かないと
      次の人が「見落とし」と読んで戻す

## 既知の対処パターン

- **差分 fixture を組む（#2810 の対処）**: 実在の `packages/` / `scripts/` ツリーを symlink した
  一時ディレクトリに、差が出る入力を並べた記録を 1 枚置き、両実装を同じ corpus へ当てて
  finding を突き合わせる。緑同士では見えなかった規則差がこれで表になる
- **所有者を 1 ディレクトリ 1 つにする**: 重複を残すと、厳しい方ではなく**両方の和**が作者に
  当たる。#2810 では TPL 本文に block quote の中の fence が書けなくなるのがそれで、
  正しい記述なのに marker でしか回避できなかった
- **移設先は既存の Required job にステップを足す**: 新しい context を増やすと ruleset の更新が
  要り、その反映は merge 順序の制約になる。先例は
  [ADR-2648](../adr/2648-record-source-path-guard.md) 決定 6 と #1480 の
  `adr check-assumptions` で、どちらも path-filter された companion workflow とは別に
  Required な `Check` へ同じコマンドを置いている
- **フラグと配線をテストで固定する**: `scripts/lint/tpl-validate-owns-tpl-dir.test.ts` が
  (1) 退役させた実装が当該ディレクトリを走査しないこと、(2) 有効化フラグが script に
  残っていること、(3) 両 Required job がそのコマンドを実行すること、
  (4) 退役させた workflow が存在しないことを assert する。どれも「消えても緑」な種類の
  regression なので、機械で固定しないと次の編集で静かに戻る
- **記法の互換は corpus で確かめる**: 移設先の実装に既存 corpus の宣言をそのまま読ませ、
  finding が増えないことを見る。#2810 では marker の綴りを上流と同一に保つ設計が
  先にあったので、corpus の 5 件の宣言が両実装で同じ意味になった

## 由来

[#2810](https://github.com/kompiro/karasu/issues/2810)。`@kompiro/tpl-tools` v0.0.10 が、
karasu の `scripts/lint/record-source-paths.ts`（[ADR-2648](../adr/2648-record-source-path-guard.md)）が
先に実装した本文ソースパス照合を `tpl validate --source-prefix` として出荷した。ADR-2648 決定 5 が
予定していた上流化なので、`docs/test-perspectives` の所有者を上流へ移す判断そのものは
既定路線だった。

判断を変えたのは、Issue が書いていなかった 2 つの事実である。第 1 に、2 実装は**既に乖離して
いた** — 現行 corpus では両方 0 件なのに、差分 fixture に当てると双方向に規則差が出て、
しかも 2 件はローカル側の読み違いだった。第 2 に、ローカル実装は Required な `Check` から
走っていたのに対し、移設先候補の `tpl-validate.yml` は job 名が `TPL validate` で Required では
なく、ファイル自身が "Still informative-only — not a required check yet" と書いていた。Issue の
記述どおりに走査対象を絞るだけでは、検査は Required から外れ、かつコード PR では一切
走らなくなる — [ADR-2648](../adr/2648-record-source-path-guard.md) の発端になった #2604 と
同じ形の変更が、また黙って通る状態に戻っていた。

どちらも「実装を消す差分」を読んでいるだけでは見えず、測って初めて出てきた。

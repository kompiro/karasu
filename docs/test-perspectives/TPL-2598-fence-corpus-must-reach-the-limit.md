# TPL-2598: 計測柵は、その資源の限界に達する入力を corpus に持って初めて柵になる

## 観点

「メトリクスが 0 であること」を assert する柵を見るとき、**メトリクスの正しさ**と**入力が限界に達しているか**を分けて確認する。両者は独立で、後者が欠けた柵は green のまま何も守らない。

有限の資源を分け合う実装（1 本の通路を N 本のエッジが使う、1 つの帯を N 個のラベルが分ける）では、**要求数が小さいうちは劣化が観測できない**。N が小さければ分け前が十分に大きく、どの指標も 0 のままになる。破綻するのは N がある閾値を超えたときで、そこに達する入力が corpus に無ければ、柵は「まだ壊れていない入力しか見ていない」だけになる。

したがって corpus には、**その資源を意図的に飽和させる入力**を 1 件は置く。実モデル（examples）は現実的だが、多くは規模が小さく飽和しない。飽和は合成フィクスチャで作るほうが確実で、かつ決定的に再現できる。

## 想定される失敗モード

- **柵が green のまま症状だけが報告される。** 実装者は「柵があるから直っているはず」と考え、報告された画面を疑う。原因究明が遅れる。
- **修正後、柵が「効いた」と誤認する。** 元から検出していなかった柵は、修正前後でどちらも 0 を返す。修正前に落ちることを確認していない柵は、その修正について何も証明していない。
- **劣化がスケールに比例して静かに進む。** N の増加に対して分け前が `band / N` のように縮む実装では、破綻が「ある日突然」ではなく連続的に進むため、閾値をまたいだ瞬間を誰も観測しない。

実例（#2598）: `routing-parity.test.ts` は 12 の実モデルで水平方向の collinear overlap 0 を assert し、main で green だった。しかし同じ関数を 10,000 行規模の外部モデルに当てると 989 件を検出した。メトリクスは正しく、corpus のどのモデルも 1 つのチャネルを混雑させていなかっただけだった。合成フィクスチャ（service 10 → database 3、30 エッジ）を足すと main で 109 件を検出する。

## チェックリスト

新しい柵を足すとき / 既存の柵に依存して「直っている」と判断するときに確認する:

- [ ] その柵が守る資源は有限か。有限なら、**要求数を飽和させる入力**が corpus にあるか
- [ ] 追加した柵は**修正前のツリーで落ちる**ことを確認したか（落ちない柵はその修正を何も証明しない）
- [ ] 飽和入力は合成フィクスチャで決定的に作れるか（実モデル頼みにしない。外部モデル頼みにはしない）
- [ ] 劣化が連続的に進む形（`band / N`・`budget / N`）になっていないか。なっているなら、閾値ではなく**単調に破綻しない形**（固定ピッチ・容量予約）へ変える

## 既知の対処パターン

- **飽和フィクスチャを corpus に足す。** 実モデルの corpus はそのまま残し、資源を飽和させる合成モデルを 1 件加える。既存のメトリクス関数をそのまま使い、新しい測り方は増やさない（測り方が増えると、どれが gate なのかが曖昧になる — TPL-2446）。
- **分け前が N に反比例する形を疑う。** 固定量を N 分割する実装は、N が大きいところで必ず視認不能になる。固定ピッチ + 必要量の事前確保に置き換える。

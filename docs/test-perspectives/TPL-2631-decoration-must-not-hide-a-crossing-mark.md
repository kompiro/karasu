# TPL-2631: 図に装飾を足したら、既存のマークがその上でまだ読めることを測る（覆われたマークは反対の意味に読まれる）

## 観点

> 起源は 2 つある。**#2631**: 出荷済みの bug ではなく、設計中に spike で観測した失敗。ADR-1859 の
> 「交差は表現で無害化する」という決定に対して、本設計が足す装飾が違反しうると分かったため
> 設計と同じ PR で起こした（proactive）。**#2884**: その proactive な観点を実装した #2883 で、
> 装飾に追従させた寸法が描画に届いておらず、この観点が禁じている読み違いがそのまま出荷された
> （retrospective）。下の失敗モード「assert が描画ではなくモデルを測っている」がその学習で、
> proactive に書いた観点でも、**柵の置き場所を間違えれば防げない**ことの実例になっている
> （`docs/test-perspectives/README.md` 「TPL のライフサイクル」「起源と運用ルールは独立」）。

図の可読性を上げる装飾を足すとき、**その装飾が既存のマークを覆っていないか**を、見た目の印象ではなく寸法で確認する。

karasu の交差マークは「交差＝接続ではない」を明示するために存在する（ADR-1859）。このマークが見えなくなると、単に情報が減るのではなく、**反対の意味（接続している）に読まれる**。同じことは合流マーク（接続を肯定する dot / tip）にも言える。マークが意味を否定・肯定している描画では、マークの消失は中立ではない。

危険なのは 2 つの形で、どちらも「装飾は別のパスが描く」ことから来る。

1. **装飾がマークより大きい。** マークの寸法が定数で、装飾の寸法が入力の量に比例するとき、量が増えたところでだけマークが埋もれる。小さいモデルでは再現しない。
2. **装飾とマークが同じ場所を取り合う。** 意味の違う 2 つの記号が同じ点に置かれると、後に描いたほうが勝つ。どちらが勝つかは描画順という、意味と無関係な理由で決まる。

実例（#2631）: 集約トランクの spine を「運んでいる本数」に比例して太く描く装飾を入れたところ、帯幅は `1 + min(本数 - 1, 8) x 3` px になった。交差アーチの立ち上がりは定数 4px（#2884 で 6px に上げた。帯幅が本数で伸びる以上、定数である限りこの構造は変わらない）なので、**本数 4 以上（帯 10px）でアーチが帯の内側に入り、7 本（19px）では完全に消えた**。その spine を横切る線は「帯に合流している」ように読める。さらに、本数を示す tip が交差点とほぼ同じ高さに来ると、**交差＝非接続のアーチが合流＝接続のマークに覆われた**。同じカードから trunk stub と外向き stub が出ると y が数十 px しか違わないため、これは構造的に起きる。

## 想定される失敗モード

- **交差が接続に読まれる。** 図としては破綻していないので、レビューでもスクリーンショットでも気付かれない。読者が誤った依存関係を信じたまま設計判断をする。
- **小さいモデルでは再現しない。** 装飾の寸法が量に比例する場合、example や unit fixture では装飾が小さく、マークが埋もれない。最混雑の実モデルでだけ起きる（TPL-2598 と同じ構造）。
- **描画順の偶然に依存する。** 「今は装飾のほうが下に描かれているから大丈夫」は、レイヤーの並べ替え 1 回で壊れる前提であり、テストが無ければ壊れたことも分からない。
- **assert が描画ではなくモデルを測っている。** マークを装飾に追従させる実装（下の対処パターン 1 つめ）は、レイアウトが計算した寸法をマークに載せ、renderer がそれを読んで描く、という 2 段になる。assert をマーク側の値に置くと、**renderer がその値を使っていなくても緑になる**。#2884 で実際に起きた: `HopMark.ry` に帯の半幅 + 余白を載せる実装は入り、「アーチの高さ > 帯の半幅」の assert も入ったが、renderer は定数の `HOP_RADIUS` を全アーチの `ry` として書き続けていた。帯幅 8.5px の上でアーチは 6px のまま描かれ、この観点がまさに防ぎたい読み違いが、それを防ぐための緑の柵の下で出荷された（TPL-2803 と同じ「測った値と描いた値は同じものか」）。

## チェックリスト

既存の描画の上に装飾を足すとき / 装飾の寸法を変えるときに確認する:

- [ ] その装飾が重なる範囲に、**意味を持つマーク**（交差 / 合流 / 診断バッジ）が存在しうるか
- [ ] 装飾の寸法は入力の量で変わるか。変わるなら、**量が最大のときにマークが読めるか**を測ったか
- [ ] マークと装飾が同じ点を取りうるか。取りうるなら、どちらを優先するかを**描画順ではなく明示的な規則**で決めたか
- [ ] 「マークが装飾の外へ出ている」ことを数値で assert できるか（アーチの高さ > 帯の半幅、など）
- [ ] その assert は**描画出力から読んだ値**か。レイアウトが計算してマークに載せた値を assert すると、renderer がそれを使っていない場合に緑のまま通る。マーク側の assert を置くなら、同じ主張を描画出力側にも 1 本置く（TPL-2803）
- [ ] その assert は、装飾を入れる前のツリーでは意味を持ち、装飾だけを入れたツリーでは落ちるか

## 既知の対処パターン

- **マークを装飾の寸法に追従させる。** 装飾に載るマークだけ、装飾の半幅 + 余白まで広げ・高くする。マークの位置も、どのセグメントに載せるかの規則も変えない（変えると交差の位置自体が動いてしまう）。
- **同じ点を取り合う 2 つの記号には、ずらす規則を持たせる。** #2631 では本数 tip を spine 上でずらして交差アーチを避ける。避ける側は「意味を否定しているほう（交差）」ではなく「肯定しているほう」にする。交差が読めないことのほうが害が大きい。
- **装飾の側を途切れさせる案も検討する。** 帯にギャップを空けてマークを通す形もありうる。どちらを採るにせよ、選んだ理由を記録する。

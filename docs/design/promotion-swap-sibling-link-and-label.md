- **日付**: 2026-11-12
- **ステータス**: 検討中
- **関連**:
  - 引き金 Issue: [#3620](https://github.com/kompiro/karasu/issues/3620)
  - 関連 ADR: [ADR-2331](../adr/2331-adr-automerge-scope.md)（昇格 PR の例外を差分の性質で判定する）、[ADR-3286](../adr/3286-risk-based-review-tiers.md)（段階の分類器。張り替えではリンクの文字列をファイル名・パス・`ADR-<n>` の言い換えに限る）、[ADR-3405](../adr/3405-promotion-adds-adr-link.md)（AT に ADR へのリンクを足す差分。許す形を文法で決め打ちにした）
  - 関連 TPL: [TPL-3286](../test-perspectives/TPL-3286-merge-eligibility-judged-on-final-diff.md)（人間を通らないマージを許す判定は、許す形と位置を決め打ちにし、当たらない入力を厳しい側に倒す）、[TPL-2287](../test-perspectives/TPL-2287-detector-near-misses-are-the-spec.md)（検出器の境界の外側をテストで固定する）

## 背景・課題

Design Doc を ADR に昇格させる PR は、新しい ADR の追加・Design Doc の削除・その Design Doc を指していた参照の張り替えだけなら Low になり、auto-merge される（`.claude/rules/adr.md`「ADR PR の auto-merge」）。張り替えを判定するのは `isLinkSwap` で、変えてよいのはリンク先と、リンクの文字列のうちファイル名・パス・`ADR-<n>` の言い換えだけである（ADR-3286）。

ADR-3038 の昇格 PR #3621 は、この条件から外れて Design になった。ADR の追加と Design Doc の削除のほかの変更は `docs/design/tpl-changed-files-recall.md` の 2 行だけだった。

```diff
-  - 関連 Design Doc: [`tpl-enforcement-status.md`](tpl-enforcement-status.md)（#3038。D5 で本件を分けた）
+  - 関連 ADR: [ADR-3038](../adr/3038-tpl-enforcement-status.md)（#3038。D5 で本件を分けた）
-TPL を結ぶ鍵が無いので、設計を分けた（`tpl-enforcement-status.md` の D5）。
+TPL を結ぶ鍵が無いので、設計を分けた（ADR-3038 の D5）。
```

外れた理由は 3 つある。

1. **隣の Design Doc への参照を認識しない。** `referenceSource` は参照を `(?:\.\.?/)*(?:docs/)?design/<file>` の形でしか認識しない。`docs/design/` の中のファイルは、隣の Design Doc をディレクトリなしの名前（`tpl-enforcement-status.md`）で指すので、どちらの行も参照を含まないと読まれる
2. **ラベルの言い換えを許さない。** 1 行目は、リンクと一緒に行の先頭のラベルが `関連 Design Doc` から `関連 ADR` に変わっている。リンク先が Design Doc から ADR に変わる以上、ラベルを直すのは張り替えの一部だが、今の規則ではリンクの外の文字は 1 文字も変えられない
3. **コードスパンの名前を `ADR-<n>` に言い換えられない。** 2 行目は、コードスパンに入れた Design Doc の名前を、地の文の `ADR-3038` に書き換えている。`ADR-<n>` への言い換えはリンクの文字列にしか許されておらず、パスではない `ADR-3038` は新しい参照とも読まれない

1 行目は 1 と 2、2 行目は 1 と 3 が同時に起きているので、どれか 1 つだけ直しても #3621 は Low にならない。

同じ形の昇格は以前にもあった。ADR-2922 の昇格 PR #3352（分類器の導入前）は、`docs/design/vscode-pre-release-channel.md` の 1 行で隣へのリンクとラベルを変え、同時に注記を `（月次トレイン。ADR 昇格待ち）` から `（月次トレイン）` に書き換えた。注記の書き換えは文の変更なので、本設計でも Low にはしない。

## 現状（インベントリ）

| 観点 | 現状 |
| --- | --- |
| 参照の形 | `referenceSource(paths)` が、各パスを `(?:\.\.?/)*(?:docs/)?<dir>/<file>(?:#anchor)?` にする。ディレクトリの無い形は無い |
| 張り替えの判定 | `isLinkSwap(removed, added, deletedDesigns, newAdrs)` が、削除行が旧参照を、追加行が新参照を含むことを確かめ、両方の行で、旧参照か新参照を指すリンク（リンク先の全体が参照のもの。リンクの文字列がファイル名・パス・`ADR-<n>` ならそれも）と、地の文やコードスパンの中にあるディレクトリ付きのパスを同じ記号に置き換え、残りが一致するかを比べる。どのファイルの行かは受け取らない |
| 呼び出し | `fileTier` が、新しい ADR を足す PR の `.md` の変更ファイルについて、hunk の削除行と追加行を順に対にして `isLinkSwap` に渡す。ファイルのすべての hunk が張り替えでなければ Low にしない。High のパスはこの前に High に決まり、張り替えでも下がらない |
| Design Doc のパス | `DESIGN_DOC = /^docs\/design\/[^/]+\.md$/`。`docs/design/` の直下だけ（今の `docs/design/` にサブディレクトリは無い） |
| 隣を名前だけで指す Design Doc | 今の `docs/design/` では `diff-resolver-warnings.md` の 2 か所（`./diagnostic-source-file-identity.md`）。9 行目は `- 関連 Design Doc:` のラベルを持ち、その Design Doc が昇格すれば D1 と D2 の実例になる |
| 名前だけで Design Doc 以外を指す記述 | `docs/design/low-pr-merger-workflow.md` の `` `adr.md` ``・`` `review.md` ``（`.claude/rules/adr.md` と `docs/process/review.md` の意味）。`docs/design/` の中でも、名前だけの記述が隣の Design Doc とは限らない |
| ラベルの形 | 字下げした `- 関連 Design Doc:`（#3621・#3352 の差分の 2 件）と、太字の `- **関連 Design Doc**:`（今の AT に 12 件） |

## 制約・前提

- 人間を通らないマージを許す例外を広げるので、許す変更の形と位置を決め打ちにする。差分から許す部分を削って残りを比べる形は ADR-3405 で問題が見つかった（削る規則の隙から意味のある変更が入る）。広げる部分は、決まった語を決まった位置でだけ同じものとして扱い、それ以外の文字はすべて一致を求める（TPL-3286）
- ディレクトリの無い名前は、`docs/design/` の外では Design Doc を指さない。`docs/acceptance/` の `foo.md` は `docs/acceptance/foo.md` であり、そこで名前だけの一致を参照と読むと、関係の無い記述を張り替えと誤認する。`docs/design/` の中でも、名前だけの記述が Design Doc 以外を指すことがある（`` `adr.md` ``）。そこで名前だけの形は、リンク先とコードスパンの中身全体に限って認識し、地の文の語は認識しない。削除された Design Doc と同じ名前の別ファイルをコードスパンで指した行は張り替えと誤認しうるが、名前が削除されたファイルとちょうど一致し、かつ追加行が新しい ADR を指していなければならないので、この残りは受け入れる
- High のパスは張り替えでも High のまま、という線は変えない
- Design Doc の書き方（隣をどう指すか、本文で何と呼ぶか）は変えない。今ある書き方のまま昇格できるようにする

## 検討した選択肢

### 案 1: 隣への参照だけを認識する（Issue の Expected）

変更されたファイルが `docs/design/` の直下にあるときだけ、削除された Design Doc を `<file>` と `./<file>` でも参照として認識する。

**メリット**

- 規則の文面を変えずに済む（「その Design Doc を指していた参照」はもともと形を問わない）

**デメリット**

- #3621 は、どちらの行も参照の認識のほかにもう 1 つ変更を含むので Low にならない。Low にするには、ADR を Design Doc と呼ぶラベルや、ADR をパスで呼ぶ本文を残すしかなく、記録の読みやすさを分類器に合わせることになる

### 案 2: 案 1 に加え、ラベルと番号での言い換えを決め打ちで許す（採用）

案 1 に加え、昇格で自然に起きる 2 つの言い換えを、形と位置を決めて許す。張り替える行のラベル `関連 Design Doc` → `関連 ADR` と、Design Doc の名前だけを入れたコードスパン → その ADR の `ADR-<n>` である。

**メリット**

- #3621 が Low になる。注記の文を変えた #3352 は Low にならない
- 許す変更を固定の語と固定の位置に決め打ちにするので、ラベルの位置やコードスパンの位置に任意の文を入れたり、別の行を変えたりはできない

**デメリット**

- 規則（ADR-3286 と `.claude/rules/adr.md`）を広げる。広げたぶんのテストが要る

### 案 3: 張り替える行では、どんなラベルや言い換えも許す

**メリット**

- `設計 (Design Doc)` のような別のラベルや、「旧設計」のような別の呼び方にも効く

**デメリット**

- ラベルや呼び名の位置に任意の語を書ける。`- **承認済み**:` のように、行の意味を変えるラベルも人間を通らずに入る（ADR-3405 の実装 PR のレビューで、任意の太字ラベルの行を足せることが問題になった）。観測した形は `関連 Design Doc` とコードスパンの名前だけなので、それより広げる根拠が無い

### 案 4: 書き方の規則で避ける

隣の Design Doc も `../design/<file>` で指し、昇格時はラベルや呼び名を変えない、と Design Doc の書き方に決める。

**メリット**

- 分類器を変えない

**デメリット**

- ラベルや呼び名を変えない規則は、ADR を Design Doc と呼ぶ行やパスで呼ぶ本文を残させる。書き方の規則が守られなかったときに例外が届かない、という形も TPL-3286 が挙げる失敗モード（AT が Issue を指すようになって例外が届かなくなった #3405）と同じで、規則を足すほど起きやすくなる

## 現時点の方針

**案 2 を採用する。** 昇格 PR が実際に作る差分（隣へのリンク、それに合わせたラベル、本文での呼び名）を、許す形を決め打ちにしたまま Low に数える。案 1 では観測した #3621 に届かず、案 3 は観測していない形まで人間を通らずに通す。

決めること（どれも、行が張り替えの行であること、つまり削除行が削除された Design Doc を、追加行が新しい ADR を指していることが前提で、ほかの文字はすべて一致しなければならない）:

- **D1: 隣への参照。** 変更されたファイルが `docs/design/` の直下にある（`DESIGN_DOC` に当たる）ときだけ、削除された Design Doc の `<file>` と `./<file>`（anchor 付きも）を参照として認識する。認識するのは、markdown リンクのリンク先の全体と、コードスパンの中身の全体だけで、地の文の語やコードスパンの一部（`` `cat <file>` ``）は認識しない。`../`・`docs/` で始まる形は今までどおり。ほかのディレクトリのファイルでは名前だけの形を認識しない。削除されていない隣の Design Doc の名前は、今までどおり参照にならない
- **D2: ラベル。** 削除行の先頭が `関連 Design Doc` のラベルで、追加行の同じ位置が `関連 ADR` のとき、その 2 語だけを同じものとして比べる。ラベルの形は、字下げ（空白だけ）の後の `- `、任意の `**`、ラベル、同じ `**`、`:` か `：` で、ラベルの外の文字（字下げ・`- `・太字の記号・コロンの種類）は削除行と追加行で一致しなければならない。逆向き（`関連 ADR` → `関連 Design Doc`）とほかの語の組は許さない。追加行に Design Doc への参照が残っていれば当たらない。この判定は外す方向にしか働かないので、広めに数える。`design/` を含むパスは、リンク先・コードスパン・地の文のどこにあっても数える。`docs/design/` の直下のファイルでは、ディレクトリを持たない `<name>.md`・`./<name>.md`（anchor 付きも）も、削除されたものに限らず、地の文を含めて行のどこにあっても数える。項目の続きの行や子リストは見ない
- **D3: 番号での呼び名。** 追加行の地の文にある `ADR-<n>` を、コードスパンに入った参照と同じものとして比べる。対象は、リンクの外にもコードスパンの外にもあり、前後がパスの境界と同じ条件（前が英数字・`.`・`/`・`:`・`-` でなく、後ろが英数字・`-` や、`.` に続く英数字でない）を満たす `ADR-<n>` で、`<n>` はファイル名の語幹が削除された Design Doc のどれかと同じ新しい ADR（`docs/design/<name>.md` に対する `docs/adr/<n>-<name>.md`）の番号に限る。置き換えるのは追加行だけで、削除行の `ADR-<n>` は置き換えない。そのため、削除行の同じ位置に参照だけのコードスパン（D1 の形を含む）があるときだけ一致し、逆向きの変更や同じ行の中での入れ替えは不一致になる。`ADR-120` の中の `ADR-12`、`/ADR-12`・`ADR-12.md` のような URL やパスの一部、コードスパンに入ったままの `` `ADR-12` ``、リンクの文字列の中の `ADR-<n>` は当たらない。削除行のコードスパンが anchor 付きでも当たる（参照先の記録は同じ）
- **置き換えの順番。** 比べる前に、両方の行に次の順で置き換えをかけ、残りを比べる。リンクを先に扱うのは、リンクの文字列に入ったコードスパン（#3621 の 1 行目の `` [`tpl-enforcement-status.md`](…) ``）をリンクの規則で扱い、D3 に渡さないためである
  1. 行の先頭のラベル（D2。削除行の `関連 Design Doc` と追加行の `関連 ADR` だけ）
  2. markdown のリンク（今の規則。リンク先の全体が旧参照か新参照なら、D1 の形を含めて置き換える）
  3. リンクの外のコードスパンのうち、中身の全体が旧参照か新参照のもの（D1 の形を含む）を `` `⟦ref⟧` `` にする
  4. 追加行だけ、D3 の `ADR-<n>` を `` `⟦ref⟧` `` にする
  5. 残りのテキストのディレクトリ付きのパス（今の規則。D1 の名前だけの形はここでは認識しない）

### 実装の指針

1. `isLinkSwap` に、変更されたファイルのパスを省略できる引数として渡す（既存のテストの呼び出しは 4 引数のまま動く）。`fileTier` はそのファイルのパスを渡す。`referenceSource` と、地の文のパスを拾う `bare` は変えない。D1 の名前だけの形は、リンク先の全体とコードスパンの中身の全体を照合する別の照合で扱い、パスが `DESIGN_DOC` に当たるときだけ有効にする
2. `normalize` を上の「置き換えの順番」のとおりにする。今の `normalize` は両方の行に同じ置き換えをするが、1 と 4 は削除行と追加行で別のものを置き換える。張り替えの行の前提（削除行が旧参照を、追加行が新参照を含む）の判定でも、D1 の形を旧参照として、D3 の `ADR-<n>` を新参照として数える。#3621 の 2 行目は、パスもリンクも持たない追加行だからである
3. `scripts/review/tier.test.ts` に足すテスト（TPL-2287。名前だけの形の境界は、認識を広げた `docs/design/` のファイルで試す）:
   - 受け入れる: `docs/design/` のファイルでの `<file>`・`./<file>` のリンク先、コードスパンの `` `<file>` ``、anchor 付き。リンクの文字列がコードスパンの名前のリンク（`` [`<file>`](<file>) `` → `[ADR-12](../adr/12-<file>)`）。既存の `` `docs/design/x.md` `` → `` `docs/adr/12-x.md` `` が引き続き通ること。ラベルの言い換えを、太字あり・なし・字下げあり・全角コロンで。コードスパンの名前やパスの `ADR-<n>` への言い換え（`docs/design/` のファイルと、`` `docs/design/<file>` `` を書いた `docs/roadmap.md` の両方で）。#3621 の 2 行をそのまま使った分類（`classifyChange` で `low`）
   - 拒む（D1。`docs/design/` のファイルで）: 名前が長い別のファイル（`old-<file>`）、別のディレクトリ（`../other/<file>`）、削除されていない隣の Design Doc の名前、地の文に書いた `<file>`、コードスパンの一部の `<file>`（`` `cat <file>` ``・`` `<file> foo` ``）
   - 拒む（D2）: ラベルだけを変えた行。逆向きのラベル。`関連 Design Doc` → `承認済み ADR` などほかの語。行頭でない位置（値の途中や地の文）の `関連 Design Doc`。字下げや `- ` の変化。太字やコロンの種類の変化。張り替えた後も別の Design Doc への参照が残る行（`../design/<other>.md`・`./<other>.md`・`<other>.md#a` のリンク先、`` `<other>.md` `` のコードスパン、地の文の `<other>.md`）でのラベルの言い換え
   - 拒む（D3）: 語幹の合わない ADR の番号。`ADR-120`・`ADR-12a` のように語の一部になった番号。`/ADR-12`・`:ADR-12`・`ADR-12.md`・`ADR-12/x` のように URL やパスの一部になった番号。コードスパンに入ったままの `` `ADR-12` ``。コードスパンの外の名前。リンクの文字列の中の `ADR-<n>`。逆向き（地の文の `ADR-<n>` → コードスパン）。同じ行の中での入れ替え（削除行が `` `<file>` `` と `ADR-<n>` を両方持ち、追加行で位置を交換する）
   - 拒む（ほかの場所で）: `docs/acceptance/` や `docs/roadmap.md` での名前だけの形。リンク先が新しい ADR でない行。High のパスでの同じ張り替え（High のまま）。#3352 の行（注記を変えているので Low にならない）
4. `.claude/rules/adr.md` を上の「仕様の変更」のとおりにする
5. 受け入れテスト（`docs/acceptance/`）は作らない。変わるのは分類器の判定だけでユーザーが観測する挙動が無く、上のテストで確かめる
6. ADR 昇格: 実装 PR のマージ後、`docs/adr/3620-<name>.md` として昇格し、本 Design Doc は同じ PR で削除する

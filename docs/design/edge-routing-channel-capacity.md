## 背景・課題

「エッジが上下に重なる」症状が繰り返し報告され、その都度パスを足して直してきた（#1927 / #1954 / #2477 / #2490）。今回 10,000 行規模の外部モデル（reverse-engineered な dify）で計測したところ、**原因は配線アルゴリズムの精度ではなく段間の欠落**だと分かった。

パイプラインはノード座標を先に確定し、そのあと配線する。層間チャネルの高さは `LAYER_GAP`(120) / `NODE_GAP`(60) という**定数の余り**で、そこを何本のエッジが通るかは配置時点で誰も知らない。結果として 2 つの欠陥が同時に成立していた。

1. **レーンが固定帯の N 分割** — `distributeChannelLanes` は `LANE_BAND = 18px` を `N + 1` 等分する。dify の `Workflow` drill-down では 31 本が 1 チャネルを共有し、レーン間隔は **0.56px**。パスは走って「成功」するが、見た目は完全な重なり。コード側のコメントも `Lane cap: deferred per ADR` と未完了を認めていた。
2. **経路の「形」で選別していた** — 同パスは waypoint がちょうど 2 個のエッジしか対象にしない。実際に重なっていたのはガター経路（waypoint 3〜4 個）の復路水平線で、同 view の 81 本中 57 本がその形。**主犯が最初から対象外**だった。

### なぜ縦は直り、横は直らなかったのか

同じレーン割り当ての発想なのに、空間ポリシーが逆になっている。

| 通路 | 空間の決まり方 | dify での実測 collinear overlap |
| --- | --- | --- |
| 縦（ガター / トランク） | `maxRight + GUTTER_GAP + (lane + 1) × TRUNK_LANE_GAP` — **外側へ無限に伸びる** | 0 |
| 横（層間チャネル） | 定数 `LAYER_GAP` の余り — **固定**、それを N 分割 | 4561 ペア / 5.50 Mpx |

#1927 の縦の修正が効いたのはアルゴリズムが優れていたからではなく、**伸ばせる方向だったから**。横は伸ばせないので、後段パスをいくら足しても 0.56px は 0.56px のまま。

### 柵は存在する。足りないのは corpus

`routing-parity.test.ts` は既に 12 の実モデルに対して `collinearOverlaps(res, "h") === 0` を assert しており、main で green。同じ関数を dify に当てると 989 件を検出するので、**見落としは許容誤差の問題ではなく入力の緩さ**。合成モデル（service 10 → database 3、30 エッジ）で main は 109 件、修正後は 0 件になるため、外部モデルに依存せず repo 内 fixture で柵を張れる。この一般則は [TPL-2598](../test-perspectives/TPL-2598-fence-corpus-must-reach-the-limit.md) として本 PR で起こす。

## 現状（インベントリ）

| 段 | 決めていること | 配線の需要を知っているか |
| --- | --- | --- |
| `computeLayers` | 層割当（kind tier / トポロジカル） | — |
| `placeNodesInLayers` | 層内順序（barycenter）・grid 折り返し・**座標** | **知らない**（gap は定数） |
| `runRoutingChain` | 経路（straight → 内部 channel-L → ガター / mixed → トランク） | 知っている |
| `distributeGutterLanes` / `fanOutGutterPorts` | 縦通路の重なり回避 | 知っている（外へ伸ばせる） |
| `distributeChannelLanes` | 横通路の重なり回避 | 知っているが**置く場所が無い** |

需要が座標へ戻る経路が 1 本も無い、というのが本質。

## 制約・前提

- **決定性は絶対** — 同じ入力 → 同じ SVG。乱数・焼きなまし・収束判定つきの反復は採らない（`docs/concepts.md` Goals、ADR-1737）。
- **viewport 非依存** — CLI は headless でレンダリングするので、画面サイズを入力にしない。
- **diff の局所性** — エッジ 1 本の増減でレイアウト全体が組み替わらないこと。compare/diff モードが直接効く。
- **既存の柵を弱めない** — 貫通 0 / 全交差に hop（TPL-1927・ADR-2330）を維持する。片方だけ良くする直し方は不可。
- 本 doc のスコープは横方向（層間チャネル）の容量のみ。deploy の配線・ガター左右・dummy node は別スライス。

## 検討した選択肢

### 案1: 衝突を見てノードを動かし、衝突が消えるまで再配線を繰り返す

**メリット**

- 直感的。局所的な衝突には確実に効く。

**デメリット**

- **収束保証が無い。** ノードを動かすと別の場所に新しい衝突が生まれる。回数上限を付ければ結果が上限に依存し、「同じ入力 → 同じ SVG」は保てても入力の微小差で出力が大きく飛ぶ。
- **diff の局所性を壊す。** エッジ 1 本の追加が全体の組み替えを誘発しうる。
- **原因に当たっていない。** 今回の重なりは「ノード位置が悪い」ではなく「複数のエッジが予約なしに同じ通路を使う」ことで起きている。ノードを動かしても通路の取り合いは残る。

### 案2: レーンのピッチだけ固定にする

**メリット**

- 変更が 1 ファイルで閉じる。

**デメリット**

- **場所が無いので溢れる。** 実測: ピッチ固定のみを入れた中間状態で、`Knowledge` view の重なりは 989 → 17 ペアに減った一方、**カード貫通が 0 → 113 件に増えた**。レーンが上下の行を突き抜けただけだった。TPL-1927 が両方を測れと言うのはまさにこのため。

### 案3: 資源キー化 + 需要ベースの容量予約（2 パス）

1. **レーン割り当ての対象を資源で定義する** — 「内部 waypoint 間の水平 run で、前後のセグメントが垂直なもの」。経路の形（waypoint 数）は判定に使わない。
2. **レーンは固定ピッチ**。本数で割らない。
3. **需要を測って場所を予約する** — 1 回目の配線が各チャネルに流した本数を数え、その行の直前の gap を `demand × pitch` に広げて**配置からやり直す**。行の単位は層ではなく**行序数**（層内の grid 折り返し sub-row を含む）。

**メリット**

- 重なりが「後で直すもの」ではなく「起き得ないもの」になる。新しい経路形状は登録不要で自動的に参加する（TPL-1954）。
- パス回数は常に 1 か 2。収束判定が無いので決定性と diff の局所性を保てる。定数で足りるモデルでは 2 回目を走らせない。

**デメリット**

- 混雑した view は配置を 2 回走らせる（`compile()` 実測: `Knowledge` 85 → 127 ms、root 32 → 36 ms）。
- チャネルが実体を持つ分キャンバスが伸びる（dify 21 view 合計で +13%）。#2593 の面積最小化（−18%）とおおむね相殺する。

## 比較

| 観点 | 案1 反復 | 案2 ピッチのみ | 案3 資源キー化 + 予約 |
| --- | --- | --- | --- |
| 決定性 | 上限依存 | 保つ | 保つ |
| 収束 | 保証なし | — | 常に 1〜2 パス |
| 重なり（dify 21 view） | 未計測 | 989 → 17（`Knowledge`） | 4561 → 8 ペア |
| 貫通 | 未計測 | **0 → 113 に悪化** | 5 → 5（不変） |
| 新しい経路形状 | 個別対応 | 個別対応 | 自動参加 |
| キャンバス面積 | 不明 | ほぼ不変 | +13% |

## 現時点の方針

**案3 を採用する。** 重なりの根が「資源の取り合いに割り当てが無い」ことなので、割り当てを入れれば構成的に消える。案2 が示したとおり割り当てだけでは場所が無く、場所を作るには配置が需要を知る必要がある。この 1 往復は反復ではなく**測定 → 予約**の 2 段であり、収束の問題を持ち込まない。

### ADR-1859 が却下した「配置レベルで解消」との線引き

ADR-1859 は貫通対策として **「配置レベルで解消（#966 / ADR-967 拡張）」を却下**している。理由は「共有 infra はどこに置いても誰かの直下に来うるので配置だけでは一般に解けない。routing で構成的に解き、配置最適化は #966 に委ねる」。

本設計はこれと矛盾しない。却下されたのは**特定のエッジを避けるためにノードを動かす**アプローチであり、本設計が配置に返すのは**通行量から決まる通路の寸法**だけである。どのエッジがどの経路を取るかは引き続き routing が構成的に決め、配置はその結果に対して場所を用意する。ノードの相対順序・層割当・列は一切変えない（変わるのは行間の gap のみ）。ADR 昇格時にこの線引きを明記する。

同様に ADR-1737 の「決定的な既定レイアウト規則であって自動レイアウト最適化ではない」線からも外れない。予約量は測定した本数 × 定数で、探索も評価関数も持たない。

### TPL-2593（配置へ測定値を返す経路の規律）との突き合わせ

[ADR-2593](../adr/2593-canvas-space-objective.md)（[#2593](https://github.com/kompiro/karasu/issues/2593)）で、配置にフィードバックを足すときの規律が [TPL-2593](../test-perspectives/TPL-2593-layout-feedback-is-floor-first-and-monotone.md) として明文化された。本設計は同じパイプラインに 2 本目のフィードバックを足すので、そのチェックリストに対する立場をここで固定する。

| チェック項目 | 本設計の立場 |
| --- | --- |
| 候補列はモデルと定数だけから決まる | **形が違う。** 本設計は候補を探索せず、予約量を `測定した本数 × 定数ピッチ` で 1 つに決める。測定値は 1 回目のパスの結果から取るので、シグネチャ上は「前回結果」を読む形になる（`channelDemandByRow(result)`）。ただしその結果自体がモデルと定数だけの純関数なので、合成もモデルの純関数であり、viewport・時刻・乱数・セッション間の状態は入らない |
| 同じ入力で 2 回走らせて座標が完全一致 | 満たす。テストを置く |
| 現行定数が先頭で、厳密比較のみが勝つ | **等価な形で満たす。** 探索が無いので「先頭候補」は無いが、`extraChannelGap()` は需要が現行 gap に収まるとき 0 を返し、その場合 2 回目のパス自体を走らせない。定数で足りる入力は座標が完全一致する。閾値をこの形に置く根拠は後述（ADR-2593 の取り込み 2） |
| 採点は呼び出し元が使う寸法 | 該当なし（採点関数を持たない）。ただし予約対象の行序数は最終座標から導く |
| 試行が純粋 | 満たす。1 回目の結果は破棄し、2 回目は `layoutInner` を新しい Map で走らせる |
| 打ち切りは単調性で説明できる | **より強い形で満たす。** 単調性ではなく構成で上限が決まる — パスは常に 1 か 2 で、3 回目は存在しない。「2 回目の配置で経路選択が変わりうる」ことは事実であり、不動点は保証しない。上限の明示であることを ADR に残す |
| 退化入力で結果が返る | 満たす。エッジ 0 / チャネル 0 は 1 パスで終わる |
| 並列に存在する全レイアウト経路が同じ規則を通る（TPL-219） | **スライス A では満たさない。** 複数 system の root view は system ごとに独立した行スタックを横に並べるため、キャンバス全体で一意な行序数が定義できない。A では単一 system / 全 drill-down のみを対象とし、multi-system root は現状維持（既定 gap のまま）とする。この縮退は親 Issue の `## Slice status` に記載する |

### ADR-2593 が実装で覆した点の取り込み

TPL-2593 の元になった設計 doc には無く、**実装とレビューで判明して方針が変わった**点が
ADR-2593「実装で設計を覆した点」に 3 件残っている。うち 2 件は同じパイプラインに 2 本目の
フィードバックを足す本設計に直接効くので、依存する前提として明記する。

1. **配置は予算に対して単調ではない。** 行の高さはその行で最も高いカードで決まるため、
   行幅予算を広げると再折り返しで総高が増えることがある（ADR-2593 実測: 不揃いカード 7 枚で
   1430 → 1492）。単調性を根拠にした早期打ち切りは削除された。本設計はこれを 2 つの形で受ける。
   - **打ち切りの根拠に単調性を使わない。** パス数の上限は構成で決まっており（常に 1 か 2）、
     「広げれば必ず良くなる」という仮定は置かない。上の表の該当行と同じ立場。
   - **2 回目の配置が行構造を変えないことに依存する。** 需要は行序数をキーに測る。ところが
     `layout()` は `layoutInner` を候補予算で回す `searchWidthBudget` の外側にあり
     （`packages/core/src/renderer/layout.ts`）、採点は**最終キャンバスの幅と高さ**である。
     予約で高さが伸びれば勝つ候補が変わりうるし、単調でない以上その向きは予測できない。
     勝つ候補が変われば折り返しが変わり、キーの指す行がずれる。よって A は
     **1 回目で選ばれた `widthBudget` を固定して 2 回目へ渡し、探索を再実行しない**。
     1 回目と 2 回目で `LayoutResult.widthBudget` と各行のメンバーが一致することをテストで押さえる。
2. **予約には閾値が要る。** ADR-2593 は deploy の unit grid を「2 個以上」で畳んで既存 6 図を
   すべて大きくし（最大 +29%、1 件は帯の外）、閾値を「4 個以上」に上げて既存 20 view を
   完全に不変へ戻した。`extraChannelGap()` も同じ性質を持つ資源で、需要が現行 gap に収まる
   チャネルにまで予約を足せば、直す必要の無かった図まで伸びる。閾値は
   「**現行 gap に収まるなら 0**」に置き、既定 gap で足りる view の出力が 1 バイトも
   変わらないことを柵にする（ADR-2593 の floor-first に対応する形）。

3 件目（同面積のタイブレークを入れない）は候補を採点しない本設計には対応物が無い。

**2 回目の配置を走らせたあとに成り立っていること**（スライス A の受け入れ条件）:

| 条件 | 測り方 |
| --- | --- |
| 貫通 0 | `totalPenetrations(res) === 0`。案2 が 0 → 113 に壊した側なので、水平の重なりと必ず同じテストで測る（TPL-1927） |
| 水平 collinear overlap 0 | `collinearOverlaps(res, "h") === 0`。混雑 fixture が修正前に落ちることを先に確認してから固定する（TPL-2598） |
| 縦 collinear overlap は現状維持 | `collinearOverlaps(res, "v")` は既存 corpus で green のまま。A はこれを改善しないし、悪化もさせない |
| 既定 gap で足りる入力は不変 | 2 回目を走らせず、座標が 1 回目と完全一致する |
| 決定性 | 同じ入力を 2 回 layout して座標が完全一致する |

### スライス（実装ステップ）

| スライス | 前提 | 独立に出荷できる理由 |
| --- | --- | --- |
| **A** チャネル容量 + レーン資源化（[#2608](https://github.com/kompiro/karasu/issues/2608)） | — | 横方向の重なりだけで閉じており、他 3 つはいずれも A の有無に関わらず現状維持で動く。A 単体で張る柵は**横方向チャネルに閉じる**（貫通 0 と水平 collinear overlap 0）。縦方向は `routing-parity.test.ts` の `collinearOverlaps(res, "v") === 0` が既存 corpus で既に green であり、A はそれを弱めないことだけを負う（未解決の問いに挙げた `usecase → resource` の既存縦 overlap は A の対象外） |

## 未解決の問い

- ピッチの値（spike では 14px）。エッジラベルの高さと `LAYER_GAP` の既定値との兼ね合いで決める。ラベル衝突は ADR-2048 の担当なので、本設計は線の分離のみを保証する。
- 予約は「1 回目に実際に流れた本数」を使うが、2 回目の配置で座標が変われば経路選択も変わりうる。実測では dify 全 view で 2 回目の結果が悪化しなかったが、**3 回目を走らせない**という決定は上限の明示であって不動点の保証ではない。ADR にその旨を残す。
- `usecase → resource` の drill-down に既存の縦方向 overlap 1 件を発見した（main / spike とも）。本スライスの対象外。柵の corpus に入れると落ちるため、別 Issue で扱う。
- multi-system root view をいつ対象にするか。行序数が定義できないので、system ごとに独立した予約を行う（各 system 内で行を数える）か、A の縮退のまま据え置くかを B/D の設計時に再検討する。

## 背景・課題

#3036 は、行の中の 2 枚のカードの間隔（既定 60 px、icon mode では 36 px）が、そこを通るエッジの本数に
関係なく一定であることを問題にした。行の上下の間隔は ADR-2598 で通行量に応じて広がるが、行の中は
広がらない。さらに、レーンは線 1 本ぶん（`LANE_PITCH = 14 px`）の幅しかなく、高さ約 15 px・幅最大
317 px のラベルはどちらの軸にも収まらない。`label-display: auto`（ADR-3022）では、密な fixture
（`packages/core/src/renderer/fixtures/dense-domain-canvas.krs` の `UmamiApp`）で 41 本中 13 本しか
ラベルが置けなかった（Issue を書いた時点の数字。今の `main` では 17 本。下の「密な fixture の今の数字」）。

Issue の受け入れ条件は 3 つある。

1. 行内の隙間について、何を需要と数えるか、ラベル付きのエッジが無いエッジより多くを求めるかを決める
2. 密な fixture で混んだ隙間が開き、空いた隙間は開かない。`auto` で置けたラベルの数を前後で示す
3. 隙間が既に通行量を賄っている `examples/` の図はバイト同一

本 Design Doc の答えは「行内の隙間の需要は、そこに既定のアンカーを持つ置けなかったラベルの幅。線の本数は
需要にしない。行間のチャネルも同じく置けなかったラベルの高さで開く。どちらを開くかは、開いた配置で置けない
ラベルが実際に減るかで選ぶ」である。面積の増加は問題にしない（maintainer の判断）。

## 制約・前提

- **floor-first**（ADR-2593 / TPL-2593）: 既定の配置でラベルが置けている図は 1 バイトも変えない
- **候補は入力だけで決まり、既定が先頭で、厳密改善のみが勝つ**（TPL-2593）: 配置をやり直すなら、試す配置は
  モデルと定数から決まる有限の集合で、`main` が返す配置より厳密に良いときだけ置き換える。収束判定のループは
  置かない
- **鍵は構造キー**（TPL-2611）: 予約の適用先は行序数・カード id で持ち、座標で持たない
- **測る判定と描く判定は同じ関数**（TPL-219）: 置けなかったラベルを数えるのは、renderer が描くときに使う
  ラベル配置パスそのものでなければならない
- **ADR-2048 の却下との線引き**: ADR-2048 は「レイアウトでノードを離してラベル空間を作る」を「影響範囲が
  全レイアウト・全 snapshot に及び、cosmetic 修正には過大」として却下した。本件は、置けなかったラベルが
  ある図の、そのラベルがある場所だけを開き、開いた配置で置けないラベルが減るときだけ採る。置けている図は
  変わらない（下の計測で `examples/` 85 本がバイト同一）
- **面積は制約にしない**: 大きい canvas は縮小表示され文字が小さくなる（TPL-1223）が、置けるラベルが
  増えるならその代償は受け入れる（maintainer の判断、#3036）
- **範囲外**: 複数 system の root view（ADR-2598 の決定 4）と deploy view（ADR-2598 の「残る限界」）は
  ADR-2598 の時点で予約しない。本件もそれに従う

## 検討した選択肢

コーパスは密な fixture（`UmamiApp`）、dify（405 view・ラベル 296 本）、WordPress（1,031 view・ラベル
258 本）。dify と WordPress は repo の外にある reverse 済みのモデルで、ADR-2598 / ADR-2611 の計測と同じもの。

計測は 3 段階で行った。

- **試作 1**: 案1・案2・案4 の方向を比べた粗い版。全エッジに既定の style（`auto`・11 px・48 文字）を当て、
  frame の境界を渡さず、相互ペアを分けずに測った
- **試作 2**: 案3 を「決定の中身」の測り方（renderer のラベル配置パスを callback で受け取り、相互ペアを
  分けた後で測る）で測った
- **spike**（`spike/3036-row-and-channel-label-room`）: 試作 2 の測り方に案2 を加え、案5 の候補選択を
  実装した。案3・案2 + 案3・案5 の数字はこれで測った

### 案1: 行内の隙間を、通る線の本数で開く（Issue の提案そのまま）

隙間を縦に通る run の最大同時数 × レーン幅が隙間の幅を超えたら、超えた分だけ開く。

- 今の `main` では需要が出ない。密な fixture の行内の隙間を通る線は 1〜2 本で、60 px に収まっている。
  線のための列は ADR-2611 が既に開いている（外側のガターへ出た分だけ）
- ラベルの問題に効かない。置けないラベルの原因は線の本数ではない

### 案2: 行内の隙間を、置けなかったラベルの幅で開く（単独、比較なし）

置けなかったラベルのうち既定のアンカーが行内の隙間にあるものの幅（+ 余白 8 px × 2）まで、その隙間を開く。
試作 1 で測った。

| | 密な fixture | dify | WordPress |
| --- | --- | --- | --- |
| `main` | 17 / 41 | 206 / 296 | 156 / 258 |
| 案2 | 23 / 41 | **204** / 296 | **120** / 258 |

- **実モデルで置けるラベルが減る。** WordPress の `WordPressApp` で 110 → 76、`WpDB` で 32 → 30、dify の
  `DifyDB` で 206 → 204
- 減る仕組み: 隙間を広げると、外側のガターを回っていたエッジが内部の回廊（ADR-2611 の到達性）としてその
  隙間に入ってくる。`WordPressApp` では、ガターの水平の run に乗るラベルが 31 → 12 本に減り、行内の隙間に
  乗るラベルが 12 → 25 本に増え、そのうち置けないものが 5 → 17 本になった。開けた空間を、測った需要とは
  別の種類の利用者（経路）が使う（[TPL-3036](../test-perspectives/TPL-3036-reserved-room-kept-only-when-measured.md)）
- ただし密な fixture のように効く図もある。問題は開くこと自体ではなく、効いたかを確かめずに採ること

### 案3: 行間のチャネルを、置けなかったラベルの高さで開く（単独）

置けなかったラベルのうち既定のアンカーが行間のチャネル（frame で区切られた最初と最後のチャネルを含む）に
あるものについて、どの x でもそこに重なるラベルの高さの合計の最大値を、そのチャネルのラベルの需要とする。
ADR-2598 のレーンの需要と合算し、既定の間隔を超えた分だけその行の直前を広げる。

| | 密な fixture | dify | WordPress |
| --- | --- | --- | --- |
| `main` | 17 / 41 | 206 / 296 | 156 / 258 |
| 案3 | 21 / 41 | 216 / 296 | 186 / 258 |

- 計測したどの view でも減らない。チャネルの高さは、縦に抜けられる回廊の候補を増やさない
- 密な fixture で効くのは 4 本で、行内の隙間に既定のアンカーを持つ置けなかったラベル（7 本）には届かない

### 案4: 間隔を一様に広げる

`NODE_GAP` を定数のまま大きくする（Issue の表の形）。試作 1 で、密な fixture は `NODE_GAP` 100 で 25 / 41、
200 で 31 / 41。

- 置けている図も含めてすべての図が伸び、全 snapshot が変わる。floor-first に反する（ADR-2048 が却下した
  形そのもの）

### 案5: 案3 と案2 + 案3 を候補として配置し、置けないラベルが最も少ないものを採る

1 回目の配置で置けなかったラベルから、2 つの候補を作る。

- **候補 A**: 案3（チャネルだけを開く）
- **候補 B**: 案2 + 案3（チャネルと行内の隙間を開く）

基準は `main` が返す配置（1 回目、または ADR-2598 / ADR-2611 / #3154 の予約を入れた 2 回目）。各候補を
配置し、renderer のラベル配置パスで置けないラベルを数え、基準より**厳密に少ない**候補のうち最も少ないものを
採る。同数なら開く量の少ない方（A → B の順）を採る。どれも基準より少なくなければ基準を返す。

| | `main` | 案3 | 案2 + 案3（候補 B だけを基準と比べる） | **案5** |
| --- | --- | --- | --- | --- |
| 密な fixture | 17 / 41 | 21 | 30 | **30**（B を採る） |
| dify | 206 / 296 | 216 | 213 | **216**（A を採る） |
| WordPress | 156 / 258 | 186 | 158 | **186**（A を採る） |
| 返した配置でラベルが減る view | — | 0 | 0 | **0** |
| `examples/`（85 本・全 view） | — | 同一 | 同一 | **同一** |

「返した配置でラベルが減る view」は、比較で候補を採らなかった view を基準のまま数えている。候補 B そのものは
`WordPressApp` で基準より減る（比較を外して B を必ず採ると 110 → 98）。そのため候補 B だけを基準と比べる形では、
この view は B を採らず基準に戻り、チャネルの効果ごと失って 110 本のままになる。候補 A を別に持つことで、
各 view が自分に効く開き方を選べる。

view ごと（案5 で変わった view はこれで全部）:

| view | 採った候補 | ラベル | 面積 |
| --- | --- | --- | --- |
| `UmamiApp`（密な fixture） | B | 17 → 30 / 41 | 1520 × 958 → 1878 × 1064（+37%） |
| `DifyDB` | A | 206 → 216 / 296 | +7% |
| `WordPressApp` | A | 110 → 138 / 200 | +20% |
| `WpDB` | A | 32 → 34 / 44 | +4% |

時間（spike、5〜9 回の中央値）:

| view | `main` | 案5 |
| --- | --- | --- |
| `DifyDB` | 213 ms | 461 ms |
| `WordPressApp` | 190 ms | 338 ms |
| 密な fixture | 9 ms | 16 ms |
| `examples/en/ec-platform/01-system.krs` | 1 ms | 2 ms |

## 現時点の方針

**案5 を採用する。**

受け入れ条件 1 への答え:

- **行内の隙間の需要は、そこに既定のアンカーを持つ置けなかったラベルの幅である。** ラベル付きのエッジは、
  無いエッジより多くを求める。線の本数は需要にしない。今の `main` で行内の隙間を通る線は 60 px に収まり、
  収まらない分（外側のガターへ出た長いエッジ）は ADR-2611 が列を開いている（案1）
- **行内の隙間は、開いた配置で置けないラベルが減るときだけ開く。** 行内の隙間は回廊にもなるので、開くと経路が
  入ってきて逆効果になる図がある（案2）。開いた配置を実際に測って選べば、効く図（密な fixture）でだけ開き、
  効かない図（dify・WordPress）ではチャネルだけを開く

受け入れ条件 2: 密な fixture で 17 → 30。開くのは置けなかったラベルがある隙間とチャネルだけで、それ以外の
間隔は変わらない。受け入れ条件 3: `examples/` 85 本はバイト同一。

### 決定の中身

1. **測る関数は renderer のラベル配置パスそのもの。** `edge-layer.ts` の `buildLabelInputs` →
   `frameBordersOf` → `resolveLabelPlacements` を 1 つの関数に切り出し、renderer の描画とレイアウトの測定の
   両方がそれを呼ぶ（TPL-219）。レイアウトには `LayoutOptions` の callback として渡す
   （`withheldLabels?: (result: LayoutResult) => { anchor; width; height }[]`）。返すのは置けなかったラベルの
   既定のアンカー・ラベルの箱の幅・箱の高さで、幅と高さは切り出した関数が `labelBox` で計算する（renderer が
   衝突を判定する箱と同じ）。`svg-renderer` が `styles` と `palette` を閉じ込めて作る。`edgeLineKey` と同じ形で、
   渡さない呼び出し元（draw.io export、素の `layout()`）では候補を作らない
2. **相互ペアを分けてから測る。** renderer は `applyMutualPairs` が分けた後の edge にラベルを置く（半分ごとの
   区間と矢印）。置けないラベルの測定は、どの配置についても分けた後の edge で行う。今の `layout()` は分割を
   最後に 1 回だけ、返す配置に対して行うので、それより前に、1 回目・基準・各候補の配置それぞれについて、その
   配置の edge を分けてから callback を呼ぶ。返すことにした配置の分割はそのまま最終の分割にし、分け直さない。
   ADR-2598 / ADR-2611 / #3154 のレーン・列・側面の予約は、今と同じく分ける前の 1 回目の結果から測る（分けた
   後の edge で数えると今の予約が変わる）
3. **チャネルのラベルの需要。** 行序数 r のチャネルの帯は、r = 0 なら frame の天井から最初の行の上端まで、
   r = 行数 なら最後の行の下端から frame の床まで、それ以外は行 r − 1 の下端から行 r の上端まで（#3132 と
   同じ範囲）。既定のアンカーが帯の中にある置けなかったラベルについて、どの x でもそこに重なるラベルの高さ
   （callback が返した箱の高さに、レイアウト側で余白 2 px を足したもの）の合計を取り、その最大値をラベルの
   需要とする。序数 r の需要は `レーン数 × LANE_PITCH + ラベルの需要` で、既定の間隔を超えた分だけ広げる。
   frame が帯を分けて 1 つの序数に ADR-2598 のチャネルが複数あるときは、`レーン数 × LANE_PITCH − 間隔` が
   最も大きいチャネルのレーン数と間隔を使う
4. **行内の隙間のラベルの需要。** 行の中の隣り合う 2 枚のカードの間（行の上端から下端まで）に既定のアンカーを
   持つ置けなかったラベルのうち、最も幅の広いものの幅 + 余白 8 px × 2 を需要とし、隙間の幅を超えた分を
   右側のカードの前に開く（`extraGapBeforeCard`、カード id で鍵を持つ。TPL-2611）。ADR-2611 の列の予約が
   同じカードにあるときは大きい方を採る。行の外端は開かない（ADR-2611 の決定 9 と同じ理由）。grouped view
   （frame がある view）でも開く。ADR-2611 の決定 10 が列を予約しないのは内部の回廊がそこでは提供されず、
   列が使われないからで、ラベルの余地にはその理由が当たらない（回廊が無いので、開いた隙間に経路が入ってくる
   心配はむしろ小さい）。効くかどうかは決定の中身 6 の比較が決める
5. **候補と基準。** 基準は `main` が返す配置。候補 A はレーン・列・側面の予約に決定の中身 3 を加えたもの、
   候補 B は候補 A に決定の中身 4 を加えたもの。需要が出なかった候補は作らない（B の需要が無ければ B は A と
   同じなので作らない。A の需要が無ければ A は作らない）。幅予算は 1 回目の探索が選んだものをどの候補でも
   使い、探索をやり直さない。行の折り返しは予約の前の幅で決まる（ADR-2611 の決定 7）ので、どの候補でも行の
   構成は 1 回目と同じである
6. **選び方。** 各候補を配置して置けないラベルを数え、基準より**厳密に少ない**候補のうち最も少ないものを採る。
   同数なら A を採る。どれも基準より少なくなければ基準を返す（TPL-2593: 既定が先頭、厳密改善のみが勝つ）。
   ラベルの需要がどこにも無い図は候補を作らないので、配置の回数も出力も今と同じ
7. **パス数の上限を 4 にする。** ここで「配置」は、幅予算の探索（ADR-2593。それ自体が予算の候補ごとに
   `layoutInner` を走らせる）が終わった後の配置を数える。探索の勝者が 1 回目で、そこに基準の 2 回目（構造の
   予約があるとき）・候補 A・候補 B が続き、最大 4 回になる。候補は 1 回目の結果だけから決まる有限の集合で、
   繰り返しは無い。これは ADR-2598 の決定 3 と ADR-2611 の決定 11（どちらも「配置は 2 回まで、
   `placementPasses` は 1 か 2」）を、ラベルの余地の候補についてだけ置き換える。`placementPasses` は
   「探索の後に配置を何回走らせたか」のまま、型を `1 | 2 | 3 | 4` に広げる。どの候補を採ったかは別の出力
   （`LayoutResult.labelRoom?: "channels" | "channels+rows"`。採らなかったときは無し）で報告する。どちらも
   出力であって入力にはしない（ADR-2521）
8. **数えないもの。** `label-display: always` と `hover` のラベル（`always` は置けなくても描かれ、`hover` は
   canvas に描かれない）、合成ラベル（`N domain edges` など。保留されないので置けなかったことにならない）、
   ghost / cyclic のエッジのラベル。ghost と cyclic の `auto` のラベルはラベル配置パスでは保留されうる
   （ADR-3022 の決定 3）ので、callback の側で外す。ghost のラベルは実線のラベルが残した余地にだけ置く
   dimmed な文脈であり、そのために図を広げない（3 つのコーパスでは、外しても外さなくても数字は同じだった）
9. **予約しない経路。** 複数 system の root view と deploy view（ADR-2598 と同じ）

### 実装の指針

spike（`spike/3036-row-and-channel-label-room`）の構成をそのまま使える。違うのは次の点。

1. `edge-layer.ts`: ラベル配置パスを 1 つの関数に切り出し、`renderEdgeLayer` と callback の両方から呼ぶ
   （spike は同じ 3 つの呼び出しを並べた関数を別に書いた）。callback が返す幅と高さは `labelBox` の箱の寸法に
   する。spike はラベルの文字列の幅と font size を返し、行内の需要を「文字列の幅 + 8 px × 2」（箱の幅より 4 px
   小さい）、チャネルの x の重なりを「アンカー ± 文字列の幅 / 2」で測った。箱の寸法にすると計測の数字
   （30 / 216 / 186）が動きうるので、実装 PR で測り直して記録する
2. `placementPasses` と `labelRoom`: spike は `placementPasses` を 1 か 2 のまま報告し、`labelRoom` を持たない
3. `layout-types.ts`: `LayoutOptions.withheldLabels` を足し、`placementPasses` の型を広げ、`labelRoom` を足す。このファイルは行数予算が
   pin されている（`.claude/rules/line-budget.md`）ので、足す分は別の型をこのファイルの外へ移して相殺する
   （spike は module augmentation で逃げた）
4. `layout-reservations.ts`: チャネルのレーンの需要（相互ペアを分ける前の edge）、チャネルのラベルの需要、
   行内の隙間のラベルの需要（どちらも callback が返したラベルから）を、それぞれ序数ごとの値として返す
5. 候補の組み立てと選択は `layout.ts` の外の module に置く（spike の `chooseLabelRoom`。`layout.ts` は
   600 行の予算の際にある）。spike は配置ごとに edge を複製して相互ペアを分けて測ったが、実装では選ばれた
   配置の分割を最終の分割として使い回し、分け直さない
6. `svg-renderer.ts`: `withheldLabels` を渡す
7. テスト:
   - 密な fixture で、置けるラベルが 17 → 30 以上、候補 B が採られる。置けないラベルが無い隙間とチャネルの
     間隔が変わらない
   - `withheldLabels` を渡さない `layout()` の出力が今と同じ
   - `examples/` の全 view がバイト同一（既存の snapshot と examples の柵）
   - 候補 B が基準に負け候補 A が勝つ入力で A が採られ、どちらも負ける入力で基準が返ること
   - font size が違うラベルが同じチャネルに重なる fixture で、合計の高さが開くこと
   - dify / WordPress は repo に無いので、view ごとの増減と採った候補を実装 PR に記録する（TPL-3036）
8. AT: `docs/acceptance/` に追加する。手動項目は preview で密な fixture を開き、混んだ行内の隙間とチャネルに
   ラベルが増えていることを目で確かめる 1 件
9. changeset: `@karasu-tools/core` と `karasu` に minor（レイアウトの挙動が変わる）
10. ADR 昇格: 実装の PR がマージされたら `docs/adr/3036-withheld-label-room.md` に昇格し、本 Design Doc を
    削除する。ADR-2598 と ADR-2611 は、パス数の上限（ADR-2598 の決定 3、ADR-2611 の決定 11）だけがこの ADR で
    改訂され、ほかは有効なままなので、`supersedes` ではなく `refines: [ADR-2598, ADR-2611]` で結ぶ（ADR-788 で
    `supersedes` は時間軸の置き換え、`related_to` は意思決定に影響しない参照。1 つの決定だけを改訂する前例は
    ADR-2761 の `refines: [ADR-2593]`）。改訂する範囲は新 ADR の本文に書く。`layout-types.ts` の
    `placementPasses` のコメント（"Never 3"）も実装 PR で直す

### 影響範囲・マイグレーション

- 既存ユーザーへの影響: `auto` でラベルが置けなかった図のうち、開くと置けるラベルが増える図だけが変わる。
  置けていた図、開いても増えない図は変わらない
- 性能: ラベルが置けなかった図では、候補の配置とラベル配置パスの分だけ遅くなる（大きな view で約 2 倍）
- ドキュメント更新: なし（`docs/spec/style.md` の `label-display` の説明は変わらない）
- テスト・examples への影響: 密な fixture を `compile` で描いて数を固定しているテスト
  （`edge-label-disclosure-surfaces.test.ts`）の期待値が変わる。E2E の
  `packages/e2e/tests/at-3031-focus-canvas.spec.ts` は同じ fixture で保留されたラベルが 10 本より多いことを
  前提にしており、30 / 41 では 11 本残って 1 本差で通る。実装で数字が動けば落ちうるので、前提を見直す。素の `layout()` で測るテスト
  （`mutual-pair.test.ts`、`label-placement.test.ts` の `dense canvas fence`）は callback を渡さないので
  変わらない。`examples/` は変わらない

## 未解決の問い / 決めないこと

- **ラベルの配置の結果を renderer で使い回すか。** 選んだ配置について、レイアウトは置けないラベルを測るために
  ラベル配置パスを走らせている。renderer が同じパスをもう一度走らせるのは重複で、使い回せば時間のコストの
  一部が消えるが、`LayoutResult` にラベルの結果を持たせる形になる。性能の最適化として実装時に判断する
- **候補を増やすか。** 案5 の候補は 2 つ（チャネルだけ、チャネル + 行内）。行内だけの候補や、行ごとに開くか
  どうかを選ぶ候補は、配置の回数が増える。2 つで実モデルの全 view が減らないことは確かめたので、増やすのは
  効かない図が見つかってからにする

## 背景・課題

ラベルの衝突回避（ADR-2048 / ADR-2360）は、カード・確定済みのラベル・他エッジの線を障害物にして、衝突したラベルを近くの空きへずらす。枠（ドリルダウンの枠、team / boundary の group 枠）は障害物に入っていない。そのため、混んだ場所からずらしたラベルが枠の線の上や枠の外に描かれる。

Issue の再現（Umami の `UmamiApp` ドリルダウン）では、`Administration -> Teams` のラベル "lists all teams via queries/prisma/team getTeams" が、隣のラベルを避けて約 35px 下へずらされ、枠の下端の線をまたいで描かれる。#3132 / #3154 で run は枠の内側に収まったが、ラベルは別のパスなので残った。

4 つの逆生成モデル（umami / dify / twenty / wordpress）と `examples/en` の全ビュー × グルーピング（none / team / boundary）で `main`（206441c2）を測った。ケースは計 5,061 で、4 モデルが 4,626、`examples/en` が 435 である（ノードが 2 未満のビューは除く）。

| 指標 | 件数 |
| --- | --- |
| 描かれたラベル | 22,270 |
| 箱に枠の線が掛かるラベル | 132（うち 114 件はずらした結果） |
| 既定位置と反対の側（枠の内↔外）へずらされたラベル | 57（すべて上の 132 件に含まれる） |

計測は `reports/3155-label-frame-borders/`（gitignore）にある。件数は `measure2.mts` で、枠の線の太さは renderer が描く太さ（`renderContainer` と同じ求め方。この計測では 1 と 2）を使った。114 件と案2 の 23 / 19 件は、線の太さを 1 に固定した `measure.mts` の値である。114 件は renderer の太さで測り直しても同じだった。23 / 19 件は線の太さに依らない。

## 現状（インベントリ）

| 観点 | 現状 |
| --- | --- |
| 障害物集合 | カード矩形、確定済みラベルの箱、他エッジの polyline（自分の線は除外、ADR-2360） |
| 枠を外した理由 | ADR-2048 / TPL-2048: 枠の**面**はラベルが正当に住む領域で、面を障害物にするとドリルダウンで全ラベルが枠の外へ追い出される。ADR-2360 は枠の**線**の扱いをスコープ外として残した |
| 枠の所在 | `layoutResult.containers`。ドリルダウンの枠、group 枠（boundary は `coverage` で L 字に広がることがある）、展開した container の枠、ghost の祖先枠 |
| 枠の描き方 | `renderContainer`: `coverage` があれば `rectUnionPath` の外形、無ければ `<rect>`（角は `style.borderRadius` で丸める）。線の太さは展開枠 2、それ以外は frame paint か container style の `borderWidth` |
| コスト | 衝突 2・曖昧さ 1（自分の線より近い他エッジの線がある）。`label-display: auto` では衝突の残るラベルを外す（ADR-3022） |

## 制約・前提

- **枠の規則を破るラベルが無いビューは変えない**（TPL-2048 の byte-stability）。枠を渡さない pass で、どのラベルも枠の線に掛からず、既定位置と同じ側にあるビューは 1px も動かさない
- **枠の面は障害物にしない**（ADR-2048 の判断を維持）
- 曖昧さの項は「どのエッジのラベルに見えるか」の判定なので、エッジでないものを入れない
- 決定論・探索範囲の prune が厳密であること（ADR-2360）
- スコープ外: 枠のタイトル文字とラベルの重なり、deploy ビュー（`renderEdge` を通らない）

## 検討した選択肢

### 案1: 枠の外形を、他エッジと同じ線障害物として足す

枠の外形を polyline にして、箱に掛かれば衝突とする。

**メリット**

- 既存の線障害物の仕組みに乗るだけで、新しい判定が要らない

**デメリット**

- 線を「またぐ」候補は止まるが、線を**跳び越えた**候補は止まらない。ラベルの箱は高さ約 15px、1 ステップも約 15px なので、2 ステップ先の候補は枠の線に掛からずに枠の外に収まる。線を障害物にすると、探索は線の向こうまで進むので、Issue の症状（枠の外に描かれる）が残る。これは探索の形からの推論で、実測ではない。`main` では反対の側にあるラベルはすべて線にも掛かっている（線が障害物でないため、跳び越える理由が無い）

### 案2: エッジの両端を囲む枠の内側に収める（包含制約）

両端点のカードを両方とも囲む枠を求め、候補の箱がその内側に無ければ衝突とする。

**メリット**

- 「枠の中のエッジのラベルは枠の中」という Issue の期待をそのまま書ける

**デメリット**

- 自分の run が枠の外を通るエッジ（boundary 枠は重なり L 字にもなるので、両端が枠の中でも経路が外を回る）のラベルは、既定位置が枠の外にある。包含制約はこれらを枠の内側へ引き込み、ラベルが自分の線から離れる。`main` の WordPress で、既定位置のまま両端を囲む枠の外にあるラベルが 23 件（うち 19 件が boundary グルーピング）あり、全部が動く
- 両端を囲まない枠（エッジが横切る枠、無関係な隣の枠）の線は防げない

### 案3: 既定位置と同じ側に留め、線に掛けない（採用）

枠ごとに、ラベルの**既定位置の箱の中心**がその枠の内か外かを求める。候補は、(a) 枠の外形の線が箱に掛からず、(b) 箱の中心が既定位置と同じ側にあるときだけ、その枠について clear とする。破れば衝突（コスト 2）。

内外の判定は、枠が覆う矩形の集まり（`coverage` の各矩形。外形を 1 つの多角形として辿れず本体の矩形に戻した枠では本体の矩形 1 つ）に対して行い、外接矩形は使わない。L 字の枠の欠けた角は外側である。各矩形は境界込み（閉じた矩形）で扱う。中心がちょうど枠の線上にある点は**内側**とする。この取り決めが効くのは既定位置の側だけである。候補の中心が線上にあれば、その候補の箱には必ず線が掛かり (a) で衝突になるので、候補の側の判定は結果を変えない。既定位置の中心が線上にあるラベルは、線に掛からない内側の候補へ動く（`label-display: auto` で内側に空きが無ければ外す）。

**メリット**

- 1 つの規則で、線の上（案1 の範囲）と、跳び越え（案1 の穴）と、枠の外への持ち出し（案2 の範囲）を同時に扱う。`label-display: auto` では防ぎきる（規則を破る位置しか無ければ外す）。`always` では、clear な候補があればそれを選ぶ最善努力になる（下のデメリットの 2 つ目）
- 既定位置が枠の外にあるラベル（自分の線が外を通る）は外に留まり、自分の線から引き離さない（案2 の欠点が無い）
- 両端を囲まない枠も同じ規則で扱える。枠の数え分けが要らない
- 探索が届く範囲（実装の指針 2 の prune）に枠の線が無いラベルは、どの候補でも側が変わらないので、そのラベル自身のコストは変わらない。ただしラベルは順に確定し、確定した箱が後続の障害物になる。先に確定したラベルが枠のコストで動くと後続の空きが変わり、後続も連鎖して動きうる。保証できるのは「枠の規則を破るラベルが無いビューは変わらない」（制約・前提の 1 つ目）までである。枠のコストは候補のコストを増やすだけで、`main` で選ばれていた候補が規則を破らなければそのコストは変わらないので、ラベルを順に見ていけば同じ候補が選ばれ続ける（連鎖の実測は「実測（試作）」）

**デメリット**

- 既定位置のまま枠の線に掛かって描かれていたラベルは、新しく衝突扱いになり動く（`main` で 18 件）。これは読めなさの解消なので許容する（ADR-2360 で線に乗っていたラベルを動かしたのと同じ）
- 規則を破る枠は、カードやラベルとの衝突と同じ 1 件の衝突（コスト 2）として数え、優先はしない。clear な候補が無いラベルは、これまでどおりコストの合計が最も小さい候補に置かれ、同じコストなら探索順で先の（近い）候補が勝つ。そのため、規則を破る以外に何も無い候補（2）が、同じ側で 1 件衝突する候補（2）と同点で近いほうに置かれたり、同じ側で 1 件衝突して曖昧さもある候補（3）や 2 件衝突する候補（4）に勝ったりする。置かれた位置は枠の向こう側のことも、線の上のこともある。文字が重なって読めなくなるより、枠を外れても読めるほうがよいと判断した。`label-display: auto` ではどの場合もラベルを外すので、この比較は起きない

作者が `label-position` / `label-offset` で置いたラベル（ADR-1184）は、これまでどおり動かさない。枠の線上にあってもそのまま残り、ほかのラベルにとっての障害物として働く。計測ヘルパーと柵は動かせるラベルだけを数える。数えると、作者の指定だけで柵が落ちるため。

### 案4: 枠の面を障害物にする

**却下**: ADR-2048 / TPL-2048 のとおり、ドリルダウンで枠の内側のラベルが全部追い出される。

## 現時点の方針

**案3 を採用する。** 枠に関係するのは面ではなく「線」と「どちら側か」で、側の基準を既定位置に取れば、Issue の症状（線の上・枠の外）を両方防ぎつつ、自分の線が枠の外を通るラベルを引き離さない。

### 実装の指針

1. `frame-geometry.ts` に `drawnFrame(frame)`（描かれる外形を閉じた polyline で、その外形が囲む矩形の集まりと一緒に返す。外形を 1 つの多角形として辿れない `coverage` は renderer と同じく本体の矩形に戻す）を足し、`rectUnionPath` の slab 走査を `rectUnionOutline` として移す。renderer の `<path>` と障害物が同じ角の列を使う
2. `label-placement.ts`
   - `FrameBorder`（外形を `EdgeLine` として包んだもの + 外形が囲む矩形の集まり。内外の判定はこれで行う）と `frameBorder(frame, strokeWidth)` を足す。`EdgeLine` の `index` は `-1` で、どのラベルの自分の線にもならない
   - `resolveLabelPlacements(labels, nodeRects, edgeLines, frames, options)`。ラベルごとに、既定位置の箱から探索が届く枠だけを、既定位置の側と一緒に取り出す（候補の中心は既定位置から `maxShift·√2` 以内にある。線の判定は箱を線の太さの半分 `h` だけ広げて中心線と比べるので、届く距離は `maxShift·√2` に、広げた箱の半対角 `hypot(w/2 + h, H/2 + h)` を足したものになる（`w` / `H` はラベルの箱の幅と高さ）。中心線がそれより遠い枠は、どの候補でも結果が同じなので外す。prune は厳密。半対角を広げない箱で測ると、箱の角の近くでは線の太さの分だけ届かない枠を落としうる）
   - 候補のコストに、規則を破る枠 1 つにつき衝突 2 を足す。枠の線は曖昧さの判定に入れない
   - 計測ヘルパー `countLabelFrameCrossings({ defaultBox, box }[], frames)` を足す（ラベル単位）
3. `svg-renderer.ts`: `layoutResult.containers` の全枠（ghost の祖先枠を含む）を、`renderContainer` が描く線の太さで `frameBorder` にして渡す。線の太さは `renderContainer` と同じ関数で求める
4. テスト（`label-placement.test.ts`）
   - 合成: 線の向こうが最寄りの空きでも内側に留まる / 外から始まるラベルは外に留まる / 既定位置で線に掛かるラベルは線に掛からない側（中心のある側）へ動く / 既定位置の箱の中心がちょうど枠の線上にあるラベルは内側として扱われ、内側の候補へ動く / 線から離れたラベルは動かない / `auto` で同じ側に空きが無ければ外す / L 字の枠は外形で測り、欠けた角は外側として扱う / 枠の線は曖昧さに入らない（枠を曖昧さに入れると落ちることを確認する）
   - 実サンプル柵: hr-tool の `Auth` ドリルダウン、team-ownership の team グルーピング。枠の線の太さは renderer と同じ関数で求め、固定値にしない（柵と canvas の線の太さがずれないように）。枠を渡さない pass では枠を越えるラベルが出ること（柵が vacuous でない）、渡すと 0 で、カード・ラベル・線との衝突も 0（TPL-2048 の全軸同時）
   - renderer の配線: 同じビューを `renderFromLayout` で描き、枠で位置が変わったラベルがその位置に描かれる（renderer が枠を渡さないと落ちることを確認する）
5. TPL-2048 に 4 本目の計測軸（label↔枠の線）と失敗モード（障害物集合の取りこぼし、面を障害物にする誤り）を足す
6. ADR-2360 の `assumptions` の grep（`resolveLabelPlacements\(labelInputs, nodeRects, edgeLines\)`）は引数が増えるので、枠を渡す呼び出しそのもの（`resolveLabelPlacements\(labelInputs, nodeRects, edgeLines, frameBorders\)`）に更新する。`edgeLines` までの前方一致に緩めると、枠を渡し忘れた呼び出しも通ってしまう（frontmatter のみ）
7. AT: `docs/acceptance/3155-label-placement-frame-borders.md`。すべて自動テストで判定でき、手動項目は無い
8. ADR 昇格: 実装のマージ後、`docs/adr/3155-label-placement-frame-borders.md` として昇格し、本 Design Doc を削除する

### 実測（試作）

案3 を実装したブランチ（`fix/3155-label-placement-frame-borders`）で同じ 5,061 ケースを測った。同じレイアウトに対して、枠を渡さない pass（`main` と同じ）と枠を渡す pass を比べた。

| 指標 | `main` | 案3 |
| --- | --- | --- |
| 箱に枠の線が掛かるラベル | 132 | 0 |
| 既定位置と反対の側へずらされたラベル | 57 | 0 |
| 位置が変わったラベル（`auto` で外れたものを含む） | （基準） | 137（54 ビュー） |
| `auto` で外れたラベル | 1,745 | 1,784（+39） |
| core の既存テスト（SVG 文字列の検証を含む） | （基準） | 無変更で通る |
| ラベル配置 pass の時間（`perf.mts`。twenty 1,521 ケース / wordpress 3,096 ケース） | 728 / 470 ms | 719 / 522 ms |

位置が変わった 137 件のうち 132 件は、`main` で枠の規則を破っていたラベルそのものである。残る 5 件は連鎖による（先に確定したラベルが動いて、後続の空きが変わった）。5 件とも boundary グルーピングの `WordPressApp` 1 ビューにある。このビューでは 45 件が変わり、うち 40 件が `main` で枠の線上にあった。位置が変わった 54 ビューは、どれも `main` で枠の規則を破るラベルを含んでいた。

時間は `perf.mts` で測った（5 回の最良値）。`perf.mts` は線の太さを 2 に固定し、ノードが 2 未満のビューも数えるので、ケース数が上の 5,061 と違う。wordpress では 11% 長くなったが、1 ケースあたり 0.02 ms 未満の差で、twenty では短くなっている。描画全体から見て無視できるとみて許容する。

### 影響範囲・マイグレーション

- 既存ユーザーへの影響: 枠のあるビューで、枠の線上・反対の側にずらされていたラベルが既定位置と同じ側（多くは枠の内側）へ動くか、`label-display: auto` なら外れる。それ以外のラベルは、同じビューで先に確定したラベルが動いて空きが変わったときだけ連鎖で動く（試作では 137 件中 5 件）。枠の規則を破るラベルが無いビューは変わらない
- ドキュメント更新（実装 PR で行う）
  - TPL-2048、ADR-2360 の frontmatter（assumptions）
  - `docs/spec/style.md` / `docs/spec/style.ja.md` の `label-display: auto` の行: 外す理由に「枠の線に掛かる・既定位置と反対の側にある」を足す
  - 昇格する ADR-3155 の frontmatter は、`refines: [ADR-2360]`（障害物集合に枠の線と側を足す）、`related_to: [ADR-2048, ADR-3022]` とする。ADR-2048（枠の面を障害物にしない）と ADR-3022（`auto` で外す衝突の種類）の本文は書き換えない
- テスト・examples への影響: core の既存テストは変わらない。`examples/en` では 32 ケースで 44 件のラベルが動く。描画結果を固定した golden は repo に無いので、更新するファイルは無い

## 未解決の問い / 決めないこと

- **枠のタイトル文字とラベルの重なり**は扱わない。タイトルは枠の左上の短い帯で、本件の症状（線・外側）とは別の障害物になる。必要になったらタイトルの箱を矩形障害物として足す（面ではないので ADR-2048 の判断に反しない）
- **既定位置が枠の外にあるラベル**（自分の run が枠の外を通る）を枠の中へ寄せることはしない。原因は経路で、ラベルを動かすとラベルと線が離れる。経路側で直すなら #3132 / #3154 の延長として別 Issue にする
- **deploy ビュー**は `renderEdge` を通らないので対象外（ADR-2048 / ADR-2360 と同じ）
- **角丸の枠**: `coverage` の無い枠は `<rect>` の `rx`（`style.borderRadius`）で角を丸めて描くが、障害物の外形と内外の判定は角の立った矩形で行う。角の近くでは、描いた線との差が最大 `rx·(1 − 1/√2)`（`rx` が 8 なら約 2.3px）になる。差が出るのは角だけで小さいので、角丸は模さない

## 背景・課題

TPL は、設計・実装・bug 修正のときに人か LLM が**思い出して**当てるチェックリストである。
当たるかどうかは思い出すかどうかで決まり、決定論的ではない。TPL は 182 件まで増え、
deprecated は 0 件なので、思い出す負担は増える一方になっている。

2026-10-02 に、当時の 154 TPL・804 項目を「プログラムで判定できるか」「今プログラムが
判定しているか」で分類した（基準と数値は #3038 本文）。

| 区分                                                     | 項目 | 割合 |
| -------------------------------------------------------- | ---: | ---: |
| mechanized（新しい箇所の違反で CI が赤くなる）           |  117 |  15% |
| instance-only（元 bug の箇所だけを固定するテストがある） |  382 |  48% |
| unguarded（判定できるが何も判定していない）              |   83 |  10% |
| judgment（設計時の判断、または人が行為をしたかの問い）   |  222 |  28% |

読み取れることは 2 つある。

1. **思い出すことに頼っている部分は 10% ではなく 48% の側にある。** instance-only は
   テストがあるので守られているように見えるが、そのテストは元の bug を固定しているだけで、
   次の箇所で同じ形を捕まえる役目は TPL を思い出す人が負っている。
2. **TPL 本文からは、どの項目が機械で守られているかが読めない。** 76 TPL は、分類が根拠に
   挙げたテストを本文で名指ししていない（その大半は instance-only で、D4 のガードに当たる
   mechanized 項目を名指ししていないのは 24 TPL）。「関連テスト: 未確立」と書いたまま、
   `packages/core/src/fs/import-resolver.test.ts` に専用のテスト block がある TPL もある
   （TPL-1381 / TPL-1383 / TPL-2168〜2170）。テストの有無すら本文から読めないので、
   ガードかどうかはなおさら読めない。

TPL ごとに「どこまで機械が守っているか」を持たせ、それを本文から**導出**して、
思い出す必要のある項目を読者に示したい。

## 制約・前提

- 検査と照会は `@kompiro/tpl-tools`（別 repo）が持つ。karasu 側は設定と TPL の本文だけを持つ
  （ADR-1357）。tpl-tools は karasu 以外でも使われる汎用ツールなので、karasu 固有の語
  （見出し名「チェックリスト」など）をハードコードしない
- `tpl validate` は既に、本文のインラインコードスパンが名指しする `packages/…` / `scripts/…`
  のパスの実在を検査している（tpl-tools ADR-17）。ガードの参照をパスにすれば、
  ガードの実在検査はその検査に乗せられる。ただしその検査は、対象の形（ソース prefix から始まる
  パス）でないスパンを黙って読み飛ばすので、ガードの参照がその形であることは別に確かめる（D1）
- **プログラムに判定できるのはガードの実在までで、一般性は判定できない。** 名指しした
  テストが「新しい箇所の違反でも赤くなる」のか「元の箇所だけを固定している」のかは、
  レビューで見るしかない
- 本文の節構成はまだ検査されていない。7 TPL は template どおりの `## チェックリスト`
  見出しを持たない（6 件は別の見出し、TPL-2133 は節が無い）

## 検討した選択肢

1. 項目ごとの印をどう書くか（D1）
2. TPL ごとの状態を宣言させるか、導出だけにするか（D2）
3. 状態の語彙（D3）
4. 何をガードと呼んでよいか（D4）
5. 変更ファイルから TPL を引く仕組み（Issue の提案 6）を同じ設計に含めるか（D5）

### D1: 項目の印

#### 案 1-A: 項目の末尾に見える印を書く（採用）

チェックリストの各項目（トップレベルのリスト項目。`- [ ]`・`- `・番号付きのどれも項目に数える）の
本文の末尾に、次のどちらかを書く。

```markdown
- [ ] key の dot-segment 数が 4 以下か。
      [guard: `packages/i18n/src/catalog.test.ts`]
- [ ] sub-feature を導入するなら、そのまとまりだけで element.state キーが
      複数生まれるか。[judgment]
- [ ] dark / light の両テンプレートで同じ kind 集合を揃えているか
```

- `[guard: …]` はインラインコードスパンでパスを 1 つ以上並べる（``[guard: `a`, `b`]``）
- `[judgment]` はプログラムで判定できない項目
- **印が無い項目は「判定できるがガードが無い」（思い出す必要がある）とみなす。** 新しく
  書いた項目の既定がこれになるので、正直な既定になる。judgment は明示して外す

**ガードのスパンは、既存の実在検査の対象になる形でなければ finding にする。** 既存の検査
（tpl-tools ADR-17 の `candidatePath`）は、ソース prefix から始まり端から端までパスである
スパンだけを見て、それ以外は**黙って読み飛ばす**。行番号付き（`path:61`）・glob・
ファイル名だけ・1 セグメントのルートのファイル（`adr.config.json`）・`node_modules/…` は
どれも読み飛ばされるので、印の検査がそれを許すと、ガードの参照が検査されないまま残る。
印の検査は次を finding にする。

- `[guard: …]` の中のスパンが `candidatePath` を通らない（行番号は付けない。行番号は
  コードの変更でずれるので、ガードの参照はファイル単位にする）
- スパンが指すものがファイルでない（一般のパス検査はディレクトリを許すが、ガードは
  チェックを実行するファイルを指す）
- 印の検査が有効なのに `--source-prefix` が 1 つも渡されていない（パスを検査する手段が
  無いので usage error にする）
- `<!-- absent-path-next-line: … -->` の直下の行に `[guard: …]` がある（ガードは実在が
  前提で、不在の宣言で黙らせてよいものではない）

印の書式の細部は次のとおり。

- 印の形をブラケットで囲むのは、項目の文中に「judgment」「guard」という語が出ても
  印と読まないためである（検出器の near-miss は仕様の一部: TPL-2287）
- 印は項目の本文（続き行を含む）の、空白を除いた最後に 1 つだけ置ける。末尾以外の位置にある
  印、印の後ろに句読点が続くもの、パスを持たない `[guard: ]` は finding にする。インライン
  コードスパンの中に書いた `[guard: …]`（書式を説明する散文）は印として読まない
- チェックリスト節は見出しから**次の見出し（レベルを問わない）まで**とする。TPL-219 は
  チェックリスト節の中に `### 本観点の範囲外` を持ち、その下のリストはチェック項目ではない
- 項目が 1 つも無いチェックリストは finding にする（D3 の `judgment` が空虚に成り立つのを防ぐ）
- 状態を導出する `regenerate` と `related --status` は、書式の誤った印を unguarded として
  数える（守られていない側に倒す）。この 2 つのコマンドは `--source-prefix` を受けないので、
  ここで言う「誤った印」は書式の規則（位置・後ろの句読点・パスの無い `[guard: ]`）だけで、
  `candidatePath` とファイルであることの検査は `validate` だけが行う。誤った印を finding に
  するのも `validate` だけで、CI で `validate` が落とすので、誤った印が main に残ることはない

利点: 人も LLM も、項目を読んだその場で「これは機械が守っている / 自分が確かめる」が分かる。
欠点: チェックリストの見た目が少し重くなる。

#### 案 1-B: HTML コメントで書く（`<!-- guard: path -->`）

描画結果には出ない。却下: 読者に見せたい情報を隠すことになる。LLM は生の markdown を
読むので隠しても得はなく、人は描画を読むので印が見えなくなる。加えて、コメント内のパスは
既存の実在検査（インラインコードスパンが対象）に掛からないので、別の検査を足す必要がある。

#### 案 1-C: 項目番号とガードの対応表を別の節に置く

チェックリストは変えず、`## ガード` 節に「項目 2 → `path`」の表を置く。却下: 項目を
並べ替えたり足したりすると番号がずれ、表と項目の対応が黙って崩れる。項目と印が同じ行に
あれば、その対応は崩れようがない。

#### 案 1-D: チェックリストを frontmatter に移す

`checklist: [{ text, guard }]` の形にする。却下: 本文の散文（続き行・強調・リンク）を YAML に
閉じ込めることになり、TPL の読みやすさを大きく損なう。

### D2: 状態は宣言させず導出だけにする

#### 案 2-A: 導出だけにし、表示先を `tpl related` と生成索引にする（採用）

状態は項目の印から毎回計算する。TPL のファイルには書かない。

- `tpl regenerate` が生成する索引（tpl-tools ADR-27）の各行に状態と数を出す
  （例: `- [TPL-2019](…) — <title> (#2019) · guarded 2/2, judgment 2`）。索引は生成物で、
  CI の `tpl regenerate --check` が古い索引を落とすので、「状態の変化が PR の diff に見え、
  しかも drift しない」は索引が持つ。`tpl validate` は索引のリンクの網羅しか見ず、行の中身は
  比べない（ADR-27）ので、この保証は `--check` を CI で回して初めて成り立つ
- `tpl related` は `--status` を付けたときだけ各行に状態を出す。既定の出力は Design Doc の
  「Related TPLs」節に貼る形なので、そこに状態を混ぜると、導出値の写しが Design Doc に入り、
  昇格後は本文を変えない ADR（ADR-2687）に固まる。これは 2-B で避ける二重管理と同じ形になる
- 印ごとの一覧（どの TPL のどの項目が unguarded か）を出す手段を tpl-tools に足す
  （コマンド名は tpl-tools 側で決める）。印はガードがあるかどうかしか持たず、どんな
  ガードを作ればよいかは持たないので、スライス 4 の backlog は分類の提案から起こし、
  この一覧はどの項目がまだ unguarded かを確かめるのに使う

karasu はまだ生成索引を採用していない（#3289 は tpl-tools v0.0.11 の release 待ちで
`status: blocked`、`tpl.config.json` に `indexFile` が無く、README の一覧表は手書き）。
#3289 が入るまでは、状態は `tpl related <topic> --status` でしか見えない。

#### 案 2-B: frontmatter に `enforcement` を宣言させ、導出値と照合する（Issue の提案。却下）

Issue は「宣言させ、validator が導出値と食い違えば落とす」を提案していた。drift は照合で
防げるが、**印を 1 つ直すたびに frontmatter も直す二重記帳**が残り、その手間に見合う
情報は増えない（frontmatter の値は印から一意に決まる）。導出できる値をもう一箇所に
持てば二重管理になる、という点で TPL-1032 と同じ形をしている。

frontmatter にあれば grep しやすい、という利点は生成索引が代わりに持つ
（索引の 1 行に TPL の id と状態が並ぶ）。

#### 案 2-C: 自己申告だけ（照合しない）

却下。申告がチェックリストからずれても誰も気づかず、Issue が避けたかった状態そのものになる。

### D3: 語彙

導出規則は、項目を guarded（`[guard: …]`）・judgment（`[judgment]`）・unguarded（印なし）に
分けた数から決める。

| 状態        | 条件                           | 意味                                     |
| ----------- | ------------------------------ | ---------------------------------------- |
| `guarded`   | unguarded = 0 かつ guarded ≥ 1 | 判定できる項目はすべて機械が守っている   |
| `partial`   | unguarded ≥ 1 かつ guarded ≥ 1 | 一部の項目は思い出す必要がある           |
| `unguarded` | guarded = 0 かつ unguarded ≥ 1 | 判定できる項目をすべて思い出す必要がある |
| `judgment`  | すべての項目が judgment        | 機械には判定できない。思い出すことが前提 |

Issue の案（`automated` / `partial` / `manual`）から 2 点変える。

- **4 つ目の値 `judgment` を足す。** Issue の定義（「judgment 以外のすべての項目にガードがある」
  なら automated）では、全項目が judgment の TPL（分類時点で 5 件）が空虚に automated になり、
  「機械が守っている」と読めてしまう
- **`manual` を `unguarded` と呼ぶ。** karasu では「手動」が受け入れテストの手動項目
  （ADR-3169）を指すので紛らわしい。分類で使った区分名と揃える

項目が 1 つも無いチェックリストは状態を持たず finding になる（D1）。これが無いと
`judgment`（すべての項目が judgment）が空虚に成り立つ。

`status: active | deprecated`（ライフサイクル）とは直交する。

### D4: ガードと呼んでよいもの

`[guard: …]` に書いてよいのは、分類の rubric の mechanized と同じ条件を満たすものだけにする:
**その項目に新しい箇所が違反したとき、CI で動くチェックが赤くなる**（ファイル集合の走査、
registry の列挙、型レベルの網羅、閉じたクラスをテストが全列挙している、のどれか）。

- 元 bug の箇所や known_consumers だけを固定するテスト（instance-only）は `[guard: …]` に
  書かない。これまでどおり「関連テスト」節に書く。その項目は印なし（unguarded）のまま残る
- 手で保守する表を回すテストは、**新しい箇所が表に入ることを何かが強制しているとき**だけ
  ガードになる（型、表とコードの突き合わせ、表がコードから導出されている）。
  `derivation-contracts.test.ts` のように、表に入れ忘れた箇所が CI を通る形は instance-only

**ガードの参照先は、CI の step から辿った呼び出しの終点にある、この repo のファイルにする。**
テストファイルか、`scripts/` や `packages/*/scripts/` のスクリプトが典型である（TPL-2005 (5) は
`packages/docs-site/scripts/check-links.ts`、TPL-2165 (4) は `scripts/reference/gen-docs.ts`）。
終点が外部の実行ファイル（`adr validate` など）のときだけ、その step を持つ workflow を
ガードにし、項目の本文で呼ばれるコマンド（`pnpm adr:validate` など）を名指しする。設定データ（`adr.config.json`）や外部パッケージの中身（`node_modules/@kompiro/adr-tools`）は
ガードではない。そのため karasu の `pnpm tpl:validate` に `--source-prefix .github` を足す。
分類で mechanized とした項目のうち 9 件（TPL-1829 (1)〜(4)、TPL-2005 (5)、TPL-2165 (4)、
TPL-2188 (2)(3)、TPL-2446 (5)）は、根拠が `.github/workflows/*.yml`・`adr.config.json`・
`node_modules/@kompiro/adr-tools` だけを指しているので、この決め方でないと検査される
ガードとして書けない。`.github` を足すと、TPL 本文が名指しする `.github` 以下の他のパス
（PR テンプレートなど）も検査されるようになる。その影響はスライス 3 で直す。

workflow のファイルは多くの step を持つので、ファイル名だけではどの step が項目を守るのかが
分からない（TPL-1829 (2)(4)、TPL-2188 (3)、TPL-2446 (5) の根拠は `ci.yml` の行番号だけ）。
上の規則により、step がこの repo のスクリプトを呼ぶならそのスクリプトがガードになり、
workflow が参照先になるのは外部の実行ファイルを呼ぶ step だけになる。`packages/` の下にあっても設定データは同じ扱いで、
TPL-1171 (5)（`playwright.config.ts`）と TPL-2167 (4)（`packages/core/package.json`）は、
その設定を読んで検査するものを探してガードにするか、見つからなければ印なしにする。

README「横断観察 A」は、curated table を meta-check の既定の選択肢とし、その採用理由に
「新エントリ追加時に table 編集を強制できる」を挙げている。この理由は実例の一部にしか
成り立たない。表そのものは、新しい箇所が追加されても編集を強制しない。強制が働くのは
表とは別の仕組みがあるときで、実例の #1233（`packages/core/src/parser/base-node-fields-coverage.test.ts`）は
型の契約で全 kind の登録を強制しているので mechanized になる。一方、実例の #1249
`derivation-contracts.test.ts` は、冒頭のコメントで「新しいエントリの登録を忘れると
このテストをすり抜ける」と自ら書いている。分類でも、ガードが無い項目に提案された手段で最も
多いのは「全箇所の表を回す meta-test」（212 項目。うち 206 項目には箇所を固定するテストが
既にある）で、表の形そのものは有効でも、登録を強制する仕組みが無いことが欠けている。
そこで、採用理由を「表への登録を型・突き合わせ・導出のどれかで強制したときに限り、
explicit な表は review で auditable なガードになる」に書き直す（注記を足すだけでは、
一部にしか成り立たない理由が本文に残る）。

**ガードの一般性はプログラムでは判定できない**（制約・前提）。実在は validator が見て、
一般性は TPL を変える PR のレビューが見る。分類で mechanized とした 117 項目は、判定を
全件人が読んでいる（ガードの中身まで開いたのは 3 件）ので、初回のバックフィルの出発点には
使える。ただし出発点に留まり、mechanized という判定だけでは一般性の根拠にならない。スライス 3 は、各ガードを開いて D4 を
確かめた記録を残してから `[guard: …]` を付け、確かめていない項目は印なしのままにする。
また根拠のファイルは分類後に消えたものがあり（#3423 の gh-aw 削除で、TPL-2658 (1)(3)(4)・
TPL-2786 (4)(5) の根拠 6 ファイル）、スライス 3 で今の tree に照らして確かめ直す。

### D5: 変更ファイルから TPL を引く仕組み（Issue の提案 6）は別 Issue に分ける

judgment 項目に対して決定論的にできるのは判定ではなく「どの TPL を見せるか」で、Issue は
`tpl related --changed-files` を提案していた。本設計には含めない。

理由: 対応付けの鍵が今の frontmatter に無い。`scope.packages` は粒度が粗く、182 TPL のうち
119 件が `core` を持つので、`packages/core` の変更でほぼ全 TPL が出てしまい、引けないのと
変わらない。`known_consumers` は機能名で、パスではない。TPL ごとにパスの glob を持たせる
（`.claude/rules` の `paths:` と同じ発想）などの新しいフィールドが要り、それ自体に
選択肢がある。本設計の印と状態はその仕組みが無くても成り立つので、別 Issue で設計する。

## 比較

| 論点           | 採用                                                         | 主な却下案                           | 決め手                                                             |
| -------------- | ------------------------------------------------------------ | ------------------------------------ | ------------------------------------------------------------------ |
| 項目の印       | 末尾に見える `[guard: …]` / `[judgment]`、印なし = unguarded | HTML コメント / 対応表 / frontmatter | 読む場所に印がある。既存のパス実在検査に乗る（乗らない形は落とす） |
| 状態           | 導出だけ（生成索引と `related --status` に表示）             | frontmatter に宣言して照合           | 導出できる値の二重記帳を避ける。drift しない保証は生成索引が持つ   |

## 現時点の方針

### スライス

スライス 1 と 2 は互いに独立で、どちらもスライス 3 の前提になる。見出しが必須になるのは
karasu がスライス 3 で見出しのキーを設定したときなので、スライス 1 は tpl-tools の版を
待たずに入れられ、スライス 2 も karasu の本文を待たない。スライス 3 の索引への表示だけは
#3289（生成索引の採用と CI での `regenerate --check`）にも依存する。スライス 4 はスライス 3 を
待つ。印を付ける前に印ごとの一覧を出すと、judgment の項目も含めて全項目が unguarded と出るため。
各スライスでできること・

sub-issue にする。tpl-tools の repo の Issue を sub-issue にできなければ、karasu 側に
追跡用の Issue を立ててそれを sub-issue にする。

   README の「3〜5 項目」を超えるが、削ると分類との対応が崩れる。削るかどうかは月次レビューで

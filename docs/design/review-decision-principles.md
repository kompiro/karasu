## 背景・課題

kompiro に判断を求める量が多すぎ、Issue も増え続けている。

- 10/26〜11/22 の 4 週間で Issue を 202 本起票し、閉じたのは 152 本。open は 122 本ある。多くは作業の副産物で、PR やレビューの途中で見つけた follow-up（約 74 本）と、ガード・TPL の行（約 71 本）だった（本文のキーワードで分けた概数）
- 同じ期間に 48 本の PR が `## For Reviewers` に 99 項目を載せた。製品の挙動・仕様を問うものは約 35 項目で、残りは TPL・ガードの扱い（約 28）、Design Doc とのずれと ADR に何を書くか（約 20）、PR の分け方とプロセスの運用（約 16）だった。同じ問いが PR をまたいで繰り返されている（#3772 と #3774 はどちらも「ガードが見つけた挙動の修正をガードの PR で出すか分けるか」を問うた）
- `/pr-verify` も、却下・先送りした指摘を「そのまま受け入れてよいか」と kompiro に聞く。記録された判断 82 件のうち 30 件あまりは、ローカルレビューの指摘の却下・後回しへの答えだった
- ADR は、kompiro がある 1 件で決めたことを残している。次に似た問いが来たとき Claude が kompiro に聞かずに決めてよいかを書いた ADR は無いので、同じ種類の問いがまた kompiro に届く

判断を Claude に委ねれば問いは減る。一方で kompiro には「Claude の決めたことが自分の方針や考え方に沿っているか分からない」という不安がある。本 doc は、委ねる範囲と従う原則を **kompiro の過去の判断から** 引き出し、沿っているかを kompiro が後から確かめられる形で委ねる方法を決める。

### 規則では再現できない

似た理由に、別の答えが出ている組がある。

| 理由 | 受け入れた | 直させた |
| --- | --- | --- |
| 裏付けの Design Doc の決めたとおりにした | #3765 #12 | #3869 LSP（手順 8） |
| 落ちる側に倒れる誤った失敗 | #3824 #39・#46 | #3824 #28・#29 |
| ガードの届かない範囲を書いて残す | #3868 #4、#3829 | #3824 #16・#20・#21 |

どの線を引いても、過去の判断のいくつかとは食い違う。kompiro の判断はその場の文脈（直す手間、PR の目的との近さ、そのとき何を重く見たか）を含んでいて、規則に畳み切れない。それでも 1 つ傾きははっきりしている。食い違いのほとんどは、Claude が後回し・却下し、kompiro が「直す」に変えた向きだった。逆向き（Claude が直そうとし、kompiro が止めた）は、当てはめた範囲では見当たらない。

## 制約・前提

- kompiro に残すべき判断は残す。B（見た目・配置）と C（公開面の方針）は原則に畳めない。好みと方針そのものだからである
- E は判断ではなく誤りである。F は Claude の判断ではない。どちらも委ねる範囲の話ではないので本 doc では扱わない
- 原則で過去の判断をすべて再現することは目指さない（上の「規則では再現できない」）。原則が外れたときの損が小さい側に外れるように原則を書き、外れは計測で拾う
- 委ねた後も、kompiro が Claude の判断を後から確かめられ、外れたら戻せること。確かめる手間が、いま問いに答える手間より小さいこと
- 原則は kompiro の判断から引き出したものに限る。Claude が新しく考えた原則は、kompiro が読んで合意するまで使わない

## 検討した選択肢

### 案1: 今のまま聞き、問いに推奨を付ける

`## For Reviewers` の各項目に Claude の推奨を書き、kompiro は同意か変更かを答える。

**メリット**

- 規則を変えない。kompiro はすべての判断を見続ける

**デメリット**

- 問いの数は減らない。答える負担が少し軽くなるだけで、kompiro が「判断を求められすぎている」状態は変わらない

### 案2: 過去の判断を再現する細かい規則を書き、一度にすべて任せる

**メリット**

- 問いがすぐに減る

**デメリット**

- 上の表のとおり、似た理由に別の答えが出ているので、規則を細かくしても再現できない。外れがどちら向きに出るかも決まらない

### 案3: 外れが安い側に出る原則を書き、原則ごとに段階的に委ね、一致率で確かめる

原則は「迷ったら直す」側に倒す。記録済みの決定に関わる問いは、今の規則どおり聞く。原則に ID を振り、Claude が決めた判断には当てた ID を PR に残す。kompiro は `/pr-verify` で一覧を見て、違うと思ったものにだけ答え、原則ごとの一致率を数える。

**メリット**

- 外れたときの損が小さい。Claude が余分に直すことはあっても、kompiro が「直す」に変える手間（今いちばん多い食い違い）は減る
- kompiro が見るのは「当てた原則と当て方が合っているか」だけで、判断を一から考え直さなくてよい
- 外れが原則ごとに数字で見える。不安の大きい種類は委ねずに試せる

**デメリット**

- Claude が直す範囲が今より広がり、PR が少し大きくなる
- 原則の ID、PR 本文の節、`pr-verify` の記録、数えるスクリプトと、足すものがある

### 案4: 原則を書かず、Claude が過去の `Decisions by kompiro` を都度引いて似た判断に倣う

**メリット**

- 文書を書く手間が無い

**デメリット**

- 似た判断どうしで答えが割れているので、何に倣うかで結果が変わる。kompiro が読んで合意する対象も、外れたときに直す場所も無い

## 現時点の方針

**案3 を採用する**（kompiro が 2026-11-23 に合意）。kompiro の不安は「沿っているか分からない」ことにあり、過去の判断は規則で再現し切れない。そこで原則を外れの安い側に倒し、外れは一致率の計測で拾う。最初は P1 だけを委ね、P2 は推奨を付けて聞く形で一致を測る。

### 原則

原則は次の順に当てる。先に当たったものが優先する。

1. **P3 に当たる問いは聞く**
2. **記録済みの決定に関わる問いは聞く。** 指摘に従うと記録済みの決定（`docs/process/coderabbit-rounds.md` の定義。裏付けの Design Doc、accepted な ADR、`docs/spec/`、`.claude/rules/`、その PR で kompiro が明示した方針）が変わるとき、または記録済みの決定に沿うことを理由に指摘を却下・後回しにするときは、Claude は決めず、`## For Reviewers` に載せる。Design Doc とのずれも同じ扱いにする（今と同じ）。指摘が書かれた規則（`docs/spec/i18n.md` など）を守っていないと言うだけで、規則を変えずに直せるなら、ここではなく P1 で直す（#3837）。Issue に書いたスコープは、ここでは記録済みの決定に数えない（P1 で扱う）
3. **TPL の marker の問いは P2 に従い、推奨を付けて聞く**
4. **それ以外のレビューの指摘は P1 で決める。** 指摘ではない問いで、ここまでのどれにも当たらないものは聞く（P3 の最後の項目）

#### P1: 当たっている指摘は、迷ったらこの PR で直す

指摘が述べる事実が正しく、それがコード・テスト・文書の主張か、書かれた規則に反しているなら、この PR で直す。差分の hunk の外か、PR の前からあったか、Issue に書いたスコープの外かは問わない。

後回し（Issue に回す）にしてよいのは、次のどれかに **はっきり** 当たるときだけである。当たるか迷ったら直す。どれに当たるかを対応欄に書く。

- **P1a** PR が変えていないところの問題か、PR の目的に関わらない問題（#3882）。対象の外の環境の問題もここに入れる（#3805）
- **P1b** 指摘が求めるのが欠陥を直すことではなく、機能を広げることである。ガードがたどる範囲を広げる、規則を厳しくする、など（#3824 の直接の import、#3833 の container）。直し方が複数あって、どれを選ぶかに見た目や方針の選択が要るときは P3 で聞く（#3888）
- **P1c** 別のモジュール・段階・repo に持ち主がある（#3828、#3820）
- **P1d** 別の PR のマージを待つ（#3829）
- **P1e** スライスを分けた計画で、後のスライスに入る。計画が Design Doc に書かれているなら規則 2 に当たるので、P1e が使えるのは Design Doc の無い計画（Issue の `## Slice status` など）に限る。当てはめた範囲に例は無い

却下してよいのは、次のどれかに当たるときだけである（**P1f**）。

- 指摘が述べる事実が誤っている。誤りはコードの挙動（テストか再現）で示す。設計の読み方の違いは誤りに数えない（#3833、#3828）
- 指摘の事実は正しいが、何の主張にも規則にも反していない（#3874 #1）

「既存の挙動と揃える」「ガードからは見えないと書いておく」「無害」「出力が変わらない」は、それだけでは後回しや却下の理由にしない。直す手間が大きいときは、手間を書いて後回しにする（P1b と同じ扱い）。

外れは「余分に直す」側にだけ出る。余分に直した PR は少し大きくなるが、kompiro が答えを変える手間は生まない。#3829 と #3868 の指摘は、ガードの届かない範囲を広げる P1 の問いとしてここに数え、P2（marker を付けるか）の根拠には For Reviewers で答えた marker の判断だけを数える。

#### P2: TPL の marker（委ねない。推奨を付けて聞く）

根拠は D の 2 件と、受け入れた #3829・#3868・#3805、#3832 の item 4・6・7 を残す判断、#3833 の × ボタンを除外して TPL-1399 item 3 に follow-up で marker を付ける判断と少ない。D の 2 件では kompiro は、ガードが届かない範囲を TPL に書いたうえで marker を付けた。これは `docs/test-perspectives/README.md` の「迷ったら印を付けない」と向きが逆である。#3868（parser の手前だけ届かないガードに marker を付けない）と #3829・#3832（届かない経路があるガードに marker を付ける）を分ける線も、まだ書けない。#3812 は届く範囲ではなくリリースの時期で決めた判断なので根拠に数えない。

当面は委ねない。`## For Reviewers` に推奨と根拠を書いて聞き、一致を測る（kompiro が 2026-11-23 に合意）。README との食い違いは、原則を書けるだけの判断が溜まったときに README の側を直すかどうかと合わせて決める。

#### P3: kompiro に残す問い

次の問いは Claude が決めず、`## For Reviewers` に載せる。

- 見た目・配置の設計（B）。AT の文と描画が食い違い、どちらに合わせるかが見た目の選択になるときもここに入る（#3888）
- 公開面・許可リストの方針（C）
- 言語仕様と互換性（言語のバージョン、experimental か stable か、新しい診断を patch で出すか）
- セキュリティの境界を弱めるか変える答え。境界のファイルへの指摘を後回しにする・却下するときを含む。境界の PR でも、指摘どおりに直す判断は P1 で決めてよい
- 取り消しにくい判断（リリース、外部に出る操作、データの移行）
- どの原則にも当たらない問い

### 委ね方

- **Claude が決めたことは PR に残す。** PR 本文に `## Decided by Claude` 節を置く。折りたたみの形は #3875 で決める PR 本文の節の形に合わせる。項目ごとに、問い・選んだ答え・当てた原則の ID・根拠（指摘やコードへのリンク）を書く。ローカルレビューの記録の対応欄（`declined: …` `→ #N`）にも、当てた ID を書く（例: `→ #3900 (P1a)`）
- **`## For Reviewers` に載せるのは、P3 の問い、記録済みの決定に関わる問い、まだ委ねていない原則（当面は P2）の問いだけにする**
- **kompiro が確かめる。** `/pr-verify` は、原則の ID を付けた却下・後回しを「受け入れてよいか」と 1 件ずつ聞くのをやめ、`## Decided by Claude` 節と合わせて一覧で見せる。kompiro は違うと思った項目に答え、最後に一覧全体について「残りはこのとおりでよい」と答える
- **記録に「Claude の案と同じか違うか」を残す。** `/pr-verify` は一覧の項目と聞いた問いを `Decisions by kompiro` の記録に残し、`[change]`（この PR に変更を求めた）とは別に、Claude の案と同じなら `agree`、違えば `differ` を付ける。原則の ID を持つ項目には ID も残す。答えの無い項目を `agree` にするのは、kompiro が一覧全体に「残りはこのとおりでよい」と答えたときだけである。その答えが無ければ、答えの無い項目は記録に入れず、同意にも数えない
- **原則ごとに一致を数える。** 数えるのは記録に残った、原則の ID を持つ項目だけである（`/pr-verify` を通らずにマージした PR の判断は数えない）。原則ごとに、記録のコメントの時刻順で PR をまたいだ直近 10 件を見る。委ねた原則では、その 10 件のうち `differ` が 2 件以上になったら、その原則を「聞く」に戻し、違った判断を根拠に文面を直す。まだ委ねていない原則では、記録が 10 件以上溜まり、直近 10 件の `differ` が 1 件以下なら委ねる段階に上げる。上げ下げは kompiro が決め、本 doc の昇格先 ADR に追記する（閾値は kompiro が 2026-11-23 に合意）
- **原則は月次の見直しで足す。** 毎月の見直しで、Claude が前月の `differ` の付いた判断のうち、どの原則にも当たらないものを種類ごとにまとめ、原則の候補として並べる。採るかどうかは kompiro が決め、採った原則は「聞く」段階から始める（kompiro が 2026-11-23 に合意）
- **原則と委ね方の置き場所は新しいトピック `docs/process/decisions.md` にする。** `docs/process/review.md` の「指摘の重大度と対応」と「High の PR で人間が読むもの」から指し、`docs/process.md`「規約の所在」の表に行を足す。review.md はすでに長く、原則の上げ下げを 1 か所で追えるようにするためである（kompiro が 2026-11-23 に合意）

### 既存の規則との衝突の解き方

- `docs/process/review.md`「指摘の重大度と対応」の「PR の差分の外への指摘は直さず、Issue にする」（ADR-3286）を P1 に置き換える。`tier.ts in-diff` の判定は P1a の手がかりの 1 つとして残し、それだけでは決めない
- 同じ規則を写した 2 つの skill も合わせて直す。`.claude/skills/coderabbit-converge/SKILL.md` のラウンドの手順の「差分の外」と、`.claude/skills/branch-review/SKILL.md` の「（差分外）」の扱いである。branch-review の判定の規則（「以前から」か「（差分外）」だけの Critical / Major は「要修正」にしない）も、P1 に合わせて「当たっている指摘は原因と場所によらず直す対象」に変える
- `docs/process/coderabbit-rounds.md`「人間に確認する指摘の判定」は残し、2 つ書き足す。P1 で直す修正は「Issue に書いたスコープの拡大」に数えないこと。記録済みの決定に沿うことを理由に指摘を却下・後回しにするときも人間に確認すること（今は「従うと決定が変わる」ときだけを問う）
- `docs/process/review.md`「High の PR で人間が読むもの」の「作成者が kompiro に決めてほしいこと」を、P3、記録済みの決定に関わる問い、まだ委ねていない原則の問いに限る
- `.claude/skills/pr-verify/SKILL.md` 手順 6 の「却下・先送りした指摘をそのまま受け入れてよいか」を、原則の ID を持たない却下・後回しに限る

### 実装の指針

1. `docs/process/decisions.md` を足して原則と委ね方を書き、`docs/process/review.md`・`docs/process/coderabbit-rounds.md` の該当箇所を書き換えて指す。`docs/process.md`「規約の所在」の表に行を足す（発火条件: 指摘の対応を決めるとき、`## For Reviewers` 節を書くとき）。`docs/process.md` は予算（16,384 バイト）まで 12 バイトしか残っていないので、同じ PR で process.md のほかの文を詰めて行の分を空ける。`pnpm lint:process-index` が通ること
2. `.claude/skills/coderabbit-converge/SKILL.md` と `.claude/skills/branch-review/SKILL.md` の「差分の外」の扱いと判定の規則を P1 に合わせる
3. PR 本文の `## Decided by Claude` 節の形を決め、`scripts/review/local-review-record.ts` の対応欄が原則の ID を持てるようにする（今の `→ #N` の正規表現は `(P1a)` を拒む）
4. `.claude/skills/pr-verify/SKILL.md`: 原則の ID を持つ判断を一覧で見せ、すべての項目を原則の ID と `agree` / `differ`（と、今どおりの `[change]`）を付けて記録する
5. 記録から原則ごとの直近 10 件と `differ` を数えるスクリプトを足す（#3380 の計測にも使う）
6. AT: 自動で判定できるものだけを置く。`## Decided by Claude` 節の形と、対応欄の原則 ID の書式を検査で確かめる
7. ADR 昇格: 実装の後、本 doc を ADR-3896 に昇格する。ADR-3286 の本文は変えない（`.claude/rules/adr.md`「既存 ADR を覆すとき」）。ADR-3286 のうち「差分の外は Issue」の 1 項目だけを改めることは、ADR-788 の関係のどれにもちょうどは当たらない（`supersedes` は ADR-3286 の全体を覆い、`refines` は抽象から具体、`related_to` は意思決定に影響しない関係）。昇格の時に、ADR-3896 の本文に改める項目を名指しして近い関係を選ぶか、一部を改める関係を adr-tools に足すかを決める

### 影響範囲・マイグレーション

- kompiro への影響: `## For Reviewers` の項目と `/pr-verify` の 1 件ずつの問いが減り、代わりに原則の ID 付きの一覧を見て、違うものにだけ答える。記録済みの決定に関わる問いと P3 の問いは今と同じく届く
- PR への影響: Claude が直す範囲が広がり、PR が少し大きくなる
- Issue への影響: P1 で直す指摘が Issue にならなくなる。A のうち #3874 の 2 件は後回しのために #3872・#3873 を起票していたが、P1 があれば起票されなかった
- 既存の PR: 実装の PR のマージより前に作られた PR には求めない

## 背景・課題

kompiro に判断を求める量が多すぎ、Issue も増え続けている。

- 10/26〜11/22 の 4 週間で Issue を 202 本起票し、閉じたのは 152 本。open は 122 本ある。多くは作業の副産物で、PR やレビューの途中で見つけた follow-up（約 74 本）と、ガード・TPL の行（約 71 本）だった（本文のキーワードで分けた概数）
- 同じ期間に 48 本の PR が `## For Reviewers` に 99 項目を載せた。製品の挙動・仕様を問うものは約 35 項目で、残りは TPL・ガードの扱い（約 28）、Design Doc とのずれと ADR に何を書くか（約 20）、PR の分け方とプロセスの運用（約 16）だった。同じ問いが PR をまたいで繰り返されている（#3772 と #3774 はどちらも「ガードが見つけた挙動の修正をガードの PR で出すか分けるか」を問うた）
- `/pr-verify` も、却下・先送りした指摘を「そのまま受け入れてよいか」と kompiro に聞く。記録された判断 82 件のうち 30 件あまり（ローカルレビューの指摘の却下・後回しへの答え）がこの問いだった
- ADR は、kompiro がある 1 件で決めたことを残している。次に似た問いが来たとき Claude が kompiro に聞かずに決めてよいかを書いた ADR は無いので、同じ種類の問いがまた kompiro に届く

判断を Claude に委ねれば問いは減る。一方で kompiro には「Claude の決めたことが自分の方針や考え方に沿っているか分からない」という不安がある。本 doc は、委ねる範囲と従う原則を **kompiro の過去の判断から** 引き出し、沿っているかを kompiro が後から確かめられる形で委ねる方法を決める。

### 読み取れる線

A の 9 件を「PR が持ち込んだかどうか」では分けられない。#3874 の 2 件は PR の前からあった。逆に #3886 や #3824 の後回しは PR が持ち込んだ制約だったが、kompiro は受け入れた。Claude が後回し・却下した理由も「PR の前からある」「既存の挙動と揃える」「ガードからは見えないと書いておく」「指摘の読み方が違う」と様々で、kompiro はどれも理由として認めなかった。

A と受け入れた例を分けているのは次の 2 つである。

1. **指摘が述べる事実が正しく、それがコード・テスト・文書の主張や書かれた規則に反しているか。** #3833 と #3828 は、指摘の述べる挙動（caption を拒む、古い場所を指す）は正しく、Claude は設計の読み方で却下した。kompiro は直させた。#3824 #39〜#46 は、落ちるのはまず使われない構文だけで、落ちる側に倒れるので受け入れた
2. **PR の目的に関わるか。** #3874 の override と test は、PR が上げた依存（jsdom）と、そのために変えたテストの中の問題だった。#3832 の cache は同じファイルにあったが、PR の目的（catch-all の経路のガード）とは関わらない。差分の hunk の内外や、PR の前からあったかどうかは、どちらにも効いていない

そのうえで、直すのに新しい選択が要るもの（見た目のトレードオフ、合意した範囲を広げること、規則を厳しくすること）は、PR の目的に関わっていても後回しにしてよかった。

## 制約・前提

- kompiro に残すべき判断は残す。B（見た目・配置）と C（公開面の方針）は原則に畳めない。好みと方針そのものだからである
- E は判断ではなく誤りである。F は Claude の判断ではない。どちらも委ねる範囲の話ではないので本 doc では扱わない
- 委ねた後も、kompiro が Claude の判断を後から確かめられ、外れたら戻せること。確かめる手間が、いま問いに答える手間より小さいこと
- 原則は kompiro の判断から引き出したものに限る。Claude が新しく考えた原則は、kompiro が読んで合意するまで使わない

## 検討した選択肢

### 案1: 今のまま聞き、問いに推奨を付ける

`## For Reviewers` の各項目に Claude の推奨を書き、kompiro は同意か変更かを答える。

**メリット**

- 規則を変えない。kompiro はすべての判断を見続ける

**デメリット**

- 問いの数は減らない。答える負担が少し軽くなるだけで、kompiro が「判断を求められすぎている」状態は変わらない

### 案2: 原則を書き、該当する判断を一度にすべて Claude に任せる

**メリット**

- 問いがすぐに減る

**デメリット**

- 原則ごとの当たり外れが見えない。D（TPL の marker）のように根拠が数件しかない種類も同じ重みで任せることになり、kompiro の不安に答えていない

### 案3: 原則ごとに段階的に委ね、記録と `[change]` の数で確かめる

原則に ID を振り、Claude が決めた判断には当てた ID を PR に残す。kompiro は `/pr-verify` で一覧を見て、違うと思ったものにだけ `[change]` を付け、原則ごとの一致率を数える。根拠の厚い原則から委ね、外れが続いた原則は「聞く」に戻して文面を直す。

**メリット**

- kompiro が見るのは「当てた原則と当て方が合っているか」だけで、判断を一から考え直さなくてよい
- 外れが原則ごとに数字で見える。不安の大きい種類は委ねずに試せる

**デメリット**

- 原則の ID、PR 本文の節、`pr-verify` の記録、数えるスクリプトと、足すものがある

### 案4: 原則を書かず、Claude が過去の `Decisions by kompiro` を都度引いて似た判断に倣う

**メリット**

- 文書を書く手間が無い

**デメリット**

- 何に倣ったかが判断ごとにばらつき、kompiro が読んで合意する対象が無い。外れたときに直す場所も無い

## 比較

| 観点 | 案1 | 案2 | 案3 | 案4 |
| --- | --- | --- | --- | --- |
| kompiro に届く問いの数 | 減らない | 大きく減る | 原則が委ねられるにつれ減る | 減る |
| 沿っているかを確かめられるか | 全件見る | 見えない | 原則ごとの一致率で見える | 見えない |
| 外れたときに直す場所 | 不要 | 原則の文面 | 原則の文面と、委ねる段階 | 無い |
| 足す仕組み | 無し | 文面のみ | 文面・節・記録・集計 | 無し |

## 現時点の方針

**案3 を採用する。** kompiro の不安は「沿っているか分からない」ことにあるので、原則を kompiro の過去の判断から引き出し、委ねた後も原則ごとに外れを数え続ける。最初は根拠の最も厚い P1 だけを委ね、P2 は推奨を付けて聞く形で一致を測る。

### 原則

#### P1: 当たっていて、PR の目的に関わる指摘は、この PR で直す（根拠: A の 9 件と、受け入れた後回し・却下の 20 件あまり）

指摘が次の 2 つを満たすなら、新しい選択を要さないかぎり、この PR で直す。差分の hunk の外か、PR の前からあったか、Issue に書いたスコープの外かは問わない。

1. 指摘が述べる事実が正しく、それがコード・テスト・文書の主張か、書かれた規則に反している
2. PR の目的に関わる。PR が足したもの、PR の変更が頼るか影響を与えるもの（上げた依存、そのために変えたテスト、移したことで古くなった参照）、PR を裏付ける Design Doc の手順のどれかに当たる

「既存の挙動と揃える」「ガードからは見えないと書いておく」「設計の読み方が違う」は、指摘の述べる事実が正しいかぎり、後回しや却下の理由にならない。

後回し（Issue に回す）にしてよいのは、次のどれかに当たるときである。どれに当たるかを対応欄に書く。

- **P1a** PR の目的に関わらない（同じファイルにあってもよい）
- **P1b** 直すには新しい選択が要る。合意した範囲を広げる、規則を厳しくする、など。見た目のトレードオフは P3 なので kompiro に聞く
- **P1c** 別のモジュール・段階・repo に持ち主がある
- **P1d** 別の PR のマージを待つ
- **P1e** 裏付けの Design Doc がスライスとして後に回した

却下してよいのは、次のどれかに当たるときである（**P1f**）。

- 指摘が述べる事実が誤っている。誤りはコードの挙動（テストか再現）で示す。設計の読み方の違いは誤りに数えない
- 無害である。PR が足したガードの誤った失敗なら、まず使われない入力でだけ起き、落ちる側に倒れ、落ちた行を示すものに限る。よくある入力で起きる誤った失敗は直す
- 裏付けの Design Doc が受け入れた制約である

上の線で過去の判断を分け直すと、A の 9 件はすべて「直す」に、受け入れた後回し・却下はすべて P1a〜P1f に当たる（ただし #3886 の 3 件は P3 の見た目に当たり、今と同じく kompiro に聞く）。

#### P2: TPL の marker（委ねない。推奨を付けて聞く）

根拠は D の 2 件と、受け入れた #3829・#3868・#3805 の 3 件と少ない。D の 2 件では kompiro は、ガードが届かない範囲を TPL に書いたうえで marker を付けた。これは `docs/test-perspectives/README.md` の「迷ったら印を付けない」と向きが逆である。#3868（parser の手前だけ届かないガードに marker を付けない）と #3829・#3832（届かない経路があるガードに marker を付ける）を分ける線も、まだ書けない。#3812 は届く範囲ではなくリリースの時期で決めた判断なので根拠に数えない。

当面は委ねない。`## For Reviewers` に推奨と根拠を書いて聞き、一致を測る（kompiro が 2026-11-23 に合意）。README との食い違いは、原則を書けるだけの判断が溜まったときに README の側を直すかどうかと合わせて決める。

#### P3: kompiro に残す問い

次の問いは、原則に当たっても Claude が決めず、`## For Reviewers` に載せる。

- 見た目・配置の設計（B）
- 公開面・許可リストの方針（C）
- 言語仕様と互換性（言語のバージョン、experimental か stable か、新しい診断を patch で出すか）
- セキュリティの境界を弱めるか変える答え。境界のファイルへの指摘を後回しにする・却下するときを含む。境界の PR でも、指摘どおりに直す判断は P1 で決めてよい
- 取り消しにくい判断（リリース、外部に出る操作、データの移行）
- どの原則にも当たらない問い

### 委ね方

- **Claude が決めたことは PR に残す。** PR 本文に `## Decided by Claude` 節を置く。折りたたみの形は #3875 で決める PR 本文の節の形に合わせる。項目ごとに、問い・選んだ答え・当てた原則の ID・根拠（指摘やコードへのリンク）を書く。ローカルレビューの記録の対応欄（`declined: …` `→ #N`）にも、当てた ID を書く（例: `→ #3900 (P1a)`）
- **`## For Reviewers` に載せるのは、P3 の問いと、まだ委ねていない原則（当面は P2）の問いだけにする**
- **kompiro が確かめる。** `/pr-verify` は、原則の ID を付けた却下・後回しを「受け入れてよいか」と 1 件ずつ聞くのをやめ、`## Decided by Claude` 節と合わせて一覧で見せる。kompiro は違うと思った項目にだけ答える。`/pr-verify` は一覧のすべての項目を `Decisions by kompiro` の記録に、原則の ID と「受け入れ」か `[change]` かを付けて残す。kompiro が読まずに過ぎた判断は記録に入らないので、同意には数えない
- **原則ごとに一致を数える。** 数えるのは `Decisions by kompiro` の記録に残った、原則の ID を持つ項目だけである（`/pr-verify` を通らずにマージした PR の判断は数えない）。原則ごとに、記録のコメントの時刻順で PR をまたいだ直近 10 件を見る。委ねた原則では、その 10 件のうち `[change]` が 2 件以上になったら、その原則を「聞く」に戻し、変えられた判断を根拠に文面を直す。まだ委ねていない原則では、直近 10 件の `[change]` が 1 件以下なら委ねる段階に上げる。上げ下げは kompiro が決め、本 doc の昇格先 ADR に追記する（閾値は kompiro が 2026-11-23 に合意）
- **原則は月次の見直しで足す。** 毎月の見直しで、Claude が前月の `[change]` の付いた判断のうち、どの原則にも当たらないものを種類ごとにまとめ、原則の候補として並べる。採るかどうかは kompiro が決め、採った原則は「聞く」段階から始める（kompiro が 2026-11-23 に合意）
- **原則と委ね方の置き場所は新しいトピック `docs/process/decisions.md` にする。** `docs/process/review.md` の「指摘の重大度と対応」と「High の PR で人間が読むもの」から指し、`docs/process.md`「規約の所在」の表に行を足す。review.md はすでに長く、原則の上げ下げを 1 か所で追えるようにするためである（kompiro が 2026-11-23 に合意）

### 既存の規則との衝突の解き方

- `docs/process/review.md`「指摘の重大度と対応」の「PR の差分の外への指摘は直さず、Issue にする」（ADR-3286）を P1 に置き換える。`tier.ts in-diff` の判定は手がかりの 1 つとして残し、それだけでは決めない
- 同じ規則を写した 2 つの skill も合わせて直す。`.claude/skills/coderabbit-converge/SKILL.md` のラウンドの手順の「差分の外」と、`.claude/skills/branch-review/SKILL.md` の「（差分外）」の扱いである。branch-review の原因の欄（「この PR」「以前から」）は、P1 の判定では PR の目的に関わるかどうかの手がかりとして読む
- `docs/process/coderabbit-rounds.md`「人間に確認する指摘の判定」で、P1 で直す修正は「Issue に書いたスコープの拡大」に数えない、と書き足す
- `docs/process/review.md`「High の PR で人間が読むもの」の「作成者が kompiro に決めてほしいこと」を、P3 と、まだ委ねていない原則の問いに限る
- `.claude/skills/pr-verify/SKILL.md` 手順 6 の「却下・先送りした指摘をそのまま受け入れてよいか」を、原則の ID を持たない却下・後回しに限る

### 実装の指針

1. `docs/process/decisions.md` を足して原則と委ね方を書き、`docs/process/review.md`・`docs/process/coderabbit-rounds.md` の該当箇所を書き換えて指す。`docs/process.md`「規約の所在」の表に行を足す（発火条件: 指摘の対応を決めるとき、`## For Reviewers` 節を書くとき）。`docs/process.md` は予算（16,384 バイト）まで 12 バイトしか残っていないので、同じ PR で process.md のほかの文を詰めて行の分を空ける。`pnpm lint:process-index` が通ること
2. `.claude/skills/coderabbit-converge/SKILL.md` と `.claude/skills/branch-review/SKILL.md` の「差分の外」の扱いを P1 に合わせる
3. PR 本文の `## Decided by Claude` 節の形を決め、`scripts/review/local-review-record.ts` の対応欄が原則の ID を持てるようにする（今の `→ #N` の正規表現は `(P1a)` を拒む）
4. `.claude/skills/pr-verify/SKILL.md`: 原則の ID を持つ判断を一覧で見せ、すべての項目を原則の ID と「受け入れ」/`[change]` を付けて記録する
5. `Decisions by kompiro` の記録から原則ごとの直近 10 件と `[change]` を数えるスクリプトを足す（#3380 の計測にも使う）
6. AT: 自動で判定できるものだけを置く。`## Decided by Claude` 節の形と、対応欄の原則 ID の書式を検査で確かめる
7. ADR 昇格: 実装の後、本 doc を ADR-3896 に昇格する。ADR-3286 の「差分の外は Issue」の決定を改めることは、ADR-3896 の frontmatter に `refines: [ADR-3286]` と書いて示し、ADR-3286 の本文は変えない（`.claude/rules/adr.md`「既存 ADR を覆すとき」）

### 影響範囲・マイグレーション

- kompiro への影響: `## For Reviewers` の項目と `/pr-verify` の 1 件ずつの問いが減り、代わりに原則の ID 付きの一覧を見て、違うものにだけ答える
- Issue への影響: P1 で直す指摘が Issue にならなくなる。A の 9 件のうち 3 件は後回しのために Issue を起票していた（#3838、#3872、#3873）。P1 があれば起票されなかった
- 既存の PR: 実装の PR のマージより前に作られた PR には求めない

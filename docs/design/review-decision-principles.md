## 背景・課題

kompiro に判断を求める量が多すぎ、Issue も増え続けている。

- 10/26〜11/22 の 4 週間で Issue を 202 本起票し、閉じたのは 152 本。open は 122 本ある。多くは作業の副産物で、PR やレビューの途中で見つけた follow-up（約 74 本）と、ガード・TPL の行（約 71 本）だった（本文のキーワードで分けた概数）
- 同じ期間に 48 本の PR が `## For Reviewers` に 99 項目を載せた。製品の挙動・仕様を問うものは約 35 項目で、残りは TPL・ガードの扱い（約 28）、Design Doc とのずれと ADR に何を書くか（約 20）、PR の分け方とプロセスの運用（約 16）だった。同じ問いが PR をまたいで繰り返されている（#3772 と #3774 はどちらも「ガードが見つけた挙動の修正をガードの PR で出すか分けるか」を問うた）
- ADR は、kompiro がある 1 件で決めたことを残している。次に似た問いが来たとき Claude が kompiro に聞かずに決めてよいかを書いた ADR は無いので、同じ種類の問いがまた kompiro に届く

判断を Claude に委ねれば問いは減る。一方で kompiro には「Claude の決めたことが自分の方針や考え方に沿っているか分からない」という不安がある。本 doc は、委ねる範囲と従う原則を **kompiro の過去の判断から** 引き出し、沿っているかを kompiro が後から確かめられる形で委ねる方法を決める。

## 制約・前提

- kompiro に残すべき判断は残す。B（見た目・配置）と C（公開面の方針）は原則に畳めない。好みと方針そのものだからである
- E は判断ではなく誤りである。委ねる範囲の話ではなく、Claude が書く文の確かめ方の話なので本 doc では扱わない
- 委ねた後も、kompiro が Claude の判断を後から確かめられ、外れたら戻せること。確かめる手間が、いま問いに答える手間より小さいこと
- 原則は kompiro の判断から引き出したものに限る。Claude が新しく考えた原則は、kompiro が読んで合意するまで使わない
- Issue の流入に上限を置くこと（見つけたものを台帳に貯めるなど）は本 doc の範囲の外とする。P1 で後回しが減ることの効果を見てから別に決める

## 検討した選択肢

### 案1: 今のまま聞き、問いに推奨を付ける

`## For Reviewers` の各項目に Claude の推奨を書き、kompiro は同意か変更かを答える。

**メリット**

- 規則を変えない。kompiro はすべての判断を見続ける

**デメリット**

- 問いの数は減らない。答える負担が少し軽くなるだけで、kompiro が「判断を求められすぎている」状態は変わらない

### 案2: 原則を書き、該当する判断を一度にすべて Claude に任せる

**メリット**

- 問いがすぐに減る

**デメリット**

- 原則ごとの当たり外れが見えない。D（TPL の marker）のように根拠が 6 件しかない種類も同じ重みで任せることになり、kompiro の不安に答えていない

### 案3: 原則ごとに段階的に委ね、記録と `[change]` の数で確かめる

原則に ID を振り、Claude が決めた判断には当てた ID を PR に残す。kompiro は違うと思ったものにだけ `[change]` を付け、原則ごとの一致率を数える。根拠の厚い原則から委ね、外れが続いた原則は「聞く」に戻して文面を直す。

**メリット**

- kompiro が見るのは「当てた原則と当て方が合っているか」だけで、判断を一から考え直さなくてよい
- 外れが原則ごとに数字で見える。不安の大きい種類は委ねずに試せる

**デメリット**

- 原則の ID、PR 本文の節、`pr-verify` の記録、数えるスクリプトと、足すものがある

### 案4: 原則を書かず、Claude が過去の `Decisions by kompiro` を都度引いて似た判断に倣う

**メリット**

- 文書を書く手間が無い

**デメリット**

- 何に倣ったかが判断ごとにばらつき、kompiro が読んで合意する対象が無い。外れたときに直す場所も無い

## 比較

| 観点 | 案1 | 案2 | 案3 | 案4 |
| --- | --- | --- | --- | --- |
| kompiro に届く問いの数 | 減らない | 大きく減る | 原則が委ねられるにつれ減る | 減る |
| 沿っているかを確かめられるか | 全件見る | 見えない | 原則ごとの一致率で見える | 見えない |
| 外れたときに直す場所 | 不要 | 原則の文面 | 原則の文面と、委ねる段階 | 無い |
| 足す仕組み | 無し | 文面のみ | 文面・節・記録・集計 | 無し |

## 現時点の方針

**案3 を採用する。** kompiro の不安は「沿っているか分からない」ことにあるので、原則を kompiro の過去の判断から引き出し、委ねた後も原則ごとに外れを数え続ける。最初は根拠の最も厚い P1 だけを委ね、P2 は推奨を付けて聞く形で一致を測る。

### 原則

#### P1: この PR が持ち込んだものはこの PR で直す（根拠: A の 10 件と、受け入れた後回し・却下の 20 件あまり）

指摘が次のどれかに当たるなら、差分の hunk の外でも、Issue に書いたスコープの外でも、この PR で直す。

- この PR が足したコード・テスト・ガード・UI の誤り。ガードの見落としと誤検知を含む
- この PR の変更が引き起こした影響。依存の解決が変わった、移したことで参照が古くなった、など
- この PR を裏付ける Design Doc の手順のうち、実装し損ねたところ

「既存の挙動と揃える」「差分の hunk の外」「Issue のスコープの外」は、それだけでは後回しや却下の理由にならない。

後回し（Issue に回す）にしてよいのは次のどれかに当たるときだけである。どれに当たるかを対応欄に書く。

- **P1a** PR の前からあり、この PR が悪化させていない
- **P1b** 別のモジュール・段階・repo に持ち主がある
- **P1c** 別の PR のマージを待つ
- **P1d** 裏付けの Design Doc がスライスとして後に回した

却下してよいのは、誤検知、無害、裏付けの Design Doc が受け入れた制約のどれかに当たるときである（**P1e**）。

#### P2: ガードが item の主な失敗の形で落ちるなら marker を付け、届かない範囲を TPL に書く（根拠: D の 2 件と、受け入れた 4 件）

- ガードが、item が防ぎたい主な失敗の形で落ちるなら marker を付け、ガードが届かない範囲を TPL の本文に書く（#3832、#3813、#3829）
- 主な失敗の形に届かないなら、marker を付けず関連テストのままにする（#3868、#3805、#3812）

根拠が 6 件と薄いので、当面は委ねない。`## For Reviewers` に推奨と P2 を書いて聞き、一致を測る（kompiro が 2026-11-23 に合意）。

#### P3: kompiro に残す問い

次の問いは、原則に当たっても Claude が決めず、`## For Reviewers` に載せる。

- 見た目・配置の設計（B）
- 公開面・許可リストの方針（C）
- 言語仕様と互換性（言語のバージョン、experimental か stable か、新しい診断を patch で出すか）
- セキュリティの境界
- 取り消しにくい判断（リリース、外部に出る操作、データの移行）
- どの原則にも当たらない問い

### 委ね方

- **Claude が決めたことは PR に残す。** PR 本文に `## Decided by Claude` 節を置く（`<details>` で折りたたむ）。項目ごとに、問い・選んだ答え・当てた原則の ID・根拠（指摘やコードへのリンク）を書く。ローカルレビューの記録の対応欄（`declined: …` `→ #N`）にも、当てた ID を書く（例: `→ #3900 (P1a)`）
- **`## For Reviewers` に載せるのは、P3 の問いと、まだ委ねていない原則（当面は P2）の問いだけにする**
- **kompiro が確かめる。** `/pr-verify` は `## Decided by Claude` 節を kompiro に見せる。kompiro は違うと思った項目にだけ答え、今と同じく `[change]` を付けて記録する。記録には当てた原則の ID も残す
- **原則ごとに一致を数える。** 委ねた原則では、直近 10 件のうち `[change]` が 2 件以上になったら、その原則を「聞く」に戻し、変えられた判断を根拠に文面を直す。まだ委ねていない原則では、直近 10 件の `[change]` が 1 件以下なら委ねる段階に上げる。上げ下げは kompiro が決め、本 doc の昇格先 ADR に追記する（閾値は kompiro が 2026-11-23 に合意）
- **原則は月次の見直しで足す。** 毎月の見直しで、Claude が前月の `[change]` の付いた判断のうち、どの原則にも当たらないものを種類ごとにまとめ、原則の候補として並べる。採るかどうかは kompiro が決め、採った原則は「聞く」段階から始める（kompiro が 2026-11-23 に合意）
- **原則と委ね方の置き場所は新しいトピック `docs/process/decisions.md` にする。** `docs/process/review.md` の「指摘の重大度と対応」と「High の PR で人間が読むもの」から指し、`docs/process.md`「規約の所在」の表に行を足す。review.md はすでに長く、原則の上げ下げを 1 か所で追えるようにするためである（kompiro が 2026-11-23 に合意）

### 既存の規則との衝突の解き方

- `docs/process/review.md`「指摘の重大度と対応」の「PR の差分の外への指摘は直さず、Issue にする」（ADR-3286）を P1 に置き換える。`tier.ts in-diff` の判定は「この PR が持ち込んだか」の手がかりの 1 つとして残し、それだけでは決めない
- `docs/process/coderabbit-rounds.md`「人間に確認する指摘の判定」で、P1 に当たる修正は「Issue に書いたスコープの拡大」に数えない、と書き足す
- `docs/process/review.md`「High の PR で人間が読むもの」の「作成者が kompiro に決めてほしいこと」を、P3 と、まだ委ねていない原則の問いに限る

### 実装の指針

1. `docs/process/decisions.md` を足して原則と委ね方を書き、`docs/process/review.md`・`docs/process/coderabbit-rounds.md` の該当箇所を書き換えて指す。`docs/process.md`「規約の所在」の表に行を足す（発火条件: 指摘の対応を決めるとき、`## For Reviewers` 節を書くとき）。`pnpm lint:process-index` が通ること
2. PR 本文の `## Decided by Claude` 節の形を決め、`scripts/review/local-review-record.ts` の対応欄が原則の ID を持てるようにする
3. `.claude/skills/pr-verify/SKILL.md`: `## Decided by Claude` 節を kompiro に見せ、`Decisions by kompiro` の記録に原則の ID を残す
4. `Decisions by kompiro` のコメントから原則ごとの `[change]` を数えるスクリプトを足す（#3380 の計測にも使う）
5. AT: 自動で判定できるものだけを置く。`## Decided by Claude` 節の形と、対応欄の原則 ID の書式を検査で確かめる
6. ADR 昇格: 実装の後、本 doc を ADR-3896 に昇格し、ADR-3286 の「差分の外は Issue」の決定を一部改める旨を両方に書く

### 影響範囲・マイグレーション

- kompiro への影響: `## For Reviewers` の項目が減り、代わりに折りたたまれた `## Decided by Claude` 節が増える。読むのは任意
- Issue への影響: P1 に当たる指摘が Issue にならなくなる。A の 10 件のうち 3 件は後回しのために Issue を起票していた（#3838、#3872、#3873）。P1 があれば起票されなかった
- 既存の PR: 実装の PR のマージより前に作られた PR には求めない

## 決めないこと

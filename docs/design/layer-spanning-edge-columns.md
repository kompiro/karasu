## 背景・課題

#2598 は「配線の需要が配置に届かない」ことを 4 つのスライスで直している。A / B / C が
merged になり、垂直軸（層間チャネル）は通行量から寸法を得るようになった。残る D の主張は
「層をまたぐエッジは配置段階で横方向の場所を確保しない。だから内部回廊が塞がれば右ガターに
落ちる」である。

Issue はこれを Sugiyama の dummy node で解くと書いている。着手前に dify モデル
（21 の architecture view、1,125 エッジ）で現状を計測したところ、**ガター送りの原因は
Issue が想定した「回廊の取り合い」ではなかった**。

| 指標（dify 21 view、ungrouped） | 値 |
| --- | --- |
| 再配線されたエッジ | 1,051 / 1,125 |
| 外側ガターに落ちたエッジ | **538**（再配線の 51%） |
| うち、空いている内部回廊を他エッジに取られたもの | **5**（nearest-8 の上限を外しても 33） |
| うち、行間バンドに幅 24px 以上の空き列が実在するもの | **243**（ガター送りの 45%） |
| うち、空き列が本当に存在しないもの | **295** |
| ガター経路が理想の中央列経路より余分に走る長さ | 平均 **1,411px** / 本（合計 759k px） |

読み取れることが 3 つある。

**1. 枯渇の原因は競合ではなく幾何。** 1 回廊 1 エッジの `claimed` 制約で回廊を逃したのは
538 本中 5 本しかない。ADR-2598 が垂直軸で見つけた「資源に割り当てが無い」問題とは原因が
違う。水平軸では、そもそも通れる回廊が存在しない。

**2. 45% は「入れない」のではなく「辿り着けない」。** 243 本は、始点の行と終点の行の間の
バンドに幅 24px 以上の空き列が実在する。それでもガターに落ちるのは、`tryCorridorRoute` の
経路形が **両端ともカードの中央高さから横に出る L 字**に固定されているからである。同じ行に
兄弟が 1 つでも間にあれば、その横走りがカードを貫通するので回廊は棄却される。空き列はある
のに、そこへ入る方法が無い。

**3. 残り 295 は列そのものが無い。** 行内のカードは `NODE_GAP`（60px）で詰められ、各 sub-row
は `centerRowsHorizontally` で**独立に**中央寄せされる。行 r の隙間の x と行 r+1 の隙間の x は
揃わない。karasu の配置には「列」という構造が存在せず、Sugiyama の座標割り当てが持つ層をまたぐ
整列が無い。回廊候補（`corridorCandidates`）はカードの左右 ±`GUTTER_GAP`/2 を集めるだけなので、
候補 x は 1,028 本あるのに実際に通れたのは 399 本にとどまる。

補足として、**内部回廊は `frames.length === 0` のビューにしか提供されていない**
（`edge-routing-groups.ts`）。Group-by / boundary frame のあるビューでは内部回廊は最初から
0 本で、上記の計測はすべて内部回廊が提供される最良条件での数字である。

## 現状（インベントリ）

| 観点 | 現状 |
| --- | --- |
| 行内の x 決定 | `placeNodesInLayers` が左から `NODE_GAP` 詰め。その後 `centerRowsHorizontally` が sub-row ごとに独立して中央寄せ |
| 層の折り返し | `wrapLayerIntoRows`（ADR-1737）。1 層が複数 sub-row になる。行序数は sub-row を含めて数える |
| 層内順序 | `forcedLayers !== null`（system view の kind tier、Group-by band）なら宣言順を維持。それ以外（drill-down）でのみ `sortByBarycenter` が走る |
| 内部回廊の候補 | `corridorCandidates(nodes)` = 各カードの左右 ±`GUTTER_GAP`/2。**frames があるビューでは候補 0 本** |
| 内部回廊の経路形 | `tryCorridorRoute`: 両端の側面ポート（中央高さ）→ 垂直回廊 → 側面ポート。回廊は `claimed` により y 範囲が重なる 1 本のみ占有 |
| 候補の試行上限 | `MAX_CORRIDOR_TRIES = 8`（中点から近い順） |
| ガター経路 | `planGutterRoute` / `planMixedRoute`。側面 stub が塞がれた端だけ上下ポート + 隣接チャネル経由に切り替える `mixedEnd` を既に持つ |
| 配置へのフィードバック | `layout()` が幅予算探索（ADR-2593）→ `channelReservations` で行間の追加 gap を測り、必要なら `layoutInner` をもう 1 回だけ実行（ADR-2598）。`placementPasses` は 1 か 2 |
| 行予約のキー | 行序数（`placeNodesInLayers` が返す `rows` の添字）。座標ではなく構造キー |

## 制約・前提

- **決定性**: 同じ入力 → 同じ SVG。候補は入力だけから決まり、既定候補が先頭で、厳密改善のみが
  勝つ（TPL-2593）。
- **floor-first**: 現行の定数で足りるビューは 1 バイトも変わらない。
- **3 パス目を作らない**: ADR-2598 が「1 か 2」と決めた上限を維持する。列の予約は既存の
  2 パス目に合流させる。
- **貫通は重なりより悪い**（TPL-1927）。空間が足りないときはレーンを帯に圧縮し、行へ溢れさせない。
- **dummy node は layout phase の外に出ない**（Issue の受け入れ条件）。`nodeMetadata` /
  deep link / outline / crossing marks / diff / draw.io export のどれからも観測されない。
- **ADR-1737 の grid wrap と共存する**。折り返された層は複数 sub-row を持ち、行が列構造の単位。
- **multi-system root と deploy view は行序数を持たない**（ADR-2598 の「残る限界」）。予約を
  伴わない改善はここでも効く必要がある。
- スコープ外: 幅予算の再探索（ADR-2598 が「探索が選んだものを固定」と決めた線を引き継ぐ）、
  slice E（ポートで終わる run の分離）。

## 検討した選択肢

### 案1: 教科書どおりの Sugiyama dummy node chain

層をまたぐエッジを、通過する層ごとの dummy node に分解し、`sortByBarycenter` の順序決定と
座標割り当てに参加させる。routing は dummy が確保した列を辿る。

**メリット**

- 交差最小化が「後から経路を探す」ではなく「順序を決める」段階で効く。Issue が求めている形そのもの。
- 長いエッジが構造的に列を得る。

**デメリット**

- **karasu の system view では順序決定が走らない。** `forcedLayers`（kind tier）が非 null の層は
  宣言順を維持する設計で、barycenter は明示的に飛ばされる。dummy を足しても順序は動かない。
  効くのは drill-down view だけで、計測した 21 view のうち順序が動くのはその一部にとどまる。
- **ADR-1737 の grid wrap と衝突する。** 層が sub-row に折り返された瞬間、dummy chain がどの
  sub-row に属するかが決まらない。sub-row を選んでも、各 sub-row は独立に中央寄せされるので
  chain の x は行ごとに動き、列にならない。
- **列にするには座標割り当てごと Sugiyama 化する必要がある。** 行の中央寄せを捨てて整列 pass を
  入れることになり、これは ADR-458 が「ツリービューの視認性が落ちる」として却下した左揃え相当の
  見た目変更である。全スナップショットが動く。
- **偽の `LayoutNode` を作ると、下流の全消費者に「これは無視しろ」を配ることになる。** 登録し忘れ
  が 1 つでもあれば deep link や outline に幽霊が出る。TPL-1954 が言う「形でゲートしたパスは
  新しい形を素通りする」と同型の穴を、今度は消費者側に新設することになる。

### 案2: 列を予約する（ADR-2598 の水平版）

dummy node という**オブジェクト**は作らず、その**空間的効果**だけを配置に返す。1 回目の配線で
「行 r のカード i と i+1 の間に幅 w の列が要る」を測り、2 パス目の `placeNodesInLayers` がその
位置に w を挿入する。列の x は、その列を共有する行すべてで揃うように決める。

**メリット**

- ADR-2598 と同じ形（測定 → 構造キーで予約 → 1 回だけ置き直し）。決定性・floor-first・パス数
  上限の議論が済んでいる枠にそのまま乗る。
- 偽ノードが存在しないので「dummy node が layout の外から観測されない」を構造的に満たす。
  受け入れ条件が assertion ではなく型で保証される。
- 行内のカードの相対順序・層割当を変えない。ADR-1859 が却下した「特定のエッジを避けるために
  ノードを動かす」ではなく、ADR-2598 と同じ「通行量から決まる通路の寸法」を返すだけである。

**デメリット**

- 行ごとにカードの並びも幅も違うので、「行をまたいで同じ x」を作るのが自明ではない。挿入位置を
  行ごとに選ぶ規則が要る。
- 2 パス目で幅が変われば中央寄せがずれ、列の実 x が動く。予約は座標ではなく構造キーで持ち、
  実 x は配置後に読み直す必要がある。

### 案3: 到達だけ直す（チャネル進入）

配置には一切触らず、既に空いている列へ **上下ポート + 行間チャネル経由**で入れるようにする。
`mixedEnd` がガター側で既にやっていることを、内部回廊にも適用する。走る先の行間チャネルは
slice A で容量を持っているので、水平の走りはレーンに載る。

**メリット**

- 幅コスト 0 で 243 本（ガター送りの 45%）を回収できる見込み。
- 1 パスのまま。multi-system root と deploy view でも効く（予約を必要としない）。
- 変更は routing 側に閉じる。

**デメリット**

- 列が存在しない 295 本は救えない。

## 比較

| 観点 | 案1 dummy node | 案2 列の予約 | 案3 チャネル進入 |
| --- | --- | --- | --- |
| 回収できるガター送り | 原理上は全部 | 295（案3 と併用） | 243 |
| 幅コスト | 列 + 整列で不明（大） | +4.4%（後述） | 0 |
| 既存スナップショットへの影響 | 全面（中央寄せの廃止） | 予約が入るビューのみ | 経路が変わるビューのみ |
| 決定性の議論 | 新規（整列 pass の tie-break） | ADR-2598 の枠を再利用 | 追加なし |
| 下流消費者への露出 | 偽ノードが全消費者に届く | 無し | 無し |
| system view で効くか | 効かない（順序が固定） | 効く | 効く |

## 現時点の方針

**案3 と案2 を両方実装し、案1 は採らない。** #2611 を sub-issue に分割せず、実装は 1 本の
PR で出す（本 PR は Design Doc と proactive TPL のみで、実装は含まない）。

案1 を却下する決め手は「karasu には列が無い」ではなく「**列を作る場所が Sugiyama と違う**」で
ある。karasu の層内順序は kind tier（system view）と宣言順で決まっており、そこは意図的に
barycenter を外してある。dummy を順序決定に参加させても system view では何も動かず、
drill-down で動かすには行の中央寄せを捨てる必要があって、それは ADR-458 が別の理由で却下した
変更である。dummy node の価値のうち karasu が受け取れるのは**空間の予約**だけで、順序決定への
参加は受け取れない。だから予約だけを実装する。

実装を 2 段に分けるのは、計測が「幅を増やさずに直せる分」と「幅を増やさないと直せない分」をきれいに
分けているからである。

- **第 1 段（案3）到達性** — 既存の空き列にチャネル経由で入る。対象 243 本、幅コスト 0、1 パスのまま。
- **第 2 段（案2）列の予約** — 残り 295 本。同一ターゲットへ入るエッジが 1 列を共有する（P2c-B の
  trunk と同じ規則）前提で、同時に必要な列数のピークは **107**。24px ピッチで幅 **+4.4%**
  （2,568px / 全 21 view の合計幅 58,367px）。1 本ずつ列を与えると +12% になるので、共有は必須。

第 1 段の後に第 2 段の需要を測り直すこと。第 1 段が 243 本を内部に引き込むと、残りが取れる
空き列の分布は変わる。第 2 段の予約量は第 1 段適用後の配線結果から測る。

### 実装の順序（1 PR 内）

#2611 は分割せず 1 本の PR で出す。ただし**実装は 2 段に分け、段と段の間で測り直す**。

| 段 | 内容 | 幅コスト | 対象 |
| --- | --- | --- | --- |
| **第 1 段** 到達性（案3） | 既存の空き列にチャネル経由で入る。配置は変えず 1 パスのまま | 0 | 243 本 |
| **第 2 段** 列の予約（案2） | 残りに列を予約し、既存の 2 パス目に合流させる | +4.4% 見込み | 295 本 |

段を分ける理由は、計測が「幅を増やさずに直せる分」と「幅を増やさないと直せない分」を
分けているからである。**第 1 段の適用後に第 2 段の需要を測り直すこと** — 243 本が内部へ
入ると残りが取れる空き列の分布が変わるので、第 1 段の前に測った 295 本 / ピーク 107 列を
そのまま予約すると過大になる。

第 1 段だけでも図は悪化しない（回廊が取れなければ従来どおりガターに落ちるだけで、経路は
決して長くならない。ADR-968 の「最悪でも現状以上に崩れない」を踏襲）。第 2 段の予約が 0 の
ビューは 1 バイトも変わらない。

### 実装の指針

**第 1 段: 内部回廊へのチャネル進入**

1. `tryCorridorRoute` の進入規則を、側面ポート固定から「側面 stub が空いていればそれ、塞がれて
   いれば上下ポート + 隣接する行間チャネル経由」に広げる。`mixedEnd` がガター側で同じ判断を
   しているので、**同じ関数を回廊にも使う**（TPL-219: 進入規則を 2 箇所に書き分けない）。
2. 回廊レーンを資源キーの割り当てに載せる。現在の `claimed` は「y 範囲が重なれば 1 本占有」だが、
   `distributeGutterLanes` と同じ interval partitioning にすれば、y 範囲が重ならない 2 本は同じ
   列を共有できる。新しくできる水平の走り（チャネル内）は `collectChannels` の run の定義
   （内部 waypoint 間の水平 segment で前後が垂直）を自動的に満たすので、slice A のレーン割り当てに
   登録なしで参加する。これが TPL-1954 の要求そのものなので、**チェーンがまだ出さない形での
   参加をテストで固定する**。
3. frames のあるビューで内部回廊を出すかは本 PR では変えない（`frames.length === 0` のゲートを
   維持する）。ADR-1859 の grouped 保証を弱めない。緩和は「frame をまたがない回廊だけ許す」形で
   別途検討する（未解決の問い）。
4. 計測: ガター送り 538 → ?、右半分 waypoint 比率 48.0% → ?、交差数、貫通 0 の維持、
   共線ペア 0 の維持。`Knowledge` view の右半分比率 204/460 は ADR-2598 が
   「slice D でしか下がらない」と書いた数字なので、ここで追う。

**第 2 段: 列の予約**

1. 予約の単位は「**カード `a` と `b` の間に幅 w**」。`a` / `b` はその行で列の両隣に来るカードの
   **id**（`rows: string[][]` が返すのは id なので、前段の出力からそのまま取れる）。座標でも
   序数でも持たない — 座標は 2 パス目で動き、**序数は順序が変われば別のカードを指す**
   （`sortByBarycenter` が走る drill-down 経路では順序が入れ替わりうる）。
   適用時に `rows` の中で `a` と `b` を引き、**隣接していれば**その位置に w を挿入する。
   隣接していなければ（片方が別の行に移った、間に別のカードが入った）**その予約は破棄して
   既定の配置に戻す**（never worse）。行の指定も同様に、序数ではなく `a` が属する行として引く。
2. `placeNodesInLayers` に `extraGapBeforeRow` の水平版（`extraGapBeforeColumn`: 行序数 →
   カード序数 → 幅）を足す。挿入は行内の x オフセットに加算するだけで、カードの順序も層割当も
   変えない。
   **鍵の安定性（TPL-2611 の核心）**: 予約の x 挿入は `wrapLayerIntoRows` が行を確定した**後**に
   適用し、折り返しをやり直さない。`wrapLayerIntoRows` は `maxWidth` で折り返すので、予約で
   広がった行幅を折り返し判定に食わせると行の構成そのものが変わり、予約が鍵にしている行序数と
   カード序数が指す先が入れ替わる。よって折り返しは**予約前の幅で判定する**（1 パス目と同じ
   `rows` が出る）。結果として予約分だけ行が `widthBudget` を超えうるが、それは「通路のために
   意図的に広げた分」であって折り返し規則の破れではない。
   テストで固定すること: 予約を与えたときと与えないときで `rows` の要素とその順序が完全に一致
   すること。この不変が成り立つので 1 の照合は通常必ず成功し、破棄経路は保険として働く。
3. 列を行をまたいで揃える: 1 本の列は「通過する行の集合 R」に対して 1 つの予約グループを作り、
   各行 r ∈ R について隣接ペア `(a_r, b_r)` を「列の目標 x（始点と終点の中点）がその行のどの
   カード間に落ちるか」で決める。各行が同じ幅 w を同じ順序で挿入するので、中央寄せ後の実 x は行ごとに
   ずれうる。**ずれの許容幅を超えた列は予約を取り下げてガターに戻す**（never worse）。
4. 需要は本数ではなく interval partitioning のピーク（ADR-2598 が実装で設計を覆した点 1 と同じ）。
   同一ターゲットへ入るエッジは 1 列を共有する。
5. 既存の 2 パス目に合流させる。`channelReservations`（行）と列の予約を同じ 1 回の再配置で適用し、
   `placementPasses` は 1 か 2 のまま。予約が空のビューは 1 バイトも変わらない。
6. **`widthBudget` / `widthBound` と予約の契約**（ADR に明記する）:
   - `widthBudget` が縛るのは**折り返しだけ**で、最終的な canvas 幅ではない。予約は折り返しの
     後段で幅を足すので、予約が入ったビューの canvas 幅は `widthBudget` を超える。これは
     ADR-2593 の時点でも side external column とコンテナ chrome が同じ性質を持っており、
     新しい破れではない。
   - `widthBound`（「より広い予算なら結果が変わりうるか」）は**1 パス目の配置だけで判定する**。
     予約は折り返し判定に入らないので、2 パス目が `widthBound` を変えることはない。
   - **幅予算は再探索しない**（ADR-2598 と同じ判断）。ADR-2593 の面積評価は予約前の canvas に
     対して行われ、予約分は評価に入らない。再探索すれば勝つ予算が変わり、予約が鍵にしている
     行序数ごと崩れる（ADR-2593 が「配置は予算に対して単調でない」と測ったとおり）。
     予約後の面積は**出力として記録する**にとどめ、目的関数には返さない。

**共通**

7. AT: `docs/acceptance/` に新規 1 件（2611）。TC は:
   - 側面 stub が兄弟で塞がれた長いエッジが、空き列へチャネル経由で入る（ガターに出ない）
   - 空き列が無いビューで列が予約され、予約後にそのエッジが内部を通る
   - 予約が要らないビューの SVG がバイト単位で不変
   - 予約を与えたときと与えないときで `rows`（行の構成と順序）が完全に一致する（鍵の安定性）
   - 予約が指すカードのペアがもう隣接していない場合、その予約が破棄され既定の配置に戻る
   - 同じ入力を 2 回レンダリングして同一（決定性）
   - `placementPasses` が 2 を超えない
   - 貫通 0 と共線ペア 0 が両軸で維持される（TPL-1927）
   - チェーンが現在出さない経路形が、登録なしでレーン割り当てに参加する（TPL-1954）
   - 人手確認: dify の `Knowledge` / `Workflow` view を app で開き、右端の帯が薄くなっていること
8. proactive TPL: TPL-2611（下記）を同 PR で起こす。
9. ADR 昇格: 実装完了後に `docs/adr/2611-layer-spanning-edge-columns.md` として昇格し、本 Design
   Doc は同 PR で削除する。ADR-2598 の「残る限界」の該当行を新 ADR が引き取る。

### 影響範囲・マイグレーション

- 既存ユーザーへの影響: 内部回廊を取れるようになったビューで経路が変わる。幅は第 2 段の予約が
  入るビューでのみ増える（dify で +4.4% 見込み）。`.krs` の書き方は変わらない。
- ドキュメント更新: なし（`docs/spec/` に規定は無い。routing は実装詳細）。
- テスト・examples への影響: `routing-parity.test.ts` の grouped 側のピン留め数値は不変であるべき
  （grouped は内部回廊を提供していないため）。ungrouped の examples でスナップショットが動く可能性が
  ある。TPL-2598 が言うとおり、**柵の corpus が限界に達しているか**を確認する — 現在の 12 モデルは
  どれも内部回廊が枯渇していないので、枯渇するフィクスチャを 1 つ足す。

## 未解決の問い / 決めないこと

- **grouped view で内部回廊を出すか。** 現在は `frames.length === 0` で一律に禁止している。
  「frame をまたがない回廊だけ許す」で ADR-1859 の保証を保てるかは本 PR では決めない。
  grouped 側は trunk が別の解を持っているので、優先度は低い。
- **multi-system root の列予約。** ADR-2598 が「system ごとの行序数で予約する案は slice D の設計で
  再検討する」と残した宿題。第 1 段は予約を必要としないので root でも効く。第 2 段の予約は system 単位の
  行序数で持てば成立するが、system をまたぐ列は定義できない。**第 2 段では multi-system root を
  対象外にする**（slice A の限界を維持）。
- **deploy view の列予約。** 同上。deploy はコンテナ間のエッジが少なく、実モデルで混雑していない。
- **交差数を受け入れ条件に入れるか。** #2611 は「交差が測定可能に減る」を条件にしているが、
  ADR-1859 は「交差は最小化ではなく表現で中和する」と決めており、`routing-parity.test.ts` は
  意図的に交差数を assert していない。**交差数は計測して ADR に記録するが、テストでピン留めしない**
  という扱いを提案する。ピン留めすると #2365 系の経路短縮と綱引きになる。

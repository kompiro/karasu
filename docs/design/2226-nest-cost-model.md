# karasu-nest のコストモデルと free-tier quota 提案

- **日付**: 2026-08-02
- **Issue**: [#2226](https://github.com/kompiro/karasu/issues/2226)（親 [#1990](https://github.com/kompiro/karasu/issues/1990)）／gates [#1994](https://github.com/kompiro/karasu/issues/1994)
- **status**: 計測系は implemented、数値は **measured**（2026-08-05、n=1）
- **関連 ADR**: [ADR-1990](../adr/1990-karasu-nest-pivot-server-reverse.md) 決定 3（service-paid + strict free-tier quota、水準は本 Issue まで保留）、決定 6
- **関連 TPL**: [TPL-2288](../test-perspectives/TPL-2288-background-work-platform-ceiling.md), [TPL-2226](../test-perspectives/TPL-2226-every-key-prefix-must-be-purgeable.md)

## 背景・課題

ADR-1990 決定 3 は「サービス側が推論費を払い、free-tier に厳しい quota を置く」までを決め、**quota の水準を #2226 の実測まで意図的に空けた**。この文書はその空欄を埋めるために書かれているが、埋め方が 2 段になっている。

- **実測系（このスタックで実装済み）**: 1 回の生成が実際に何トークン・何秒・何ファイルだったかを記録し、集計する経路。`GET /admin/metrics` が数字を返す
- **実測（この文書）**: 実サービス経路で 1 回完走させた値。投影を置き換えたが、n=1 である

**実測は自分の public repo に対してのみ取れた。** ADR-1990 決定 6 により、[#1996](https://github.com/kompiro/karasu/issues/1996)（data-trust）が入るまで他人の repo には向けない。したがって「repo 規模の分布」は依然として未知で、**n=1 であることを数値の隣に書く**のが本文書の役割になった。レポートに `pricingAsOf` を載せているのも同じ理由による。

## 計測系の形

| 何を | どこに | 鍵 |
| --- | --- | --- |
| 1 試行のトークン・秒・ファイル数・redaction 数・成否 | `MetricsStore` | `metrics/krs/v1/<inst>/<owner>/<repo>/<sha>/<finishedAt>` |
| 生成済みモデルが読まれた回数（下限値） | `ReadCounter` | `reads/krs/v1/<inst>/<owner>/<repo>/<YYYY-MM-DD>` |
| 集計と単価適用 | `GET /admin/metrics`（bearer token） | — |

設計上の判断を 4 つ記す。

**本文に repo の中身を入れない。** ファイルパスも内容も redaction の値も `.krs` 本文も入れない。owner / repo は**鍵**にだけ置く。metrics store は「実行より長生きし、別のコードから読まれ、誰もこれを repo の内容だと思っていない」という三拍子が揃う場所で、私的データが横に漏れる典型的な経路である（決定 6）。集計レポートが repo 名を 1 つも読まずに作れるのはこの配置のおかげ。

**commit ではなく試行ごとに記録する。** 失敗した実行も課金される。commit だけを鍵にすると、3 回目に成功した試行が課金済みの 2 回を上書きし、レポートはリトライ分だけ支出を過少に報告する。終了時刻を鍵に含めることでこれを避ける。

**purge に含める。** 決定 6 に「ただしトークン数は残す」という但し書きは無い。本文に repo の内容が無くても鍵に名前がある。この観点は [TPL-2226](../test-perspectives/TPL-2226-every-key-prefix-must-be-purgeable.md) に切り出し、`nest-purge-coverage.test.ts` で機械的に検証している。

**集計は list metadata から読む。** `kv.get` は 1 件ごとに subrequest を消費し、Workers はこれを 1 リクエストあたりで上限する。鍵 1 件ごとに値を取得する集計は、およそ千件を超えたところで動かなくなる。**それはレポートが読む価値を持ちはじめる、まさにその時点である。** TPL-2288 と同じ「器の上限を実測に対して先に確かめる」話で、対象が `waitUntil` ではなく subrequest なだけ。

### read 計数は下限値であること

`ReadCounter` は KV の read-modify-write で、KV の読み取りは colo ごとのキャッシュから最大 1 分間返る。したがって**同一 colo での 1 分以内のバーストは 1 件に潰れる**。200 回読まれて 1 と記録されうる。複数 colo は互いを上書きする。

これは「おおよその読まれ具合」を答える指標であって、カウントではない。許容できるのは**ずれる向きが固定されている**からで、この指標は低くしか出ず、低い値はサービスが払える quota より**小さい** quota を主張する。高く出うる指標なら許容できない。レポートは `readsAreLowerBound: true` を返してこれを明示する。

正確な計数を買うなら repo ごとの Durable Object（オブジェクト・migration・リクエストごとのホップ）が要る。下限値であることが判断を阻害すると分かってから払う。

## 実測（2026-08-05、`ddd-by-examples/library` の fork）

**投影は実測に置き換わった。** 以下は `GET /admin/metrics` が返した値で、対象は spike #1991 が人手 gold と突き合わせた 4 repo のひとつ。

| | 投影（旧） | **実測** | 比 |
| --- | --- | --- | --- |
| 1 回あたりのコスト | 想定 $2.15 / 上限 $3.60 | **$0.83** | 投影は 2.6 倍過大 |
| 入力トークン | 0.22M | **117,203** | |
| 出力トークン | 0.042M | **9,767** | 上限 84,000 の 12% |
| 所要時間 | 12〜19 分（spike のローカル値） | **3〜4 分**（p50 191 秒 / p95 266 秒） | 4 倍過大 |
| 読んだファイル | — | **164**（434KB） | 上限 200 に未達 |

出力が上限の 12% しか使われていない点が効いている。投影は「上限の半分」を想定的な 1 回としたが、実際の `.krs` は 300 行・9,950 バイトで、上限には遠い。**コストを決めているのは入力側**（repo の中身を 3 パスに渡す量）で、出力側ではなかった。

所要時間の差は構造の違いによる。spike のローカル harness は per-domain subagent fan-out を行い、こちらは 3 パス固定である。**同じ土俵の比較ではない** — 品質を落として速くなった可能性を排除していないので、#2228（ratchet 検証）と合わせて再評価する。

### この実測の限界

- **成功実行は 1 件**（n=1）。同日の 9 回中 8 回は開発中の失敗で、価格を出せるのは成功した 1 回だけ
- **repo は 1 つ**。164 ファイル・434KB は 4 repo 中もっとも小さい部類で、`Dify` 規模は未測定
- p50 / p95 は失敗実行を含む。失敗も 3〜4 分かかっており（大半は合成まで到達していた）、桁は変わらない

### 構造的上限は変わらない

実測が投影を下回っても、上限の議論は生きている。`MAX_TOKENS`（3 パス合計 84,000）と `DEFAULT_MAX_BYTES_READ`（1 パス 400,000 バイト）が変わらない限り、**1 回のコストは repo の大きさに比例せず $3.60 で頭打ちになる**。実測 $0.83 は「典型」であって「上限」ではない。

上限を決めているのが `generate/run.ts` の `MAX_FILES_FETCHED = 200` / `MAX_FILE_BYTES = 200_000` ではない点も変わらない。後者は取得と redact の量を縛るだけで、モデルに届くのは常に最大 60 ファイル・400KB である。

> **2026-08-02 追記**: 下の提案は [ADR-1994](../adr/1994-karasu-nest-free-tier-quota.md) として決定済み。水準は提案どおり（月 3 回・同時実行 1）。

## #1994 への提案

実測 $0.83、構造的上限 $3.60。個人が払える月額を $50〜100 と置くと、**実測なら月 60〜120 回、上限価格で計算しても月 14〜27 回**。

[ADR-1994](../adr/1994-karasu-nest-free-tier-quota.md) は上限価格で計算して installation あたり月 3 回に決めた。**実測はその判断を否定しないが、根拠を緩める**: 10 installation × 月 3 回は、上限価格の見積りで $108/月、実測なら **$25/月**である。水準を上げる余地は生まれたが、上げるかどうかは別の判断で、n=1 の実測で決めるものではない（下記「未了」）。

提案:

1. **installation あたり月 3 回**を初期 free-tier とする。上限価格で 10 installation なら月 $108。試すには十分で、継続的に回されても破綻しない
2. **同時実行はデプロイ全体で 1**。並列は latency を改善せず、支出速度だけを上げる。#2288 の決定的インスタンス id が既に同一 commit の二重起動を潰しているので、残るのは異なる repo 間の同時実行
3. **同一 SHA の再生成は quota を消費しない**（キャッシュヒットを返す）。ここは既に SHA キーで成立している
4. **失敗した試行も quota を消費する**。課金されているので。ただし GitHub 側 5xx など我々の外側の原因は例外とする余地がある（#1994 で決める）
5. **上限に達したら 429 と、ローカル逆生成ガイドへの導線**。断り方が導線になっていれば、quota は締め出しではなく分岐になる
6. **`claude-opus-5` を維持する。** ADR-1990 決定 4 が品質を差別化要因に置いており、安いモデルで質を落とすのは差別化を捨てて費用を下げることになる。落とすなら quota を下げるほうが筋が通る

**BYO-LLM key の再検討は取り下げる。** 前版はこれを提案していたが、根拠は $12〜19 という誤った単価だった。$3.60 なら service-paid は 10〜20 installation 規模で成立するので、ADR-1990 が zero-setup を理由に退けた判断を覆す理由が無い。再検討が必要になるのは installation 数が 2 桁後半に届いたときで、そのときは実測が揃っている。

## 未了 — n=1 で決めないこと

投影は実測に置き換わったが、**実測は 1 repo・1 回**である。以下が揃うまで quota の水準は動かさない。

- [ ] **repo 規模の分布**。測ったのは 164 ファイル・434KB で、4 repo 中もっとも小さい部類。`Dify` 規模で入力トークンがどう伸びるかは未知。入力側がコストを決めている以上、ここが最大の未知数
- [ ] **失敗率**。ADR-1994 は失敗も課金すると決めた。実測の 9 回中 8 回は開発中の失敗なので率としては使えない。運用時の失敗率が高ければ、実効コストは 1 回あたりの額より上がる
- [ ] **品質との対比**。所要時間が spike の 4 分の 1 なのは、per-domain fan-out をしていないからでもある。安く速いのが劣化の結果でないことは #2228 が確かめる

**引用するときは n=1 と併記すること。** 前版は投影を投影と書かずに引用される危険があり、いまは実測を「実測」と書けるが、母数 1 の実測を分布の代表として扱えば同じ間違いになる。

## 記録: 投影がどれだけ外れたか

| | 初版の投影 | 訂正後の投影 | 実測 |
| --- | --- | --- | --- |
| 1 回あたり | $12〜19 | $2.15（上限 $3.60） | **$0.83** |

初版はレビューで訂正され（spike のローカル harness 値をサーバ側パイプラインに持ち込んでいた）、訂正後も 2.6 倍過大だった。**どちらの誤りも安全側**で、結果として quota を厳しく置いた。緩める方向の訂正は急がなくてよい。

## 背景・課題

プレビューツールバーは system view のリッチなモデルで 10 個以上のコントロールを並べ、通常の
ウィンドウ幅で 2 行に折り返す。#2317 はこれを 2 つの問題に分けており、i18n 側（5 つの英語
ハードコード）は #2332 で解決済み。残るのはレイアウト側で、コントロール数は #2174 の Facets
追加でむしろ増えた。

`spike/preview-toolbar-density` ブランチで 7 案を実装し、同一モデル・同一コントロール集合で
ツールバー高さを実測した（ja / dark / 50-50 分割、34px = 1 行、61px = 2 行）:

| 案 | 1280px | 1440px | 1680px | 1280px (en) | メニューを開かずに届くコントロール数 |
| --- | --- | --- | --- | --- | --- |
| 現状（wrap） | 61 ⚠ | 61 ⚠ | 61 ⚠ | 61 ⚠ | 10 |
| 出口系を 1 メニューに集約 | 61 ⚠ | 34 | 34 | 34 | 6 |
| 幅に応じた overflow（`⋯`） | 36 | 36 | 36 | 36 | 5 / 6 / 8 |
| view state をキャンバスへ | 34 | 34 | 34 | 34 | 10 |
| ハイブリッド（出口系を 1 メニュー） | 34 | 34 | 34 | 34 | 7 |
| **ハイブリッド（採用案・出口系を 3 コントロール）** | **34** | **34** | **34** | **34** | **9** |
| icon-only + tooltip | 34 | 34 | 34 | 34 | 10 |

この計測から 3 つ言える。

1. **現状は 1680px でも、en でも 2 行**。「ja だから」「狭い窓だから」ではなく、コントロール数が
   プレビュー列（ウィンドウ幅の約半分）の幅を単純に超えている。
2. **集約だけでは 1280px の ja に足りない**。6 個まで減らしても ja のラベル幅では折り返す。
3. **overflow は 1 行にはなるが代償が大きい**。1280px では 11 個中 6 個が `⋯` の中に入り、しかも
   左詰めで隠すため Export と Focus という優先度の高い側から消える。優先度順の退避規則を別途
   設計しない限り採れない。

案6 は同じ spike で 2 通り実装・実測した。どちらも全幅で 34px（1 行）で、違いは出口系の畳み方
だけ。

- **6a: 出口系をすべてエクスポートの ▾ に畳む** — 届くコントロール 7 個。共有・Docs も 1 クリック
  遠くなる。
- **6b（採用）: 出口系を 3 コントロールに分ける** — 届くコントロール 9 個。エクスポートの ▾ は
  ファイルを書き出すもの（ドリルダウン / 全図 / draw.io / 全ビューを開く）だけを持ち、`🔗 Share`
  は単独ボタン、ドキュメント系は `📘 Docs ▾`（Reference / ドキュメントサイト）にまとまる。

## 制約・前提

- **ADR-9009（icon + text label 必須）を維持する。** icon-only 案は計測上は 1 行に収まるが、
  spike のスクリーンショットが示す通りラベル無しでは機能を判別できない。ADR-9009 を覆す根拠には
  ならなかったので、本 doc は同 ADR を前提として扱う。
- **コントロールを減らさない。** どれを消すかは本 doc のスコープ外。置き場所だけを変える。
- **`--preview-toolbar-h` の契約を壊さない。** facet overview panel が依存している。
- **z-index はトークンから選ぶ**（TPL-1468）。spike の `z-index: 90` はマジックナンバーで、実装では
  トークン化する。
- **shadcn の `Button` / `DropdownMenu` を使う**（ADR-1368、`.claude/rules/app-ui.md`）。
- スコープ外: キーボードショートカットの追加、コマンドパレットの再編、コントロールそのものの取捨。

## 検討した選択肢

### 案1: 現状維持（折り返しを許容する）

**メリット**

- 変更ゼロ。すべてのコントロールが 1 クリックで届く。

**デメリット**

- 2 行がプレビューの縦を常時 27px 食う。図の面積は karasu の主目的そのもの。
- 折り返し位置が幅とロケールで変わるため、「あのボタンは右上」という位置記憶が育たない。

### 案2: 出口系を 1 メニューに集約する（consolidated）

Export / Share / Docs / 全ビューを開く / 全レイヤー表示 を 1 つの `↓ 出力 ▾` に畳み、
view state 系を左寄せ・出口系を右寄せの 2 ゾーンにする。

**メリット**

- 1440px 以上で 1 行。ADR-9009 に触れない。
- 「図を変える／図を持ち出す」という意味の境界が視覚的にも出る。

**デメリット**

- 1280px の ja では依然 2 行（実測 61px）。ラップトップ幅の日本語ユーザーが救われない。
- Export が 1 クリック遠くなる（トリガーを split button に保てば回避可能）。

### 案3: 幅に応じた overflow（`⋯ n`）

行幅を実測し、入らない分だけドロップダウンへ退避する。

**メリット**

- どの幅でも必ず 1 行。広い窓では今と同じ見え方になる。

**デメリット**

- 1280px で 11 個中 6 個が隠れる。「1 行に収まる」だけで、操作は遠くなる。
- 左詰めで退避するため優先度の高いコントロールから消える。優先度規則・測定タイミング・
  ResizeObserver のフィードバックループなど、実装と検証コストが 4 案中最大。

### 案4: view state をキャンバス上のフローティングバーへ

図を変えるコントロールを図の上に浮かせ、ツールバーには出口系と chrome を残す。

**メリット**

- 実測で唯一、**何も隠さずに全幅で 1 行**（34px）。
- 操作対象（図）と操作子が同じ面に来る。

**デメリット**

- フローティングバーが図に重なる。spike ではパンくずを覆い、オフセットを手当てした。
- ツールバー側は出口系 5 個 + Focus が残るため、これ単独では右側の混雑が残る。

### 案5: icon-only + tooltip

**メリット**

- 最も詰まる（34px、全 10 個）。

**デメリット**

- ADR-9009 の改訂が前提。spike のスクリーンショットでは何のボタンか読めず、ADR-9009 を覆すより
  裏づける結果になった。

### 案6: 案4 + 案2 のハイブリッド（採用）

図を変えるコントロールはキャンバス側のバーへ、持ち出すコントロールはツールバーへ。出口系の
畳み方で 2 通りを実装し、両方を計測した。

**6a — 出口系をエクスポートの ▾ に全部入れる**: ツールバーは `[↓ SVG をエクスポート ǀ ▾]` と
`↗ フォーカス` の 2 コントロールになる。最も少ないが、共有 と Docs もメニューの中に沈む。

**6b — 出口系を 3 コントロールに分ける（採用）**: エクスポートの ▾ は**ファイルを書き出すもの**
だけを持ち（ドリルダウン / 全図 / draw.io / 全ビューを開く）、`🔗 Share` は単独ボタン、
ドキュメント系は `📘 Docs ▾` にまとめる。ツールバーは 4 コントロール。

**メリット**

- 案4 の「1 行・何も隠さない」を保ちつつ、案4 が残していたツールバー右側の混雑も消える
  （6b でも実測 34px）。
- 置き場所の判断基準が 1 つになる — **図を変えるならキャンバス、図を持ち出すならツールバー**。
  今後コントロールが増えたときに、どちらに置くかを数え上げずに決められる。
- 6b はメニューの中身が「何をするものの集まりか」で説明できる。エクスポートの ▾ に共有や
  Reference が混ざる 6a より、開く前に中身を予測できる。
- Export は split button のままなので 1 クリック。ADR-9009 も無傷。

**デメリット**

- 2 か所を実装・検証する必要がある（キャンバスバーの重なり、ツールバーのメニュー構成）。
- 6b でも Reference は 1 クリック遠くなる（`📘 Docs ▾` の中）。コマンドパレットからも到達できる
  ため許容する。

## 現時点の方針

**案6b を採用する** — 実測で 1 行に収まり、かつ view state が何も隠れないのは案4 系統だけであり、
案2 を重ねるとツールバー側も 4 コントロールまで減る（実測 34px、全幅で 1 行）。6a ではなく 6b を
採るのは、1 行に収まるという結果が同じなら、メニューの中身が種類で説明できる側（ファイルを
書き出すもの＝エクスポート、共有＝単独、読み物＝Docs）を選ぶため。加えて、この案だけが
「どちらに置くか」を後続の変更でも機械的に決められる基準（図を変える / 図を持ち出す）を残す。
案3 は 1 行という結果だけを見れば同等だが、その代償として優先度の高いコントロールが幅に応じて消えるため採らない。案5 は ADR-9009
の改訂を要求するのに対し、spike の結果は同 ADR を裏づけたため採らない。

配置は以下とする。

| 面 | 置くもの |
| --- | --- |
| キャンバスバー（図の左上、パンくずの下） | ◇ アイコンモード / グループ化 / ◎ ファセット / ⊖ すべて畳む / ◇ エンティティ / ⊞ 全レイヤー表示（org view では ⬡ ツリー表示） |
| ツールバー（右寄せ） | `[↓ SVG をエクスポート ǀ ▾]`（▾ = ドリルダウン / 全図 / draw.io / ⊟ 全ビューを開く）、`🔗 Share`、`📘 Docs ▾`（Reference / ドキュメントサイト）、`↗ フォーカス` |

「⊞ 全レイヤー表示」は #2317 では出口系に分類されていたが、実際には描かれる図を差し替える操作
なのでキャンバス側に置く。判断基準を 1 つに保つための整理であり、意図的に Issue の分類から外す。

### 実装の指針

1. `PreviewColumn.tsx` からツールバーのマークアップを `PreviewToolbar.tsx` へ切り出す（spike で
   実施済みの分割をそのまま使う）。group-by テーブルは `preview-group-by.ts` へ移し、ツールバーと
   キャンバスバーが同じ 1 つのコントロール定義を読む形にする。
2. キャンバスバー `PreviewCanvasControls` を新設する。
   - `.preview-column` を containing block とした absolute 配置。上端は
     `--preview-toolbar-bottom`（ツールバーの `offsetTop + height`）+ パンくず高さで求める。
   - 狭幅対策として `flex-wrap: wrap` + `max-width: calc(100% - 24px)` + ラベルの
     `white-space: nowrap` を必ず添える（「詰めた問い」1 — 無いと列外にはみ出して壊れる）。
   - 背景は不透明（facet overview panel と同じ理由 — 図の上に半透明を重ねると 2 つの文字が
     同じピクセルに乗る）。
   - `z-index` は `tokens.css` に `--z-canvas-controls: 60` を追加して参照する（TPL-1468）。
   - `--preview-toolbar-bottom` は `PreviewColumn` が publish する。facet overview panel の
     アンカーずれ（「詰めた問い」4）はこの変数を使って
     [#2492](https://github.com/kompiro/karasu/issues/2492) で直す — 本 doc の範囲外。
3. ツールバー側は split button を保ったまま、▾ メニューに ⊟ 全ビューを開く を追加する
   （ファイルを書き出す操作の集まり、という 1 つの説明で閉じる）。`🔗 Share` と `📘 Docs ▾` は
   現状のまま単独で残す。新しい i18n key が要る場合は 4 段以内に収める（TPL-2019）。
   なお ja でも `preview.share.label` は「🔗 Share」、`preview.docs.label` は「📖 Docs」のままで、
   #2332 の翻訳対象から外れている。本 doc では扱わないが、Docs のアイコンを `📘` に変えるなら
   同時に見直す候補になる。
4. `activeView === "matrix"` はツールバー自体を描かない現状を維持する。deploy view は
   キャンバスバーに載るものが「アイコンモード」だけになるため、1 個でもバーを出す
   （出したり消したりする方が位置記憶を壊す）。
5. AT: `docs/acceptance/` に新規ファイル。TC は:
   - ja ロケール・1280px / 1440px / 1680px で `.preview-toolbar` が 1 行に収まる（高さを実測）
   - キャンバスバーとツールバーを合わせて、従来のコントロールがすべて `aria-label` で到達できる
     （TPL-1399）
   - 移設した toggle の `aria-pressed` が両状態で正しく反映される（TPL-1402）
   - キャンバスバー上のクリックが背後の SVG のドリルダウンを誘発しない（TPL-948）
   - facet overview panel が従来どおりツールバー直下に出る（`--preview-toolbar-h` の契約）
   - キャンバスバーの `z-index` がトークン参照である（`FacetSelector.test.tsx` と同じ CSS 規則の
     文字列検証）
   - 1024px（プレビュー列 512px）でキャンバスバーが列内に収まり、2 行に折り返す — ラベルが
     縦積みにならない（「詰めた問い」1）
   - ファセット所属一覧パネルがツールバーに食い込まない（「詰めた問い」4 の既存 bug の回帰防止）
6. ドキュメント: `docs/tools/app.md` / `docs/tools/app.ja.md` のツールバー説明を新しい 2 面構成に
   更新する。
7. ADR 昇格: 実装完了後 `docs/adr/2317-preview-toolbar-density.md` として昇格し、本 Design Doc は
   同 PR で削除する。

## 詰めた問い（spike で計測して確定）

`reports/` の probe（`spike/preview-toolbar-density`）で 4 点を計測した。ツールバーは 960px〜1680px の
全幅で 34px = 1 行のまま、以下はすべてキャンバスバー側の話。

### 1. 狭幅でキャンバスバーが折り返す幅

キャンバスバーの自然幅は 549px（system view 5 コントロール、ja）。プレビュー列がそれを下回ると
折り返す。50-50 分割ではウィンドウ約 1150px が境界。

| ウィンドウ | プレビュー列 | ツールバー | キャンバスバー |
| --- | --- | --- | --- |
| 1680 / 1440 / 1280 / 1152px | 840 / 720 / 640 / 576px | 34px | 35px（1 行） |
| 1024px | 512px | 34px | 62px（2 行） |
| 960px | 480px | 34px | 62px（2 行） |

**素の absolute 配置では折り返さずに壊れる**ことも確認した。バーが列幅を超えたまま
「グループ化」が 1 文字ずつ縦積みになり、高さ 93px・右端のコントロールが列外にはみ出す。
そこで `flex-wrap: wrap` と `max-width: calc(100% - 24px)`、ラベルの `white-space: nowrap` を
バーに与える。上表の 62px はこの 3 行を入れた後の値で、2 行に畳んで列内に収まる。

**決定**: 狭幅ではキャンバスバーを 2 行に折り返す。案3 の overflow 機構はバーにも入れない
（`⋯` の優先度規則という宿題を、避けたはずの場所に持ち込むことになるため）。折り返しても図は
縮まず、覆う面積が 1 行ぶん増えるだけである点が、ツールバーが折り返す現状との違い。

### 2. ドリルダウン時（エンティティが出る）

domain までドリルすると `◇ エンティティ` が出るが、その階層では畳めるものが無くなり
`⊖ すべて畳む` が消えるため、バーは 5 コントロールのまま（自然幅 558px）。1152px では
2 行になる（列 576px に対しバー 552px + 余白）。**バーの上限は 6 コントロール**（畳める要素が
あり、かつエンティティを持つ domain）で、そのときの折り返し境界はさらに 1 段上がる。

**決定**: 上限 6 を前提にする。それを超える追加は、キャンバスバーではなくコントロール自体の
取捨を検討する合図とする。

### 3. フォーカスモード

プレビューが全幅（1280px）になり、ツールバー 34px・バー 35px。どちらも 1 行で、バーが図を
覆う割合はむしろ下がる。

**決定**: フォーカスモードでもキャンバスバーを出したままにする。消すと「フォーカス中は操作が
別の場所にある」という例外を 1 つ増やすことになる。

### 4. バーの上に載る surface と z-index

バーに重なりうるのは 2 つ。ポータルされるエクスポートメニュー（`--z-menu: 3000`）と、
ファセット所属一覧パネル（`z-index: 100` のリテラル）。どちらもバーより上でよい。

**決定**: `tokens.css` に `--z-canvas-controls: 60` を追加する（`--z-handle: 50` と
`--z-dropdown: 100` の間）。バーは常にメニュー・パネルの下、図の上。

**あわせて見つかった既存 bug**: ファセット所属一覧パネルは `top: calc(var(--preview-toolbar-h) + 8px)`
で位置を決めているが、この原点は `.preview-column` の上端であり、あいだにタブバー（36px）がある。
その結果**現状のツールバー（`?toolbar=current`、未改修）でもパネルがツールバーに 28px 食い込んで
いる**（1280px / ja で計測。パネル上端 69px に対しツールバー下端 97px）。#2177 の時点から入っていた
ずれで、本 doc の変更とは独立。[#2492](https://github.com/kompiro/karasu/issues/2492) として
切り出し、そちらで `--preview-toolbar-bottom` に付け替えて直す（3-Yes 判定と TPL の起票も
同 Issue で扱う）。本 doc の実装が publish する `--preview-toolbar-bottom` を、その修正が
そのまま使える。

## 決めないこと

- コントロールそのものの取捨（例: 全ビューを開く をエクスポートメニューに吸収できないか）は
  本 doc では決めない。置き場所の問題と混ぜると判断基準が濁るため。上記 2 の上限 6 に達したときに
  改めて検討する。

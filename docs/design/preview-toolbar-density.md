- **ステータス**: 検討中

## 背景・課題

プレビューツールバーは system view のリッチなモデルで 10 個以上のコントロールを並べ、通常の
ウィンドウ幅で 2 行に折り返す。#2317 はこれを 2 つの問題に分けており、i18n 側（5 つの英語
ハードコード）は #2332 で解決済み。残るのはレイアウト側で、コントロール数は #2174 の Facets
追加でむしろ増えた。

`spike/preview-toolbar-density` ブランチで 5 案を実装し、同一モデル・同一コントロール集合で
ツールバー高さを実測した（ja / dark / 50-50 分割、34px = 1 行、61px = 2 行）:

| 案 | 1280px | 1440px | 1680px | 1280px (en) | メニューを開かずに届くコントロール数 |
| --- | --- | --- | --- | --- | --- |
| 現状（wrap） | 61 ⚠ | 61 ⚠ | 61 ⚠ | 61 ⚠ | 10 |
| 出口系を 1 メニューに集約 | 61 ⚠ | 34 | 34 | 34 | 6 |
| 幅に応じた overflow（`⋯`） | 36 | 36 | 36 | 36 | 5 / 6 / 8 |
| view state をキャンバスへ | 34 | 34 | 34 | 34 | 10 |
| icon-only + tooltip | 34 | 34 | 34 | 34 | 10 |

この計測から 3 つ言える。

1. **現状は 1680px でも、en でも 2 行**。「ja だから」「狭い窓だから」ではなく、コントロール数が
   プレビュー列（ウィンドウ幅の約半分）の幅を単純に超えている。
2. **集約だけでは 1280px の ja に足りない**。6 個まで減らしても ja のラベル幅では折り返す。
3. **overflow は 1 行にはなるが代償が大きい**。1280px では 11 個中 6 個が `⋯` の中に入り、しかも
   左詰めで隠すため Export と Focus という優先度の高い側から消える。優先度順の退避規則を別途
   設計しない限り採れない。

## 制約・前提

- **ADR-9009（icon + text label 必須）を維持する。** icon-only 案は計測上は 1 行に収まるが、
  spike のスクリーンショットが示す通りラベル無しでは機能を判別できない。ADR-9009 を覆す根拠には
  ならなかったので、本 doc は同 ADR を前提として扱う。
- **コントロールを減らさない。** どれを消すかは本 doc のスコープ外。置き場所だけを変える。
- **`--preview-toolbar-h` の契約を壊さない。** facet overview panel が依存している。
- **z-index はトークンから選ぶ**（TPL-1468）。spike の `z-index: 90` はマジックナンバーで、実装では
  トークン化する。
- **shadcn の `Button` / `DropdownMenu` を使う**（ADR-1368、`.claude/rules/app-ui.md`）。
- スコープ外: キーボードショートカットの追加、コマンドパレットの再編、コントロールそのものの取捨。

## 検討した選択肢

### 案1: 現状維持（折り返しを許容する）

**メリット**

- 変更ゼロ。すべてのコントロールが 1 クリックで届く。

**デメリット**

- 2 行がプレビューの縦を常時 27px 食う。図の面積は karasu の主目的そのもの。
- 折り返し位置が幅とロケールで変わるため、「あのボタンは右上」という位置記憶が育たない。

### 案2: 出口系を 1 メニューに集約する（consolidated）

Export / Share / Docs / 全ビューを開く / 全レイヤー表示 を 1 つの `↓ 出力 ▾` に畳み、
view state 系を左寄せ・出口系を右寄せの 2 ゾーンにする。

**メリット**

- 1440px 以上で 1 行。ADR-9009 に触れない。
- 「図を変える／図を持ち出す」という意味の境界が視覚的にも出る。

**デメリット**

- 1280px の ja では依然 2 行（実測 61px）。ラップトップ幅の日本語ユーザーが救われない。
- Export が 1 クリック遠くなる（トリガーを split button に保てば回避可能）。

### 案3: 幅に応じた overflow（`⋯ n`）

行幅を実測し、入らない分だけドロップダウンへ退避する。

**メリット**

- どの幅でも必ず 1 行。広い窓では今と同じ見え方になる。

**デメリット**

- 1280px で 11 個中 6 個が隠れる。「1 行に収まる」だけで、操作は遠くなる。
- 左詰めで退避するため優先度の高いコントロールから消える。優先度規則・測定タイミング・
  ResizeObserver のフィードバックループなど、実装と検証コストが 4 案中最大。

### 案4: view state をキャンバス上のフローティングバーへ

図を変えるコントロールを図の上に浮かせ、ツールバーには出口系と chrome を残す。

**メリット**

- 実測で唯一、**何も隠さずに全幅で 1 行**（34px）。
- 操作対象（図）と操作子が同じ面に来る。

**デメリット**

- フローティングバーが図に重なる。spike ではパンくずを覆い、オフセットを手当てした。
- ツールバー側は出口系 5 個 + Focus が残るため、これ単独では右側の混雑が残る。

### 案5: icon-only + tooltip

**メリット**

- 最も詰まる（34px、全 10 個）。

**デメリット**

- ADR-9009 の改訂が前提。spike のスクリーンショットでは何のボタンか読めず、ADR-9009 を覆すより
  裏づける結果になった。

### 案6: 案4 + 案2 のハイブリッド（採用）

図を変えるコントロールはキャンバス側のバーへ、持ち出すコントロールは Export の split button 1 つに
畳む。ツールバーに残るのは `[↓ SVG をエクスポート | ▾]` と `↗ フォーカス` の 2 コントロールだけ。

**メリット**

- 案4 の「1 行・何も隠さない」を保ちつつ、案4 が残していたツールバー右側の混雑も消える。
- 置き場所の判断基準が 1 つになる — **図を変えるならキャンバス、図を持ち出すならツールバー**。
  今後コントロールが増えたときに、どちらに置くかを数え上げずに決められる。
- Export は split button のままなので 1 クリックのまま。ADR-9009 も無傷。

**デメリット**

- 2 か所を実装・検証する必要がある（キャンバスバーの重なり、ツールバーのメニュー構成）。
- 共有 / Docs / 全ビューを開く が 1 クリック遠くなる。いずれも「思考の途中で押すもの」ではない
  ため許容する（#2317 の分類と同じ判断）。

## 現時点の方針

**案6 を採用する** — 実測で 1 行に収まり、かつ何も隠れないのは案4 系統だけであり、案2 を重ねると
ツールバー側も 2 コントロールまで減る。加えて、この案だけが「どちらに置くか」を後続の変更でも
機械的に決められる基準（図を変える / 図を持ち出す）を残す。案3 は 1 行という結果だけを見れば
同等だが、その代償として優先度の高いコントロールが幅に応じて消えるため採らない。案5 は ADR-9009
の改訂を要求するのに対し、spike の結果は同 ADR を裏づけたため採らない。

配置は以下とする。

| 面 | 置くもの |
| --- | --- |
| キャンバスバー（図の左上、パンくずの下） | ◇ アイコンモード / グループ化 / ◎ ファセット / ⊖ すべて畳む / ◇ エンティティ / ⊞ 全レイヤー表示（org view では ⬡ ツリー表示） |
| ツールバー（右寄せ） | `[↓ SVG をエクスポート ǀ ▾]`（▾ の中に ドリルダウン / 全図 / draw.io / 🔗 共有 / ⊟ 全ビューを開く / 📖 Reference・Docs サイト）、`↗ フォーカス` |

「⊞ 全レイヤー表示」は #2317 では出口系に分類されていたが、実際には描かれる図を差し替える操作
なのでキャンバス側に置く。判断基準を 1 つに保つための整理であり、意図的に Issue の分類から外す。

### 実装の指針

1. `PreviewColumn.tsx` からツールバーのマークアップを `PreviewToolbar.tsx` へ切り出す（spike で
   実施済みの分割をそのまま使う）。group-by テーブルは `preview-group-by.ts` へ移し、ツールバーと
   キャンバスバーが同じ 1 つのコントロール定義を読む形にする。
2. キャンバスバー `PreviewCanvasControls` を新設する。
   - `.preview-column` を containing block とした absolute 配置。上端は
     `--preview-toolbar-bottom`（ツールバーの `offsetTop + height`）+ パンくず高さで求める。
     既存の `--preview-toolbar-h` は facet overview panel の契約なので変えず、新しい変数を足す。
   - 背景は不透明（facet overview panel と同じ理由 — 図の上に半透明を重ねると 2 つの文字が
     同じピクセルに乗る）。
   - `z-index` は `tokens.css` に `--z-canvas-controls`（`--z-handle` と `--z-dropdown` の間）を
     追加して参照する（TPL-1468）。
3. ツールバー側は split button を保ったまま、▾ メニューに 共有 / 全ビューを開く / Docs を
   セクション区切りで追加する。i18n key は `preview.output.*` 配下に 4 段以内で足す（TPL-2019）。
4. `activeView === "matrix"` はツールバー自体を描かない現状を維持する。deploy view は
   キャンバスバーに載るものが「アイコンモード」だけになるため、1 個でもバーを出す
   （出したり消したりする方が位置記憶を壊す）。
5. AT: `docs/acceptance/` に新規ファイル。TC は:
   - ja ロケール・1280px / 1440px / 1680px で `.preview-toolbar` が 1 行に収まる（高さを実測）
   - キャンバスバーとツールバーを合わせて、従来のコントロールがすべて `aria-label` で到達できる
     （TPL-1399）
   - 移設した toggle の `aria-pressed` が両状態で正しく反映される（TPL-1402）
   - キャンバスバー上のクリックが背後の SVG のドリルダウンを誘発しない（TPL-948）
   - facet overview panel が従来どおりツールバー直下に出る（`--preview-toolbar-h` の契約）
   - キャンバスバーの `z-index` がトークン参照である（`FacetSelector.test.tsx` と同じ CSS 規則の
     文字列検証）
6. ドキュメント: `docs/tools/app.md` / `docs/tools/app.ja.md` のツールバー説明を新しい 2 面構成に
   更新する。
7. ADR 昇格: 実装完了後 `docs/adr/2317-preview-toolbar-density.md` として昇格し、本 Design Doc は
   同 PR で削除する。

### 影響範囲・マイグレーション

- 既存ユーザーへの影響: ボタンの位置が変わる。共有 / 全ビューを開く / Docs はメニュー内に移動し
  1 クリック遠くなる。消えるコントロールは無い。
- ドキュメント更新: `docs/tools/app.md`、`docs/tools/app.ja.md`。
- テスト・examples への影響: `PreviewColumn.test.tsx` のツールバー関連アサーションが 2 面に分かれる。
  examples への影響は無い。

## 未解決の問い / 決めないこと

- **狭幅（<1100px）でキャンバスバー自身が折り返す可能性。** system view で 6 個並ぶため、
  プレビュー列が 500px を切ると折り返しうる。実測は 1280px 以上でしか取っていない。実装時に
  下限を測り、必要ならキャンバスバー側にだけ overflow（案3 の機構）を入れるかを決める。
- **フォーカスモード時の扱い。** プレビューが全幅になるためツールバーは確実に 1 行だが、
  キャンバスバーを出したままにするかは実装時に見て決める。
- コントロールそのものの取捨（例: 全ビューを開く は Export メニューに吸収できるのではないか）は
  本 doc では決めない。置き場所の問題と混ぜると判断基準が濁るため。

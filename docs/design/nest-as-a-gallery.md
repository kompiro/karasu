## 背景・課題

ADR-1990 は **server-side reverse** を決め、「ゼロ設定（App を入れる → 図が出る）が最大の差別化」と位置づけた。ピボットから 3 週間で、その手段のコストが推定ではなく実測になった。

- 1 ラン **$3.15**（#2226）。失敗しても同額で、[ADR-1994](../adr/1994-karasu-nest-free-tier-quota.md) の枠を 1 消費する
- [ADR-1996](../adr/1996-karasu-nest-data-trust.md) の未了 6 件（zero-retention 契約・privacy policy・ToS 責任制限・DPA・公開先・問い合わせ窓口）は**すべて法務**で、すべてブロッカー。ADR-1990 自身が「技術ではなくここが solo 運用の重り」と書いている
- 最初の 1 回が通るまでに 5 回以上の失敗と、[#2374](https://github.com/kompiro/karasu/issues/2374) / [#2379](https://github.com/kompiro/karasu/issues/2379) の起票を要した

本文書が検討するのは、**生成をサービスから外し、ユーザーが自分の環境で reverse した `.krs` を預かって共有するギャラリー**にする案である。

## 現状（インベントリ）

### ピボットの動機と、それを満たす手段

ADR-1990 が挙げた動機は 2 つで、どちらも **server-side 生成を必要としない**。

| 動機 | server-side 生成での解 | ギャラリーでの解 |
| --- | --- | --- |
| private repo が開けない（#1960） | installation token で fetch する | **問題が発生しない** — サービスはソースを見ない |
| repo に `.krs` が commit されていない | サービスが生成する | 投稿を受け付ける（commit 不要） |

**server-side 生成は目的ではなく手段として選ばれていた。** これが本文書の出発点である。

### いま `packages/nest` にあるもの

ギャラリーに転じたとき、何が残り何が消えるかを先に確定させる。

| モジュール | 役割 | ギャラリーでの扱い |
| --- | --- | --- |
| `store/` | 生成物の SHA-keyed キャッシュ、`owner/repo` ディレクトリ、purge | **残る**（保存対象が生成物から投稿物に変わるだけ） |
| `routes/repo.ts` | `GET /<owner>/<repo>` | **残る** |
| `routes/health.ts` | binding 報告 | 残る（項目は減る） |
| `github/` | App JWT・installation token・tarball 取得・PR 作成 | **大半が消える**。投稿の帰属確認に一部残る可能性 |
| `reverse/` | survey → decompose → synthesise → repair | **消える** |
| `redact/` | egress 前の資格情報置換 | **消える**（送る先が無い）。ただし投稿物の scan は別途要否を判断 |
| `generate/`, `quota/`, `meter/` | Workflow・枠・計測 | **消える** |
| `deliver/` | PR 還元 | **消える**（ユーザーが自分で commit する） |

`packages/nest` のおよそ半分が削除され、残るのは**保存と配信**である。

### 制約として効いている過去決定

- [ADR-1783](../adr/1783-karasu-nest-hosted-preview.md) は inline share をステートレスにした理由を「**DB・保存型 paste・モデレーション面を持たず**、運用負荷ゼロ」と書いた。ギャラリーはこの 3 つを持つ
- [ADR-2249](../adr/2249-permalink-generation-seam.md) は「2 つの面は実行時に接続されず、repo で合流する」と決めた。投稿を受け付けると**合流点が repo でなくなる**
- [ADR-2262](../adr/2262-nest-intake-and-completion.md) は起動権限を installation に閉じ、完了通知を PR 還元にした。生成が無ければ両方とも意味を失う

## 制約・前提

- **`.krs` は構造のみ**という性質は変わらない。投稿物を保存することは、生成物を保存することと同じ種類の行為である
- ローカル reverse の手段は既にある（`.claude/skills/reverse-architecture/SKILL.md`、`karasu` CLI、`docs/guide/reverse-engineering-with-ai.md`）。ADR-1783 の「reverse はドキュメントで案内」は生きている
- #2378 と両立しない。**どちらを採るかを決めてからでないと #2378 のレビューが宙に浮く**
- 本文書は ADR-1990 を supersede しうる。採らない場合も、**なぜ採らないか**を記録する必要がある（動機 2 つが server-side 抜きで満たせる事実は消えないので、この問いは再浮上する）

## 検討した選択肢

### A. ギャラリーへ転じる（生成を廃止）

サービスは投稿された `.krs` を預かり、閲覧・共有・permalink を提供する。生成はユーザーの環境で行う。

- data processor ではなくなる。未了 6 件のうち **zero-retention 契約と DPA の 2 件が消え、残る 4 件は性質が変わる**（下記「決めたこと」の訂正を参照）
- 推論費ゼロ。quota 機構（#1994 / #2382）が不要になる
- `packages/nest` の約半分が削除され、維持面が縮む
- **ゼロ設定を失う**。#1960 の「実質ローカルツールに収束」批判を正面から受ける
- **モデレーション面を持つ**（ADR-1783 が意図的に避けたもの）

### B. 現状維持（server-side 生成）

- ゼロ設定という差別化を保つ
- 法務 6 件が未了のまま。他人の private repo に向けられない状態が続く
- 1 ラン $3.15 をサービスが負担し続ける

### C. #2378 の方向（生成を維持し、public repo へ公開範囲を広げる）

- 起動を運用者に閉じたまま、読む人を増やす
- 法務の重りは**軽くなる**（public repo なら private コードの処理が無い）が消えはしない（ToS・privacy policy は public でも要る — ADR-1996 の却下記録）
- 推論費は残り、むしろリクエスト増で伸びる

### D. 段階案 — ギャラリーを土台に、生成を後付けする

投稿を基本とし、installation がある repo に限って server-side 生成も提供する。

- 移行が滑らか。生成を止めずに済む
- **両方の重りを背負う** — モデレーション面と data processor 責任が同時に発生する。ADR-1996 の 6 件は 1 件も減らない
- 「ゼロ設定が売り」と「投稿してもらう」が同居し、**サービスが何であるかの説明が 2 つになる**

## 現時点の方針

**まだ無い。** 下の問いが未解決で、どれも技術ではなく製品の判断に属する。

ただし 1 点だけ確定している: **#2378 のレビューはこの決着まで保留すべき**である。逆を向いた 2 つの提案を同時に進めると、どちらの前提も検証できない。

## 決めたこと

| 論点 | 決定 |
| --- | --- |
| 方向 | **ギャラリーへ転じる。** ADR-1990 決定 1（server-side reverse）と決定 3（service-paid inference）を supersede する |
| 投稿の資格 | **GitHub repository に紐づけない。** 任意の `.krs` を投稿でき、GitHub は**投稿者の認証（本人性）にだけ**使う。push 権限の証明には使わない |
| URL 空間 | **投稿 id の独立した名前空間。** `owner/repo` は使わない |
| 品質保証 | **parse と structure-only 検査のみ。** 分解の質は投稿者のもの |

### 訂正 — 法務は消滅ではなく縮小である

本文書の初版は「法務の重り 6 件が消滅する」と書いた。**投稿を repo に紐づけず、GitHub ログインで本人性だけを預かる**と決めたことで、これは不正確になった。内訳はこうなる。

| ADR-1996 の未了 | ギャラリーでの扱い |
| --- | --- |
| Anthropic との zero-retention 契約 | **消滅** — モデルを呼ばない |
| 企業向け DPA の要否判断 | **消滅** — 他人のデータを処理しない |
| privacy policy の起草と法務レビュー | **残る（縮小）** — 保持するのは GitHub アカウント識別子と投稿物。他人の private コードの処理ではないので記述量は大幅に減る |
| ToS（責任制限） | **残る** — 公開プラットフォームには必要。むしろ投稿物の権利帰属という新しい条項が要る |
| 公開先の決定 | **残る** |
| 問い合わせ窓口 | **残る（重くなる）** — 削除請求に加えて**投稿の取り下げ請求**が来る |

**個人データがゼロでなくなる点は明記しておく。** [ADR-2262](../adr/2262-nest-intake-and-completion.md) は完了通知にメールを採らなかった理由を「karasu-nest が抱える最初の個人データになる。privacy policy の厚み・保持期間・削除請求・subprocessor 開示がすべてそこから発生する」と書いた。GitHub ログインを入れる決定は、**その線を意図的に越える**ことを意味する。越える理由は、匿名投稿を許すと取り下げ請求に応じる相手も、荒らしを止める手段も存在しないためである。

### この 4 つが噛み合っている点

投稿を repo に紐づけないので、`owner/repo` を鍵にする意味が最初から無い — **URL 空間の決定は方向の帰結であって、独立した選択ではない**。結果として [TPL-2249](../test-perspectives/TPL-2249-resolution-stays-deterministic.md)（解決は決定的である）は**満たされる**: `owner/repo` は従来どおり commit された `.krs` だけを指し（app の permalink 面）、投稿物は別の名前空間に居るので、同じアドレスが 2 つのものを指すことがない。

### 消える論点

repo に紐づかないことで、次が対象外になる。

- **PR 還元のラチェット**（ADR-1990 決定 4 のもう一方の柱、[#2228](https://github.com/kompiro/karasu/issues/2228)） — 投稿者は自分のファイルを自分で直して投稿し直す
- [#2400](https://github.com/kompiro/karasu/issues/2400)（配送先パスの不一致）、[#2403](https://github.com/kompiro/karasu/issues/2403)（リクエスト時の配送選択） — 配送そのものが無い
- [ADR-2249](../adr/2249-permalink-generation-seam.md) の合流点 — 2 つの面は repo で合流していたが、ギャラリーは**第 3 の面**として独立する
- `routes/repo.ts`（`GET /<owner>/<repo>`） — 生成物が無いので消える。app 側の permalink 面（commit された `.krs`）は無傷

### 新しく要るもの

- **投稿の取り下げ経路**。投稿者本人と、第三者からの申し立ての 2 系統
- **なりすまし対策**。「これは有名 OSS のアーキテクチャです」と誰でも名乗れる。GitHub ログインが与えるのは**権限の証明ではなく責任の所在**（凍結できるハンドル）である
- **投稿物の権利帰属**を ToS に書く

## #2378 の扱い

**close する。** server-side 生成を維持したまま公開範囲を広げる設計であり、本文書と両立しない。方向が決まった以上、宙に浮かせたまま置かない。

ただし捨てるのは**前提**であって、そこで解かれた問題ではない。#2378 が扱った 3 点はギャラリーでも形を変えて残り、この設計が引き取る:

| #2378 の論点 | ギャラリーでの帰結 |
| --- | --- |
| 認証が無く、第三者が他人の quota を消費できる | quota が無くなるので消える。ただし**投稿に認証が要る**という結論は同じで、GitHub ログインとして引き取る |
| installation の無い repo は構造的に読めない | 投稿なので**発生しない** |
| `GET /<owner>/<repo>` が `.krs` テキストを返すだけで、図として読めない | **図として見せる面は引き取る**（ギャラリーの中心機能）。ただし [ADR-2259](../adr/2259-permalink-payload-cap.md) の 8000 文字上限は**適用されない** — 下記参照 |

**ADR-2259 の上限は inline share 経路の性質であって、描画の性質ではない。** あの上限が効くのは `resolveRepoPermalink` が repo の `.krs` を取ってきて `/s?s=…` に畳み直すからで、縛っているのは **URL に載るサイズ**である。ギャラリーは投稿物をストアから id で配信するので、モデルが URL に載る経路そのものが無い。#2378 が「生成物は上限を超える」と書いた制約は、ギャラリーでは**発生しない**。

なお app 側の permalink 面（commit された `.krs` → `/s?s=…`）は無傷なので、ADR-2259 はその面の決定として引き続き有効である。

`docs/design/nest-public-reading-service.md` と、同 PR が起こした proactive TPL（`TPL-2378`）の扱いは、close 時に判断する — TPL は「public と restricted が同じ経路を共有する」観点なので、ギャラリーでも生きる可能性がある。

## 投稿者による自己管理（コンソール）

**投稿者が自分の投稿を自分で管理できる面を用意する。** 削除・非公開化・差し替えを本人が任意に行える。狙いは問い合わせ工数の削減である。

### 削減できるのは 2 列のうち 1 列だけ

「新しく要るもの」に挙げた取り下げ経路は 2 系統ある。コンソールが効くのは片方だけで、取り違えると効果を過大に見積もる。

| 誰から | コンソールの効果 |
| --- | --- |
| **投稿者本人**（消したい・直したい・間違えて出した） | **消える。** ボタン 1 つで完結し、人手のキューに入らない |
| **第三者**（なりすまし・権利侵害・不適切） | **消えない。** 申し立てる人はアカウント保持者ではないので、原理的に self-service できない |

コンソールは**件数**を減らすが、**難易度**は減らさない。残るキューは判断を要するものだけになる — それは元々少なく、元々重い。それでも価値はある。定型作業が消えれば、重い案件に時間を割ける。

### 削除より先に「非公開」を置く

取り下げ要求の多くは「消したい」ではなく「いま人に見られたくない」である。**公開／非公開のトグルを削除と別に用意する**と、可逆な操作で済む要求が削除に流れない。「誤って消した」という問い合わせも生まれない。

### 保持期間の設計が変わる

現行のストアは全部 TTL で切れる（生成物 90 日、計測 400 日）。これは「保存しない」を担保するための設計だった。

**投稿者が管理するコンテンツが黙って消えるのは、この機能の目的と正面から衝突する。** 90 日で消えれば「投稿したはずの図が無い」という問い合わせが発生し、**削減しようとしたものを自分で作る**ことになる。ギャラリーの投稿物は**削除されるまで残る**のが自然である。

代償として、保持が無期限になる分は privacy policy に書く必要がある。ただし「投稿者が削除するまで保持し、アカウント削除ですべて消える」は、日数より説明しやすい。

### アカウント削除を明示的に置く

個別の投稿削除だけだと、「全部消してアカウントも消したい」が人手の問い合わせとして残る。**アカウント削除を 1 操作にする**と、いちばん面倒な要求が self-service に落ちる。[TPL-2226](../test-perspectives/TPL-2226-every-key-prefix-must-be-purgeable.md) がそのまま効く — 投稿・アカウント・監査記録のすべての prefix が 1 回の削除で消えることを機械で検証する。既存の `purgeInstallation` が同型の先例になる。

### 新しい面が増える

コンソールは**セッションを持つ最初の面**である（いまの nest は bearer token の admin ルートしか無い）。ADR-1990 決定 5 は secret と state を静的 app に同居させない決定なので、セッション状態は nest 側に置くことになる。UI をどちらに置くかは別問題で、下の問いに挙げる。

## 未解決の問い

1. **コンソールの UI をどこに置くか。** `packages/app`（React が既にある）が nest の API を叩くか、nest が自前でページを返すか。前者は資産を使えるが、セッション付きの面が Pages 側に生えて ADR-1990 決定 5 の線が曖昧になる。後者は nest に UI ビルドを持ち込む
2. **投稿物の保持を無期限にするか。** 削除されるまで残すのが自然だが、放置アカウントの投稿が永久に残ることも意味する。最終アクセスからの期限（例: 2 年）を置くなら、消える前に通知する手段が要る — つまりメールアドレスで、[ADR-2262](../adr/2262-nest-intake-and-completion.md) が避けた個人データに戻る
3. **第三者からの申し立てをどう受けるか。** コンソールでは減らせない列。専用フォームか、GitHub Issue か、連絡先の記載だけか

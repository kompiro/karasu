# 交差ホップを同じ stroke の連続区間ごとに 1 本の `<path>` にまとめる

## 背景・課題

交差ホップ（ある線が別の線を飛び越える箇所に描く小さな弧）が、出力 SVG の大半を占めている。dify モデルの全ビュー bundle では:

- **8.72MB のうち 3.74MB（42.8%）**が `<g class="crossing-marks">` の中身（MB は 10^6 バイト。以下すべて同じ）
- **`<path>` 43,079 個のうち 38,572 個**がホップの弧。`DifyDB` のビュー 1 枚だけで 16,349 個

ホップは 1 個ずつ独立した要素で、毎回同じ表示属性を繰り返している。

```svg
<path d="M 1247.46 343 A 14.27 6 0 0 1 1276 343" fill="none" stroke="#94A3B8" stroke-width="1.5"/>
```

コストを払うのは SVG を表示する側である。アプリのプレビューは 1 枚のビューのために数万の DOM 要素を組む。CLI の描画時間への効きは小さい（全ビューで −30〜50ms、測定の揺れと同程度）ので、本件の目的は **出力サイズと、表示側の要素数** である。

## 現状（インベントリ）

| 観点 | 現状 |
| --- | --- |
| 描画 | `renderCrossingMarks` がホップ 1 個につき `<path>` を 1 個出す。stroke は host エッジのもの（`edgeStroke[hop.edge]`）。ホップの後に junction chip（`<circle>` + `<text>`）が続く |
| 描画順 | `marks.hops` の順。同じ場所に重なるホップ同士は、後のものが上に描かれる |
| stroke の種類 | dify 全ビューで 4 種（`#38BDF8`/1.5 が 16,349、`#94A3B8`/2 が 13,539、`#94A3B8`/1.5 が 8,683、`#A78BFA`/1.5 が 1） |
| 辺との対応 | ホップの要素は辺の id を持たない。`crossing-marks` は辺のグループ（`.krs-edge`）の外にある別レイヤ |
| ホバー | `preview.css` はホバー中のエッジ以外の `.krs-edge` を opacity 0.25 に沈めるが、ホップはそのグループに属さないので**明るいまま残る**。今日すでにそうなっている |
| 利用者 | ホップを個別に選ぶ app / VS Code / e2e のコードは無い |
| テスト | `group-by-render.test.ts` はレイヤに `<path>` / `<circle>` / junction の数字があることを確かめる。色の検査（`stroke="#dc143c"`）は grouped ビューのレイヤ全体に対する 1 件だけで、**ホップの `<path>` の stroke を名指しで確かめるテストは無い**。個数も数えていない。レイヤは `/<g class="crossing-marks">.*?<\/g>/s` で最初の `</g>` まで切り出している |

## 制約・前提

- **見た目を変えない。** 交差マークは「交差＝非接続」を示す記号で、欠けたり上下が変わったりすると意味の読み違いにつながる（TPL-2631）。
- **描画順を黙って変えない。** 同じ点に重なる要素は後に描いたほうが勝つ。どちらが勝つかが意味と無関係な理由（まとめ方）で変わってはならない。
- **レイヤの中に `<g>` を入れ子にしない。** 既存テストの切り出しが最初の `</g>` で止まる。入れ子が要るなら、テストを直すことをこの設計のコストに数える。
- **ホップの幾何（位置・寸法・角度）は変えない。** 変わるのは要素への詰め方だけ。
- out of scope: どの交差にホップを描くか（`computeCrossingMarks`）、junction chip の描き方、ホバー時にホップを辺と一緒に強調・減光すること（#2632 側の仕事。本件はそれを塞がないかだけを見る）。

## 検討した選択肢

計測はすべて dify の全ビュー bundle（`main` の `6c9b13b1` 時点）。表示時間は Playwright の Chromium に `DifyDB` のビュー 1 枚を挿入して描画が終わるまでの時間で、測る順番をラウンドごとに回した 20 ラウンドの中央値。

### 案1: stroke ごとに 1 本（初出順）

同じ stroke のホップを、どこにあっても 1 本の `<path>` のサブパスにまとめる。

**メリット**

- 要素数が最も減る（ホップ 38,572 → 55 個）。出力 8.72 → 6.44MB（−26.2%）。
- 表示時間 55 → 23ms。

**デメリット**

- **描画順が変わる。** 色の違うホップが重なると、どちらが上に来るかがグループの初出順で決まる。dify では色違いでバウンディングボックスが重なる組が 9,798 組あり、**そのうち 4,757 組で上下が入れ替わる**。ホップ同士は意味が同じ（どちらも非接続）なので読み違いにはならないが、「見た目を変えない」を満たさない。

### 案2: 同じ stroke の連続区間ごとに 1 本（採用）

元の順番のまま、stroke が同じホップが**連続している区間**だけを 1 本にまとめる。

**メリット**

- **描画順がそのまま**。描く順序は元の 1 個ずつの描画と同じで、変わるのは要素の区切りだけ。
- 要素数はホップ 38,572 → 894 個（−97.7%）。出力 8.72 → 6.49MB（−25.6%）。案1 との差は出力で 0.6 ポイント。
- `DifyDB` では案1 と同じ出力になる（この図ではすべての stroke が連続している）ので、表示時間も案1 と同じ（55 → 23ms）。

**デメリット**

- 辺との対応は、案1 と同じく持たない。

### 案3: 同じ stroke かつ同じ辺の連続区間ごとに 1 本

案2 の区切りに「同じ辺」を足す。まとめた `<path>` に辺を示す属性を付ければ、ホップを辺ごとに参照できる。

**メリット**

- 描画順はそのまま。
- ホバー時にホップを辺と一緒に強調・減光できる形になる（今日はできていない。インベントリ参照）。

**デメリット**

- 要素はホップ 3,153 個（案2 の 3.5 倍）、出力 6.62MB（−24.1%）、表示時間 33ms（案2 は 23ms）。
- **それを使う側がまだ無い。** 辺を示す属性は、ホバーの CSS がホップを辺に結びつける規則とセットで初めて意味を持つ。その規則は #2632 側で決めることで、属性の形（canonical id か描画上の index か）もそちらが決める。

### 案4: 要素は 1 ホップ 1 個のまま、共通の属性を親に上げる

stroke の連続区間ごとに `<g fill="none" stroke=… stroke-width=…>` で包み、各ホップは `<path d="…"/>` だけにする。

**メリット**

- 描画順はそのまま。ホップ 1 個 1 要素なので、後から辺の属性を足すのも容易。

**デメリット**

- **要素数が減らない**（`<path>` 43,079 個のまま、`<g>` が増える）。出力は −20.4% だが、表示時間は main と変わらない見込み。本件の目的の半分（表示側の要素数）を満たさない。
- レイヤの中に `<g>` が入れ子になり、既存テストの切り出しが壊れる。

### 案5: 変更しない

出力も表示も今のまま。ホップが出力の 43% を占め、密な図ほど表示側の要素数が増える状態が続く。

## 比較

| 観点 | 案1 stroke ごと | **案2 連続区間** | 案3 辺も区切る | 案4 属性を上げる | 案5 変更なし |
| --- | --- | --- | --- | --- | --- |
| 出力（dify 全ビュー） | 6.44MB（−26.2%） | **6.49MB（−25.6%）** | 6.62MB（−24.1%） | 6.95MB（−20.4%） | 8.72MB |
| ホップの要素数 | 55 | **894** | 3,153 | 38,572（+`<g>`） | 38,572 |
| `DifyDB` 表示 | 23ms | **23ms** | 33ms | 変わらない見込み | 55ms |
| 描画順 | 4,757 組が入れ替わる | **不変** | 不変 | 不変 | — |
| 辺ごとの参照 | 不可 | 不可 | 可 | 可 | 不可 |
| 既存テスト | 通る | **通る** | 通る | 切り出しが壊れる | — |

パン（transform の変更）1 回の再描画は、どの案も 33〜38ms で差が出なかった。描く線の量は同じなので、減るのは要素ごとのスタイル計算とレイアウトだけである。CLI の描画時間も、どの案も main から −30〜50ms で、案同士の差は測定の揺れの内側。

## 現時点の方針

**案2（同じ stroke の連続区間ごとに 1 本）を採用する。**

決め手は、描画順を変えずに案1 とほぼ同じ効果が出ることである。案1 との差は出力で 0.6 ポイント、`DifyDB` では同一で、その代わり「色の違うホップが重なった箇所の上下」という、読者が気づかないまま変わる箇所を 4,757 組作らずに済む。

案3 は採らないが、塞がない。まとめる単位（区切りのキー）は 1 箇所で、「同じ辺」を区切りに足すのは小さな変更である。ホバーでホップを辺と一緒に扱う必要が出たとき（#2632 またはその後続）に、その規則と一緒に切り替える。そのときの代償は、出力 +2%、`DifyDB` の表示 +10ms 程度と見積もれている。

### 実装の指針

1. `renderCrossingMarks` で、ホップの `d` を直前のホップと同じ stroke（色と線幅）なら同じ `<path>` のサブパスに足し、違えば新しい `<path>` を始める。サブパスは空白 1 つで連結する。junction chip の出力は変えない。
2. 区切りのキーを 1 つの関数にまとめ、そこに「連続区間で区切る理由（描画順を保つ）」と「案3 に切り替えるときはここにキーを足す」をコメントで残す。
3. テスト（`svg-renderer` 側）:
   - 同じ stroke のホップが連続すると 1 本になり、サブパスの順が元の順と同じ
   - stroke が A, B, A と並ぶと 3 本になる（A を 1 本にまとめない = 描画順を保つ）
   - サブパスを順に展開すると、1 個ずつ描いていたときの `d` の列と一致する（幾何を変えていないことの柵）
   - まとめた各 `<path>` の `stroke` / `stroke-width` が、その区間のホップの host エッジの stroke と一致する（今は誰も検査していない。まとめ方を誤ると色が化けるのに気づけない）
   - junction chip がホップの後に出る順序は変わらない
4. 計測を PR に載せる: dify 全ビューの出力サイズと `<path>` 数、`DifyDB` の表示時間（Chromium）、`karasu render` の時間。
5. changeset: SVG の出力が変わるので `@karasu-tools/core` と `karasu` の両方を名指しで `patch`（`.claude/rules/changesets.md` の cascade 表）。
6. AT: `docs/acceptance/2956-hop-path-grouping.md` を新規に作る。TC は:
   - 同じ stroke の連続するホップが 1 本の `<path>` になる（自動）
   - stroke が交互に並ぶと描画順どおりに分かれる（自動）
   - 展開したサブパスの列が変更前の `d` の列と一致する（自動）
   - examples 全モデルの描画結果を変更前と画素で比べ、差のある画素がすべて**同色ホップの重なり領域**の内側に収まる（Chromium のスクリーンショット比較で自動化できるか実装時に確かめる）。examples には色違いのホップの重なりが 0 組、同色の重なりが 18 組（バウンディングボックス基準）あり、後者では下の「未解決の問い」のアンチエイリアスの差が正しい実装でも出うる。重なり領域の外に差が出たら、まとめ方の誤りである
7. ADR 昇格: 実装完了後、`docs/adr/2956-hop-path-grouping.md` として昇格し、本 Design Doc は同 PR で削除する。

### 影響範囲・マイグレーション

- **既存ユーザーへの影響**: SVG のホップの要素構造が変わる（見た目は変わらない）。出力 SVG を後処理してホップの `<path>` を 1 個ずつ扱っていた外部の利用者がいれば影響するが、ホップは辺の id を持たないので、個別に扱える手掛かりはもともと無い。
- **ドキュメント更新**: `docs/spec/` の変更はない（ホップの要素構造は仕様として公開していない）。
- **テスト・examples への影響**: examples のうちホップを持つ 20 モデル以上で出力のバイト列が変わる。スナップショットを持つテストがあれば更新が要る。既存の crossing-marks のテストは `<path>` の有無と色を見ているだけなので通る見込み。
- **TPL**: [TPL-2956](../test-perspectives/TPL-2956-regrouping-svg-elements-keeps-paint-order.md) を本件の proactive TPL として同じ PR で起こす。案1 が「描画順を黙って変える」形でこの観点に違反しうることが、spike の計測で分かったため。

## 未解決の問い / 決めないこと

- **ホバー時にホップが辺と一緒に沈まない件**は本件では直さない。今日すでに起きている（周囲のエッジが 0.25 に沈むのに、ホップは明るいまま残る）。直すなら案3 の形と、ホップを辺に結ぶ CSS の規則が要り、それは #2632 側で決める。
- **重なった同色ホップのアンチエイリアス**: 同じ stroke のホップを 1 本の `<path>` にまとめると、重なった箇所の縁の画素は 1 回だけ塗られる（別要素なら 2 回重ね塗りされる）。完全に不透明な同色の線なので見た目の差は縁の数画素に限られ、本件ではこれを「見た目を変えない」の範囲内とみなす。examples には同色ホップの重なりが 18 組あるので、画素比較ではこの差を重なり領域の内側に限って許す（実装の指針 6）。差が実際に出たかどうかは AT に記録する。
- **junction chip のまとめ方**は扱わない。junction は grouped ビューでだけ描かれ（ADR-1859）、dify の全ビュー bundle には 1 個も無い。`<text>` を伴うので同じ方法ではまとめられない。

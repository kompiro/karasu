# .claude/rules — authoring ガイド

`.claude/rules/*.md` は、frontmatter の `paths:` にマッチするファイルを編集する
ときに自動で文脈へ読み込まれる行動ルール置き場。Claude 5 世代の lean system
prompt（本体プロンプトの大幅削減）以降、書き方が悪いルールは黙って効かなくなる。
このガイドはその再発を防ぐための authoring 規約。
背景: [Claude 5 世代での rules 崩壊と修正方法](https://zenn.dev/u1/articles/claude5-rules-collapse-and-fix)
／導入経緯は [#2134](https://github.com/kompiro/karasu/issues/2134)。

## どの層に書くか

指示は「変えたい行動の直前に、短く、毎回届く」層に置くほど効く。

| 層 | 効くタイミング | 置くべきもの |
| --- | --- | --- |
| `.claude/rules/*.md`（`paths:` trigger） | 該当ファイルの編集時 | 編集行為に直結する行動ルール |
| スキル（`/hane:*` 等） | 明示呼び出し時 | ワークフロー（triage・release などファイル編集を伴わない作業） |
| hooks / `settings.json` | ツール実行の直前直後 | 機械的強制（lint・drift ガード起動） |
| `CLAUDE.md` / `docs/` | セッション開始時・参照時 | 背景知識・ポインタ（行動を変える力は最弱） |

ファイル編集を伴わない作業（PR トリアージ等）は `paths:` では発火しない。
その作業の入口となるスキルに置くか、ルール冒頭に「この作業を始めたら本ファイルを
明示的に読む」と入口を書く（例: `dependabot.md`）。

## ルール品質チェックリスト

新規作成・改訂時に各項目を自己検証する:

1. **単独で意味が閉じているか** — そのファイルだけ読んで実行できるか
2. **発火条件が観測可能な事実か** — 「重要な変更のとき」「不安なとき」といった
   自己分類は世代交代で不発になる。「変更ファイル集合に X が含まれるとき」
   「エラーが `ERR_X` のとき」のような事実で書く
3. **既定動作と矛盾する場合、優先を明示しているか** — 並列に書くだけでは既定に
   負ける。「既定の◯◯より本節を優先する」と名指しで宣言する
4. **望ましい動きで書かれているか** — 禁止（〜するな）だけでは代替行動を示さず
   抜け道を生む。禁止を書くなら代替行動をセットで書く
5. **判断基準が 1 つか** — 場面の数え上げはモデル変更で漏れる。単一の判定条件に
   畳む
6. **強調は本当に必要か** — 全部が bold /「必ず」だと強調が機能しない。
   1 ファイル内で最も重要な 1〜2 文に絞る
7. **到達状態で書かれているか** — 手順・テンプレ先行ではなく「終わったとき何が
   成り立っているか」を先頭に書き、検証コマンドを添える
8. **守られたか事後判定できるか** — できれば機械チェック（validator / drift
   test / lint hook）を根拠に置く

## このリポジトリでの参考実装

- 到達状態 + 機械検証: `changesets.md`（`pnpm changeset status --since=main`）、
  `examples-sync.md`（`examples.test.ts` の drift ガード）
- 観測可能な発火条件: `dependabot.md`（`ERR_PNPM_*` エラーコードで失敗モードを判別）
- 事後検証可能な出力要求: `spec-audit.md`（指摘に「何を grep したか」を含める）
- 既定動作への明示的例外: `adr.md`「ADR PR の auto-merge」

Width-budget ladder: what a shorter search costs the reader

Issue #2761 option 3 — re-measuring ADR-2593's canvas objective against the number of full placements the ladder buys.

spike/width-budget-ladder Issue #2761 / #2757 slice D model: /workspaces/dify/index.krs 405 drill-down levels wall time: best of 5 × 7 2026-09-10

問い

layout() は searchWidthBudget の候補ごとに配置をまるごとやり直す （BUDGET_STEPS = 12, MAX_BUDGET_MULTIPLE = 6、exhausted で早期終了）。 はしごを短くするのが 回数 を減らす唯一のレバーだが、出力が変わるので ADR-2593 の目的関数（帯の内側で最小キャンバス、floor-first）を仮定せず測り直す必要がある。

この spike は パッチではなくトレードオフ表 を出す。各設定について、読者が失う キャンバス空間と、レンダラが節約する時間を並べる。

方法

  • 参照モデルは /workspaces/dify/index.krs（ADR-2593 / #2598 / #2585 が測った corpus）。 buildDrillDownSvg と同じ歩き方で 405 レベルすべてを描画する （walk は scripts/bench/render.ts から写した）。
  • 面積・帯・placement 回数は harness.ts（このディレクトリ）。 aspect-search.ts / layout.ts にカウンタを入れた spike ビルドで走らせる。
  • wall time は 設定ごとに新しいプロセスで buildAllViewsSvg を best-of-7、それを 5 ラウンド round-robin して最小を採る（allviews-sweep.ts）。 同じプロセスの中で 1 個目より後の候補配置に入った時間も積む（attributed）。 リポジトリ既存の pnpm bench:render <file> --runs 5 も KARASU_SPIKE_LADDER 付きで 3 ラウンド回して突き合わせている（bench-sweep.ts）。
  • 「SVG が変わったレベル」は 未改変の main（origin/main、計測時 62208571）で 先に取った SHA-1 との突き合わせ。today 設定で 0 件になることが、計装が出力に影響していない証拠でもある。
  • 面積と帯の判定は探索が採点するのと同じ寸法（LayoutResult.width/height）。

ADR-2593 の表と数字を直接引き算しないこと。 ADR は dify の 40 view（158.1 → 130.7 Mpx）を 測っており、ここは 405 drill-down レベルの合計なので母集団が違う。比較できるのは形と百分率。

「full placements」= 候補配置 + チャネル予約の再配置の合計（405 レベル分）。 「candidate time attributed」は 1 個目より後の候補配置の中で使った時間を buildAllViewsSvg 1 回ぶんで積んだもの。 wall time と attributed はどちらも 設定ごとに新しいプロセスを立て、5 ラウンド × best-of-7 の最小 （allviews-sweep.ts）。 「levels with a different budget」は today との比較、「SVG differs from main」は未改変 main との byte 比較。

ノイズについて。 同一設定でもラウンド間で 10% 前後ばらつく （例: today = 634.7 / 646.2 / 701.1 / 628.1 / 651.9 ms）。最小を採ってもなお、 差が 30 ms 程度の行は wall time だけでは区別できない。attributed 列は削減対象そのものを測っており、 両者の差分が概ね一致していることが妥当性の裏付けになる。

はしごを短くしても TPL-2593 の 3 条件のうち「候補は入力だけで決まる」「既定候補が先頭で厳密改善のみが勝つ」 「打ち切りは単調性で説明できる（exhausted のみ）」はすべて保たれる。floor-first の意味は 評価した候補の中で厳密に小さいものだけが floor を置き換える、に変わる（未評価の予算にもっと小さい キャンバスがありうる）。

一方 patience 系は打ち切りが単調性で説明できない。ADR-2593「実装で設計を覆した点」1 が まさにこれを取り消している: 行の高さはその行の最も高いカードで決まるので、予算を広げると総高が増えうる。 下の表が示すとおり、patience は実測でも今日と違う予算を選ぶ。

layoutDeploy は size() に exhausted を渡していないので、 常に 12 候補すべてを配置する。dify の deploy view ではその 12 回が 1 バイトも出力を変えない（floor がそのまま勝つ）。11 回ぶんの余分は compile で 11.6 ms 前後。 ADR-2593 が記録した deploy の改善（1274 × 3686 → 今日の 1568 × 2292）は、少なくとも現在のコードでは幅予算の探索から来ていない。 同 ADR のもう半分（deploy コンテナ内 unit の ceil(sqrt(n)) 列）か、その後の変更に由来するはず—— 探索を切っても同じキャンバスが出るので。断定は保留: ADR 当時のコードでは探索が勝っていた可能性を、 この spike では確認していない。

drill-down の walk は論理ビューだけを回るので、上のトレードオフ表の 面積合計に deploy view は入っていない。ここで別に測っているのはそのため。

examples corpus

15 モデル / 40 drill-down レベルを全設定で描画した結果、 どの設定でも today と 1 バイトも変わらない（floor only を含む）。 ADR-2593 が「束ねられた examples 104 view は無変化」と書いたとおり、探索は examples では一度も勝っていない。 #2761 の受け入れ条件「examples corpus で選ばれる予算が変わらないこと」は、はしごを 1 段まで削っても満たされる。

同じパスで決定性も確認した: 各設定・各モデルで 2 回歩いて、ハッシュ不一致は 0 件。

どのレベルが動くのか

405 レベルのうち、そもそも 2 個目の候補に進むのは 68 レベルだけ。したがってはしごを短くして変わりうるのもその範囲で、 実測では下のとおり。floor only（探索を丸ごと外す）で 20 レベルの SVG が変わり、面積は +26.0 Mpx (+6.6%) になる。

結論と推奨

回数を減らすためにはしごを短くするのは、割に合わない。 取るとしても 12 → 8 の 1 段だけで、 それ以上は明確に損。

  • 12 → 8: 面積 +0.3 Mpx（405 レベル合計で +0.1%、動く 9 レベルの中でも +0.5%）で 60 ms（all-views の −9.6%）。この 1 段だけは実質タダに近い。
  • 12 → 6: 面積 +8.8 Mpx（+2.2%、動く 12 レベルでは +8.4%）で 85 ms。
  • 12 → 4 / 3: 面積 +24.7 Mpx（+6.3%、動く 19 レベルでは +17.7%）で 143〜147 ms。 floor only の面積コストの 95% を払って、時間の節約は 68% しか取れない—— 中途半端な短縮はフロンティアの外にある。
  • floor only（= ADR-2593 の探索を丸ごと撤回）: 面積 +26.0 Mpx（+6.6%、動く 20 レベルでは +18.4%）で 210 ms。#2761 の受け入れ条件「最重量レベルで placement を 2 回以下」を満たすのはこの設定だけ。
  • patience（賢い打ち切り）は買うものが無い。 patience 2 は出力を 1 バイトも変えないが 節約は 19〜23 ms でノイズと同程度。patience 1 は 2 レベル動かして 48 ms。どちらも TPL-2593 の「打ち切りは単調性で説明できる」を壊す対価に見合わない。

「割に合わない」と言い切れる根拠は、賞金の中身が routing だということ。 追加候補の 188 ms は all-views の 30% だが、その中身は 1 回あたりの配置コストであって回数ではない。 同じ 188 ms は #2790（routing の障害物を索引化）と #2760 が出力を 1 バイトも変えずに削りにいく対象そのもの。回数を減らす前に単価を下げる方が、 ADR も snapshot churn も要らない。

逆に、どの数字なら見合うか。 #2790 が入って 1 候補あたりの原価が半分になれば、 はしごの残り賞金は 90 ms 前後になり、ADR を 1 本書く価値は無くなる。逆に #2790 が入らず、 親 Issue の受け入れ条件（all-views を約 600 ms 以下）を今すぐ満たす必要があるなら、 12 → 8 の 1 段だけがその条件を単独で満たす最安手（628 → 568 ms）で、 面積の代償は測れる範囲で最小（+0.1%）。

ついでに、出力を変えずに取れる回数削減が 1 つ残っている: layoutDeploy に exhausted を渡すこと（下記「副次的な事実」2）。

計測中に見つかった副次的な事実

  1. analyze() が AST を書き換えるので、同一プロセス内で「同じ入力 → 同じ SVG」が崩れる。 packages/core/src/resolver/warnings.ts は sync cycle 上の辺に edge.cyclic = true を 立てる。buildAllViewsSvg はその analyze を呼ぶので、同じ KrsFile を その前後で描画すると 405 レベルすべての SVG が変わる（cyclic 辺の配線・スタイルが変わり、キャンバス寸法も動く）。 最初これで計測が壊れた。ハーネスは設定ごとにパースし直し、パース直後に analyze を通すことで揃えている。 compile() は毎回パースし直すので製品パスでは表面化しないが、KrsFile を使い回す 呼び出し側（app の useViewSvg のような）には順序依存が潜在する。
  2. layoutDeploy は exhausted を報告しないので、deploy view は 必ず 12 候補を配置する。上の表のとおり dify では出力が floor と同一なので、これは出力を変えずに 減らせる回数（option 1/2 と同じ性質の作業で、option 3 のトレードオフを踏まない）。
  3. #2761 本文の「386 of 405 levels exit after one placement」は実測と合わない。 同じ計装で数えると、2 個目の候補へ進むのは 68 レベル （drill-down 405 レベル中）、all-views 全体では 79 / 425 探索。 探索・候補・再配置の総数（425 / 602 / 17）は Issue の数字と完全一致するので、計装ではなく Issue の一文の方が誤り。結論の向きは変わらない （それでも大多数のレベルは 1 回で抜ける）。
